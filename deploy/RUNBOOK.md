# Runbook

Правила: каждая команда — одной строкой; секреты, адреса и ключи в этот файл не записываются.

## Восстановление из резервной копии

### Что считается проверенной копией

- Копия, не проверенная восстановлением, бэкапом не считается. Проверенной считается только копия, для которой `deploy/restore-check.sh` напечатал `RESTORE OK counters=match migration=<n>`.
- Внешняя копия одна — в закрытом Telegram-канале. Это временное внешнее хранилище: независимой второй копии нет.
- Локальные копии лежат на диске VPS рядом с базой и независимыми не являются.

### Ежемесячная проверка (Mac владельца)

Периодичность: раз в месяц и после любого изменения скриптов бэкапа или ключа.

1. В клиенте Telegram открыть канал бэкапов, сохранить последний файл `aggregator-ГГГГ-ММ-ДД.dump.age`, не переименовывая, и скопировать подпись сообщения целиком.
2. Из корня репозитория: `deploy/restore-check.sh "<файл>" "<файл ключа>" '<подпись>' 2>&1 | tee "$HOME/run-agg-phase6/restore-check.log"`
3. Ожидаемые строки: `file=… sha256=ok size=…`, `counts=…`, последняя — `RESTORE OK counters=match migration=<n>`.
4. Для сравнения прочитать состояние production: `ssh -F ~/.ssh/run_agg.conf run-agg-vps 'sudo -n /usr/local/sbin/agg verify'`
5. Добавить строку в «Журнал проверок восстановления».

Что нужно знать:

- Скрипт восстанавливает копию в отдельный контейнер PostgreSQL без сети и удаляет его по завершении. Расшифрованный дамп на диск не пишется. Образ `postgres` должен быть на Mac заранее: скрипт его не скачивает.
- Приватный ключ хранится только на Mac владельца и на офлайн-носителе. На VPS, в репозиторий и в переписку он не попадает.
- Копия с диска VPS проверяется так же: подпись собирается из имени файла, суммы из `.sha256`, размера и строки `.meta` в виде `aggregator-ДАТА.dump.age sha256=<сумма> size=<байт> counts=<строка .meta>`.
- На VPS состояние копии `usable` означает только совпадение суммы и формат `.meta`. Соответствие счётчиков данным проверяет лишь это восстановление.
- Копия в состоянии `unverified` (строка `ROTATE UNVERIFIED` в логе бэкапа) автоматически не удаляется и проверенной не считается: владелец либо проверяет её восстановлением, либо удаляет вручную.
- Сообщения `age`, `pg_restore` и `psql` скрипт не печатает: PostgreSQL цитирует в них строки данных. Вместо них перед `RESTORE FAIL` идёт строка `detail` с этапом и кодом.

### Причины отказа

Коды выхода: 0 — `RESTORE OK`; 1 — `RESTORE FAIL`, подтверждённый отказ копии или восстановления; 2 — `STOP:`, проверка не выполнена и о копии ничего не говорит; 130, 143, 129 — прерывание сигналом.

| Строка | Смысл | Действие |
|---|---|---|
| `RESTORE FAIL reason=sha` | сумма или размер файла не равны подписи | скачать файл заново и скопировать подпись заново; повторный отказ — копия непригодна |
| `RESTORE FAIL reason=decrypt` | `age` не расшифровал файл: не тот ключ либо файл повреждён | сравнить вывод `age-keygen -y <файл ключа>` с `deploy/vps/backup-recipient`; ключ тот — копия повреждена |
| `RESTORE FAIL reason=restore` | дамп не восстановился (сбой окружения сюда не относится — он даёт `STOP`) | смотреть `kind=` в строке `detail` (таблица ниже) |
| `RESTORE FAIL reason=counters` | счётчики восстановленной базы не равны подписи | порядок разбора — в подразделе «Допустимые расхождения счётчиков»; копия проверенной не считается |
| `STOP: …` | проверка не выполнена: нет `age`, не запущен Docker, образа `postgres` нет локально, контейнер не стартовал, PostgreSQL не стал готов за 60 с, имя контейнера занято, подпись не распознана; во время восстановления или запроса счётчиков — контейнер остановился, не хватило места или памяти, PostgreSQL перестал отвечать, отказал `docker exec` | устранить причину и повторить; при остановке контейнера или нехватке места и памяти — увеличить память, выделенную Docker; образ загрузить вручную: `docker pull postgres:17`; вывода о копии нет |
| `INTERRUPTED signal=…` | проверка прервана (Ctrl-C, закрытие терминала) | повторить; убедиться, что контейнера не осталось: `docker ps -a --filter name=aggregator-restore-check-` |

Строка `detail` перед `RESTORE FAIL`:

| Строка | Смысл |
|---|---|
| `detail stage=age exit=<код>` | отказ расшифровки |
| `detail stage=pg_restore exit=<код> age_exit=<код> kind=archive-version` | версия архива не поддерживается: обновить локальный образ `postgres` и повторить |
| `… kind=archive-format` | файл не является дампом или дамп обрезан |
| `… kind=data table=<имя>` | строка данных не загрузилась в таблицу |
| `… kind=query` | не выполнился запрос схемы |
| `… kind=other` | иная ошибка `pg_restore`; текст сообщения скрипт не печатает |
| `detail stage=counters exit=<код>` | не выполнился запрос счётчиков в восстановленной базе |

Восстановление выполняется с флагами `--no-owner --exit-on-error --single-transaction`: первая же ошибка отменяет всё восстановление.

Общее правило: при отказе проверить копию предыдущего дня. Два отказа подряд — дефект конвейера бэкапа: хост не менять до исправления.

### Допустимые расхождения счётчиков

С подписью копии расхождений быть не должно. Счётчики снимаются отдельным запросом до дампа, поэтому штатное изменение данных в секунды между запросом и снимком возможно. Но никакое расхождение, в том числе на единицы, само по себе безопасным не считается и копию исправной не делает.

Порядок при `reason=counters`:

1. Сопоставить строки `expected=` и `actual=` по каждому ключу.
2. Определить характер изменения: какие ключи отличаются, в какую сторону и чем это объясняется. Регистрация пользователя — `users`; прогон источника — `events_listed`, `source_alerts`, `dedup_candidates=pending`; разбор дублей администратором — `confirmed`, `rejected`, `events_merged`. Сверить объяснение со временем копии.
3. Повторить восстановление той же копии, скачав файл заново.
4. Восстановить копию соседнего дня.

Проверенной считается только копия с `RESTORE OK`. Копия с расхождением остаётся непроверенной при любом объяснении; в журнал вносится отказ с обеими строками дословно и выводом о характере изменения.

Дефект конвейера бэкапа (хост не менять до исправления): необъяснимое расхождение; убывание там, где возможен только рост; отличие `migration`; повтор на соседней копии.

Сравнение с `agg verify` на живой базе: копия старше, поэтому `users` и счётчики событий отличаются на активность после копии. `migration` обязана совпадать с развёрнутой версией. Отметки `backup` и `backup_copy` в копии старые. Недопустимо: `events_listed=0`, отличие на порядок, другая `migration`.

### Аварийное восстановление в production

Выполняется только по решению владельца в момент аварии; каждый шаг — отдельное изменение VPS. Данные после даты копии теряются (до 24 часов).

**Ежемесячно проверяется только восстановление в отдельный контейнер. Шаги ниже на VPS в production не выполнялись.**

1. Mac: копия проходит `deploy/restore-check.sh` (`RESTORE OK`).
2. Root-консоль, если PostgreSQL отвечает, — сохранить текущее состояние: `/bin/bash /usr/local/lib/aggregator/backup.sh`
3. Mac — сумма расшифрованного дампа: `age -d -i <файл ключа> <файл> | shasum -a 256`, затем передача: `age -d -i <файл ключа> <файл> | ssh -F ~/.ssh/run_agg.conf run-agg-vps 'umask 077 && cat > agg-deploy/restore.dump'`
4. Root-консоль: `sha256sum /home/runagg/agg-deploy/restore.dump` — сумма равна шагу 3.
5. `docker compose -f /opt/aggregator/docker-compose.yml stop bot worker`
6. `docker compose -f /opt/aggregator/docker-compose.yml exec -T postgres dropdb -U aggregator --force aggregator`, затем `docker compose -f /opt/aggregator/docker-compose.yml exec -T postgres createdb -U aggregator -O aggregator aggregator`
7. `docker compose -f /opt/aggregator/docker-compose.yml exec -T postgres pg_restore -U aggregator -d aggregator --no-owner --exit-on-error --single-transaction < /home/runagg/agg-deploy/restore.dump`
8. `docker compose -f /opt/aggregator/docker-compose.yml up -d`, затем с Mac `agg verify`; сравнить счётчики с подписью копии.
9. `rm -f /home/runagg/agg-deploy/restore.dump`
10. Ручной запуск бэкапа: отметки в восстановленной базе старые, алерты о просрочке до него верны.

Потеря VPS целиком: новый хост по `deploy/README.md`, затем шаги 3–10.

Предупреждения:

- том `pgdata` не удаляется;
- откат миграций не выполняется;
- восстановление при работающих `bot` и `worker` не выполняется;
- на шагах 3–9 расшифрованный дамп лежит на диске VPS — шаг 9 обязателен.

### Ограничения Telegram как хранилища

1. Нет гарантий сохранности, ротации и контроля целостности — поэтому SHA-256 в подписи и ежемесячная проверка восстановления.
2. Лимит файла для бота — 50 МБ на отправку; за размером дампа нужно следить заранее (`SIZE WARN`).
3. Скачивание через Bot API ограничено 20 МБ; восстановление — ручное скачивание в клиенте Telegram.
4. Потеря аккаунта или канала — потеря всех внешних копий.
5. Токен бота бэкапов лежит на VPS: при взломе VPS возможны удаление сообщений бота за последние 48 часов и отправка мусора. Прочитать копии без приватного ключа нельзя.
6. Telegram одновременно канал алертов и хранилище внешней копии: при его недоступности с VPS теряется и то, и другое.
7. Локальные копии лежат на том же диске, что и база, и независимыми не являются.
