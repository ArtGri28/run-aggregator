# Развёртывание на VPS (Phase 4, PRD-01)

Памятка владельца. Скрипты лежат в репозитории и не содержат IP-адресов, имён хостов и секретов. Каждый скрипт VPS идёт по схеме PREFLIGHT (только чтение) -> APPLY (подтверждение словом) -> VERIFY. Исходники, Go и реестр образов на VPS не нужны: образ собирается на Mac и передаётся по ssh.

## Предпосылки

- Бот создан в BotFather, токен под рукой (вводится скрыто при первом развёртывании).
- Известен ваш числовой Telegram ID (пойдёт в `ADMIN_TG_IDS`).
- В `~/.ssh/config` есть алиас для root-доступа к VPS (ниже `<alias>`).
- Код закоммичен: `ship.sh` берёт тег образа из коммита и останавливается, если файлы сборки изменены и не закоммичены (иначе задайте `TAG=...` явно).
- Docker на Mac запущен.

## Порядок шагов

Все команды с Mac из корня репозитория. Скрипты не запускать параллельно.

1. **Доставка.** `deploy/ship.sh <alias>` — собирает образ `linux/amd64`, проверяет его `deploy/smoke.sh`, передаёт `docker save | gzip | ssh ... docker load`, копирует `docker-compose.yml` и `deploy/vps/*.sh` в `/root/agg-deploy/` и печатает однострочники с SHA256 и строку `IMAGE_TAG=<TAG>`. Дальше `<TAG>` — это значение из этой строки.
2. **A0 host-preflight (лог).** Выполните печатаемую Mac-форму для `host-preflight.sh`. Вывод пишется в `$HOME/run-agg-phase4/host-preflight.log`. Прочтите: какие контейнеры и с какой политикой перезапуска есть на хосте, нужна ли перезагрузка, что с обновлениями и часами.
3. **Решение по хосту.** Хост используется не только проектом: перезагрузка может задеть чужие сервисы (контейнеры с `unless-stopped`/`always`, `tinyproxy`). Решайте сами: шаги 4–5 (обновления и перезагрузку) можно отложить, но шаг 6 нужен в любом случае — без плагина Compose развернуть нельзя.
4. **A1 `host-apply.sh updates`.** Security-обновления без перезагрузки. Скрипт покажет разрешённые источники и попросит ввести слово `UPDATES`.
5. **A2 перезагрузка.** Только вручную, когда готовы: `systemctl reboot`. Скрипты хост не перезагружают.
6. **A1 `host-apply.sh compose`.** Ставит плагин Compose из репозитория Ubuntu (`docker-compose-v2`), слово `COMPOSE`.
7. **A3 host-verify (лог).** Ожидается `HOST VERIFY OK` (Compose не ниже 2.20, docker активен). Строка `reboot-required: yes|no` оценивается вами.
8. **B0 deploy-preflight `<TAG>` (лог).** Образ загружен (`linux/amd64`), права и наличие ключей `.env`, SHA256 compose-файла (сравните с выводом `oneliner.sh` на Mac).
9. **B1 deploy-apply `<TAG>`.** Слово `DEPLOY`. При первом запуске создаёт `/opt/aggregator/.env` (права 600): токен и `ADMIN_TG_IDS` вводятся без эха, `OWNER_CONTACT` — обычным вводом, пароль БД генерируется. Значения не печатаются. Затем поднимает postgres, migrate, bot и worker.
10. **B2 deploy-verify (лог).** Через 1–2 минуты после шага 9. Ожидается `DEPLOY VERIFY OK`.
11. **Первое включение (D-07).** Worker сразу делает первый прогон Марафонца; прогон получает статус `suspect` («первый прогон источника»). В течение пары минут бот пришлёт администраторам алерт с кнопкой `[Принять как базу]`. Нажмите её и подтвердите; в `/runs` прогон станет принятым, а `/start` покажет выдачу. Пока не принято, каталог пуст.

Повторные обновления: `deploy/ship.sh <alias>`, затем B0 (по желанию) и B1 с новым `<TAG>`, затем B2. Прежний тег сохраняется как `IMAGE_PREV`. Откат: `rollback.sh` (слово `ROLLBACK`) — меняет местами `IMAGE_TAG` и `IMAGE_PREV`.

## Однострочники и хеш

`deploy/oneliner.sh <alias> deploy/vps/*.sh` (с `TAG=<TAG>` для скриптов с тегом) печатает для каждого скрипта две формы. VPS-форма:

```
cd /root/agg-deploy && if printf '%s  %s\n' <sha256> <скрипт> | sha256sum -c --quiet -; then bash <скрипт>; else echo 'STOP: HASH MISMATCH'; fi
```

Mac-форма — та же команда через `ssh`. Для скриптов только чтения она пишет вывод в `$HOME/run-agg-phase4/<имя>.log`; для меняющих хост идёт через `ssh -t` без записи (ввод в терминале).

**`STOP: HASH MISMATCH`** означает, что файл на VPS отличается от файла на Mac. Скрипт не запускался. Ничего не править на VPS вручную: запустите `deploy/ship.sh <alias>` заново, чтобы перекопировать файлы и получить новые хеши. Хеши устаревают при любой правке скрипта.

## Логи и секреты

- Логи запусков хранятся только в `$HOME/run-agg-phase4/` вне репозитория; не коммитить и не копировать в `.planning/`.
- Не печатать `.env`, не использовать `docker inspect` контейнеров (печатает окружение с секретами) и `docker compose config` без `-q`; для образа — `docker image inspect --format ...`.
- Не запускать бот локально с тем же токеном: два `getUpdates` дают 409 Conflict обоим.

## Запасные пути

- **Принятие базы из CLI**, если кнопка недоступна:
  `docker compose -f /opt/aggregator/docker-compose.yml run --rm worker worker accept-baseline --source marathonec`
  Слово `worker` дважды: первое — имя сервиса, дальше аргументы целиком заменяют `command` сервиса (иначе будет запущен `/aggregator accept-baseline` и вернётся usage).
- **Перенос `postgres:17` с Mac**, если VPS не достаёт до Docker Hub (`deploy-apply.sh` остановится с подсказкой):
  `docker pull --platform linux/amd64 postgres:17`, затем `docker save postgres:17 | gzip | ssh <alias> 'gunzip | docker load'`. Флаг `--platform` обязателен: Mac по умолчанию возьмёт arm64.

## Правила

- **Никогда `docker compose down -v`**: удалит том с БД, а бэкапов до Phase 6 нет. Остановка без `-v` безопасна; откат образа делается сменой `IMAGE_TAG`.
- Пароль Postgres действует только при первой инициализации тома: менять его в `.env` без `ALTER ROLE` нельзя.
- Не перезагружать хост скриптами; решение о перезагрузке принимает владелец.
- Порт PostgreSQL наружу не публикуется (порты Docker обходят ufw); `deploy-verify.sh` это проверяет.
- Вне этой фазы (Phase 6): ssh root/пароль, ufw, swap, синхронизация часов, `tinyproxy`, резервные копии.
