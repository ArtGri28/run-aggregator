## 1. Краткие выводы

1. **Конвейер сбора, география, слияния и бот почти не зависят от вида спорта.** Бег зашит в четырёх местах: перечень типов события, разбор и корзины дистанций, отсев небеговых записей в адаптерах, тексты бота.
2. **Вида спорта в модели события нет вообще.** Поле `event_type` — это покрытие и формат бегового старта (шоссе, трейл, кросс, стадион, OCR). Спорт подразумевается: все четыре подключённых источника отдают только бег.
3. **Несколько дистанций у события уже поддерживаются.** Не поддерживается другое: дистанция — это одно число в метрах без указания, к какому виду спорта оно относится. Плавание и велоспорт в это укладываются, триатлон — нет.
4. **Минимальный первый шаг — одна колонка `events.sport` со значением по умолчанию `running`.** Существующие события, слияния и записи источников при этом не переписываются.
5. **Справочник спорта и дисциплин стоит держать в коде, а не в таблицах** — так уже сделаны типы, страны анкеты и виды спорта профиля.
6. **Триатлон — самое дорогое направление по модели**, плавание и велоспорт — самые дешёвые. При этом единственный источник, про который в репозитории есть подтверждённые сведения о других видах спорта, — календарь триатлонного клуба (`tristyle`).
7. **Правила дедупликации вид спорта не учитывают.** Автослияние выключено, поэтому ошибочных слияний не будет, но очередь `/dupes` начнёт получать пары «заплыв и забег одного фестиваля».
8. **Поведенческой аналитики нет.** Есть только сводка анкеты `/stats` — это заявленные интересы, а не поведение. Данных о спросе по видам спорта сейчас нет: в production 2 пользователя (на 2026-10-06).
9. **Рекомендуемый порядок:** закрыть Phase 6 → колонка спорта без изменений интерфейса → проверка источников по образцу Phase 1 → один новый вид спорта за выключателем → интерфейс → остальные виды.

## 2. Аудит текущей архитектуры

### 2.1 Модель события

**Факт.** `internal/event/event.go`: `Event` содержит название, даты, место (`CountryCode`, `Region`, `City`, `CityKey`, `Address`), `Type`, `Status`, описание, ссылку регистрации и срез `Distances []Distance`. Поля «вид спорта» нет.

**Факт.** `event.Type` — шесть значений: `road`, `trail`, `cross`, `track`, `obstacle`, `other`. Комментарий: «one of the six race types (MVP.md §2.2)». Те же шесть значений зашиты в ограничение `CHECK` колонки `events.event_type` (`migrations/00001_init_schema.sql`).

**Факт.** `event.Distance` — `Meters int` и `Label string`. Таблица `event_distances` имеет первичный ключ `(event_id, distance_m)`: у события не может быть двух дистанций с одинаковым числом метров.

**Факт.** `Label` из сбора не заполняется никогда: `Prepare` создаёт `event.Distance{Meters: meters}` (`internal/ingest/prepare.go`). Подпись дистанции в карточке (`internal/bot/list.go`) сейчас достижима только из тестов.

### 2.2 Запись источника

**Факт.** `internal/ingest/source.go`: `SourceEvent` — строки как на странице: `Title`, `Date`, `Distances`, `City`, `Region`, `Country`, `TypeLabel`, `RegistrationURL`, `Description`, `EndDate`, `GroupKey`, `Address`, `Timezone`. Поля вида спорта нет.

**Факт.** Там же описан способ расширения без поломки: «Новые поля стоят в конце и с omitempty: payload записей без них (и content_hash) не меняется». Это прямо применимо к новому полю `Sport`.

**Факт.** `source_events.fields` (миграция `00004`) хранит нормализованные поля записи — вход свёртки `event.Fold`. Структура `sourceFields` в `internal/store/events.go` содержит `event_type`; поля спорта нет.

### 2.3 Нормализация

| Что | Где | Зависит от бега |
|---|---|---|
| Город, ключ города, область, часовой пояс, страна | `internal/normalize/place.go`, `regions.go`, `country.go` | нет |
| Дата, время, описание | `internal/normalize/normalize.go` (`Date`, `Time`, `Description`) | нет |
| Тип | `normalize.Type` и карта `types` | да: только беговые подписи, всё остальное — `other` |
| Название для сравнения | `TitleNorm`, `titleStopWords` = «забег», «марафон», «полумарафон» | да |
| Дистанции | `internal/normalize/distance.go`: `Distances`, `namedDistances` («марафон» = 42195, «полумарафон» = 21098) | частично |

**Факт.** `normalize.Distances` понимает километры, метры и мили. Запись «1500 м» или «100 км» разбирается без изменений — для плавания и велоспорта разбор чисел годится.

**Факт.** `Prepare` берёт дистанции из столбца дистанций, а при пустом — из названия (`internal/ingest/prepare.go`, пометка LO-06). Для названия «Марафон 4,2 км» есть защита, для «Велогонка 100» её нет.

### 2.4 Источники

**Факт.** Зарегистрированы четыре источника (`cmd/aggregator/main.go`, `newSources`): `marathonec`, `probeg`, `heroleague`, `tristyle`. Адаптеры `klbamatar` и `runin` написаны, но не подключены — «дают только дубли ПроБЕГа».

**Факт.** Каждый подключённый источник сознательно отсекает всё, кроме бега:

| Источник | Как отсекает | Где |
|---|---|---|
| Марафонец | адрес календаря — раздел бега; в эталоне подписи типа только `trejl` (88) и `shosse` (45) | `internal/ingest/sources/marathonec/testdata/calendar-beg.golden.json` |
| ПроБЕГ | из списка дистанций выбрасываются фрагменты со словами «ходьба», «триатлон», «прыжок», «толкание», «каникросс» | `nonRunning`, `isNonRunning` в `internal/ingest/sources/probeg/parse.go` |
| Лига Героев | берутся только проекты `gonka`, `urban`, `mudrun`; тип всегда `obstacle` | `ocrTypes` в `internal/ingest/sources/heroleague/parse.go` |
| Tristyle.Клуб | адрес списка содержит `specialization=running&only_belarus=on` | `ListURL` в `internal/ingest/sources/tristyle/tristyle.go` |

**Факт.** В фикстуре Tristyle фильтр «Вид спорта» имеет значения: `triathlon`, `swimming`, `running`, `cycling`, `skiing`, `hiking`, `other` (`internal/ingest/sources/tristyle/testdata/list.html`). На странице события вид спорта не указан — «следует из фильтров списка» (`testdata/README.md`).

**Факт.** Tristyle не передаёт `TypeLabel`, Лига Героев передаёт `obstacle`. Все события Tristyle получают тип `other`.

**Факт.** Контракт `ingest.Source` (`Code`, `Policy`, `Fetch`, `Parse`) и оценка прогона (`internal/ingest/quality.go`) от вида спорта не зависят. Первый прогон нового источника всегда `suspect` и требует принятия; рост `parsed` больше чем в 5 раз от медианы — тоже `suspect`.

### 2.5 Дедупликация

**Факт.** `dedup.Decide` (`internal/dedup/decide.go`) пропускает пару через четыре условия: одна страна, записи разных источников (или общий `GroupKey`), даты отстоят не больше чем на день, схожесть названий не ниже `Low` (0,3). Ни тип, ни дистанции не участвуют: в структуре `Side` их нет, комментарий — «в решении о паре они не участвуют (DDP-05)».

**Факт.** Признак `WouldAuto` требует схожести не ниже `High` (0,7), пересечения дат, одного города и единственного партнёра. Автослияние выполняется только при `AutoMerge = true`; по умолчанию и в production — `false` (`internal/dedup/config.go`).

**Факт.** Перебор пар (`WindowPairs` в `internal/dedup/pairs.go`) идёт внутри страны в окне дат. Число сравнений растёт квадратично от числа событий в одном окне.

**Факт.** `event.Fold` собирает поля слитого события: тип — первый не `other` по приоритету источников; дистанции — объединение с допуском `DistanceTolM` (100 м).

**Факт.** Серии внутри одного источника сворачиваются в `Prepare` по `GroupKey` до ближайшей по дате записи.

### 2.6 Бот

**Факт.** Фильтры пользователя — JSON в `users.filters` (`userFilters` в `internal/bot/filters.go`): период, город, корзины дистанций, тип, страна. Новый ключ добавляется без миграции; лишние ключи при чтении игнорируются (`loadFilters`).

**Факт.** Корзины дистанций заданы под бег: «До 10 км», «10–21 км», «21–42 км», «42+ км» (`buckets` в `internal/bot/filters.go`).

**Факт.** Меню типа показывает только типы, реально встречающиеся в будущих событиях страны (`typeMenu`, `store.EventTypes`). «Другое» в меню не выводится.

**Факт.** Отбор выдачи — один фрагмент SQL `listWhere` (`internal/store/listing.go`) с девятью параметрами; им пользуются список, счётчик, города и страны.

**Факт.** Текстовый поиск сравнивает слова запроса со словами названия и города (`matchEvents` в `internal/bot/search.go`); тип и вид спорта не участвуют.

**Факт.** Карточка (`internal/bot/list.go`) выводит дистанции одной строкой в километрах и строку типа со значком; у «Другого» значок — бегун (`typeEmoji`).

**Факт.** Слово «забег» встречается в семи местах `internal/bot/filters.go` и ещё в трёх файлах пакета; в `internal/bot/testdata/screens` 173 эталона экранов. Эталоны правятся только вручную после утверждения владельцем.

**Факт.** Кодек кнопок (`internal/bot/callback.go`): префиксы `m f s p e g r d u h`, предел 64 байта. В семействе `f:` свободны буквы для нового фильтра.

### 2.7 Анкета и профиль

**Факт.** Анкета реализована (Phase 9): пол, возрастная группа, страна и город проживания, виды спорта. Город проживания хранится отдельно от города поиска (`user_profiles.residence_*` против `users.filters`). Анкету можно пропустить.

**Факт.** Виды спорта профиля множественные: `user_profiles.sports TEXT[]` с ограничением на восемь кодов — `run`, `trail`, `ocr`, `bike`, `swim`, `ski`, `tri`, `row` (`migrations/00006_user_profiles.sql`, `profileSports` в `internal/bot/callback.go`).

**Факт.** Профиль не влияет на поиск: решение D-07 Phase 9, комментарий в миграции — «ответы добровольной анкеты отдельно от настроек поиска».

### 2.8 Аналитика

**Факт.** Единственная статистика — `store.ProfileCounts` и команда `/stats`: число пользователей и разрезы анкеты по одному признаку, группы 1–4 показываются как «меньше 5».

**Факт.** Таблиц с действиями пользователей нет: семь миграций создают каталог, прогоны, алерты, слияния, профиль и поддержку. О пользователе хранится один момент времени — `users.last_seen_at`.

**Факт.** Отдельного направления или документа Product Analytics в репозитории нет.

### 2.10 Ответы на вопросы аудита

**Что уже достаточно универсально:** контракт источника, загрузка, сырые ответы, `Prepare` (кроме дистанций и типа), оценка прогона, наблюдение записей, география и часовые пояса, слияние и его отмена, перебор и решение по паре, хранение фильтров, кодек кнопок, анкета, поддержка.

**Что жёстко завязано на бег:**
- `event.Type` и `CHECK` колонки `event_type`;
- `normalize.types`, `titleStopWords`, `namedDistances`;
- `buckets`, `typeLabels`, `menuTypes`, значок по умолчанию;
- отсев небеговых записей в четырёх адаптерах;
- тексты экранов, название проекта и `User-Agent` (`RunAggregator/0.3`, `internal/ingest/config.go`).

**Где предполагается одна дистанция:** нигде — у события их может быть много. Предположение другое: дистанция — одно число метров одного вида спорта, вариант участия равен дистанции.

**Где тип смешан с видом спорта:** в двух местах. `event_type` совмещает дисциплины бега и значение `obstacle`, которое можно считать отдельным видом. `profileSports` ставит в один ряд виды спорта (`bike`, `swim`) и дисциплины бега (`trail`, `ocr`).

**Ограничения для плавания и велоспорта:**
- события попадут в тип `other` и в выдачу «Найти забег» со значком бегуна;
- корзины бесполезны: заплывы почти все окажутся в «До 10 км», велогонки — в «42+ км»;
- карточка покажет заплыв на 1500 м как «1,5 км»;
- бассейн или открытая вода, покрытие, набор высоты хранить негде.

**Ограничения для триатлона:**
- этапы 1,5 + 40 + 10 км будут записаны как три дистанции события и показаны «1,5 · 10 · 40 км»; фильтр «До 10 км» найдёт триатлон как забег;
- вариантов участия (спринт, олимпийская и другие) с собственным набором этапов модель не знает;
- первичный ключ `(event_id, distance_m)` не позволит фестивалю иметь «заплыв 1 км» и «забег 1 км» одновременно.

**Какие существующие данные затрагиваются:** при рекомендуемом первом шаге — никакие (см. §7). В production на 2026-10-06: 537 событий в выдаче, 96 слияний — все из беговых источников.

## 4. Концептуальная модель

### 4.1 Что нужно различать

| Понятие | Пример | Есть сейчас |
|---|---|---|
| Вид спорта | бег, плавание, велоспорт | нет |
| Дисциплина | шоссе, трейл; бассейн, открытая вода; MTB, gravel | частично — `event_type` для бега |
| Формат | триатлон, дуатлон, акватлон | нет |
| Мероприятие | Минский полумарафон | `events` |
| Вариант участия | 10 км; «олимпийская» | только как число метров |
| Этап | плавание 1,5 км внутри триатлона | нет |
| Категория участника | возрастная группа, элита | нет |
| Источник | Марафонец | `sources`, `source_events` |

### 4.2 Варианты

**Вариант 1 — плоский.** У события один вид спорта и одна дисциплина; дистанции как сейчас.
- Плюсы: одна колонка, ничего не переписывается, бег не затронут.
- Минусы: триатлон и фестивали не выражаются; годится для плавания и велоспорта.

**Вариант 2 — полностью нормализованный** (`Sport → Discipline → Event → Race → Leg`): таблицы видов спорта и дисциплин, у события много видов спорта, у события варианты участия, у варианта упорядоченные этапы.
- Плюсы: выражает всё из задания, включая фестивали и этапы.
- Минусы: переписывает запись события, выдачу, свёртку, карточку и отмену слияния; беговое событие из одной строки превращается в три-четыре; расходится с `MVP.md` §2.3 («отдельные таблицы … типов» — вне MVP); выигрыш появляется только на триатлоне.

**Вариант 3 — гибридный, по шагам.**
1. Событию — один основной вид спорта и дисциплина (как вариант 1).
2. Дистанции — вид спорта, когда появится первый фестиваль с дистанциями разных видов.
3. Многоэтапным стартам — отдельная небольшая таблица вариантов участия с этапами; беговые события её не используют.

**Рекомендация.** Вариант 3. Каждый шаг делается только тогда, когда появился источник, которому он нужен; первый шаг совпадает с вариантом 1.

### 4.3 Ответы на вопросы задания

| Вопрос | Ответ |
|---|---|
| Один основной вид спорта? | Да, у события один основной — по нему идёт фильтр. |
| Несколько видов спорта у события? | Не на первом шаге. Фестиваль — либо отдельные события (как их обычно дают источники), либо шаг 2. |
| Последовательность этапов? | Только у многоэтапных форматов, шаг 3. |
| Разные дистанции этапов? | Шаг 3, внутри варианта участия. |
| Несколько вариантов участия? | У одного вида спорта уже есть — это дистанции. У триатлона — шаг 3. |
| События без числовой дистанции? | Уже поддерживаются: Лига Героев дистанций не даёт, поле просто пусто. |
| Категория участника? | Не моделировать: фильтровать по ней никто не будет, источники дают её нерегулярно. |

**Предположение.** Источники чаще представляют фестиваль несколькими отдельными записями, чем одной общей. Не проверено.

## 5. Таксономия

### 5.1 Что вид спорта, а что дисциплина

| Код из задания | Предлагаемая роль | Запись в модели |
|---|---|---|
| `running` | вид спорта | `sport = running` |
| `trail_running` | дисциплина бега | `running` + `trail` (значение уже есть) |
| `swimming` | вид спорта | `sport = swimming` |
| `open_water_swimming` | дисциплина плавания | `swimming` + `open_water` |
| `cycling` | вид спорта | `sport = cycling` |
| `road_cycling` | дисциплина | `cycling` + `road` |
| `mountain_biking` | дисциплина | `cycling` + `mtb` |
| `gravel` | дисциплина | `cycling` + `gravel` |
| `triathlon`, `duathlon`, `aquathlon` | форматы многоэтапного вида | `sport = multisport` + `triathlon` / `duathlon` / `aquathlon` |

**Рекомендация.** Дисциплина определяется парой «вид спорта + код», а не одним глобальным кодом. Тогда существующие значения `road`, `trail`, `cross`, `track`, `obstacle`, `other` остаются как есть и означают дисциплины бега, а `cycling` + `road` с ними не конфликтует. Данные не переписываются.

**Вопрос.** OCR — дисциплина бега или отдельный вид спорта? В задании OCR стоит в разделе «Бег», в анкете — отдельной строкой. Оставить дисциплиной бега дешевле: ничего не меняется.

**Вопрос.** Как пользователь видит многоэтапные старты: строкой «Триатлон» (понятно, но дуатлон и акватлон прячутся внутри) или «Мультиспорт» (точно, но слово незнакомое)?

### 5.2 Где хранить справочник

| | В коде (как `profileSports`, `typeLabels`) | В таблицах |
|---|---|---|
| Новый вид спорта | строка в справочнике и выкат | `INSERT` без выката |
| Названия и значки | там же | колонки или таблица переводов |
| Проверка значений | регулярное выражение в схеме + справочник в коде | внешний ключ |
| Временное отключение | поле «включён» в справочнике или переменная окружения | колонка |
| Согласованность с проектом | так сделаны типы, страны и виды спорта анкеты | расходится с `MVP.md` §2.3 |

**Рекомендация.** Справочник в коде, один на весь проект: код, название, значок, список дисциплин, признак «включён», единица показа дистанции, корзины. В схеме — проверка формата кода (как у `city_key`), а не закрытый список: новый вид спорта не требует миграции.

**Предположение.** Добавление вида спорта без выката не понадобится: каждый новый вид спорта всё равно приходит вместе с новым адаптером источника, то есть с выкатом.

**Рекомендация.** Локализацию не строить: интерфейс только русский. Названия лежат в справочнике рядом с кодом; когда появится второй язык, это одно место для замены.

### 5.3 Связь с кодами анкеты

| Код анкеты | Соответствие каталогу |
|---|---|
| `run` | `running` |
| `trail` | `running` + `trail` |
| `ocr` | `running` + `obstacle` |
| `bike` | `cycling` |
| `swim` | `swimming` |
| `tri` | `multisport` |
| `ski`, `row` | видов в каталоге пока нет |

**Рекомендация.** Коды анкеты не переименовывать: это заявленные интересы, они уже в базе и на них опирается Phase 10 (отбор получателей по виду спорта). Соответствие — таблицей в коде.

## 6. Варианты схемы PostgreSQL

Тексты ниже — наброски для обсуждения, не утверждённые миграции.

### 6.1 Минимальное расширение (шаг 1)

```sql
ALTER TABLE events ADD COLUMN sport TEXT NOT NULL DEFAULT 'running'
    CHECK (sport ~ '^[a-z_]{2,32}$');
-- event_type: закрытый список заменить проверкой формата, когда появится
-- первая небеговая дисциплина
```

- `source_events.fields` и `SourceEvent` получают необязательное поле `sport`; отсутствие читается как `running`.
- `listWhere` получает десятый параметр — список видов спорта.
- Индекс по виду спорта не нужен: при сотнях событий частичный индекс по дате достаточен.

Сложность: низкая. Обратная совместимость: полная. Не покрывает: О-3, О-4.

### 6.2 Нормализованная модель

```
sports(code, title, enabled)
disciplines(sport_code, code, title)
events(…, primary_sport)
event_races(id, event_id, sport, discipline, label, sort)
race_legs(race_id, seq, sport, distance_m, extra jsonb)
```

`event_distances` заменяется на `event_races` + `race_legs`. Сложность: высокая — затронуты `saveEventTx`, `Fold`, `listWhere`, фасеты, карточка, отмена слияния, поля записей, все эталоны разбора. Требуется перенос существующих дистанций. Покрывает всё.

### 6.3 Гибрид (рекомендуется)

Шаг 1 — как 6.1.

Шаг 2 — когда появится событие с дистанциями разных видов спорта:

```sql
ALTER TABLE event_distances ADD COLUMN sport TEXT NOT NULL DEFAULT 'running';
-- первичный ключ: (event_id, sport, distance_m)
```

Шаг 3 — когда подключается многоэтапный вид:

```sql
CREATE TABLE event_formats (
    event_id BIGINT NOT NULL REFERENCES events(id) ON DELETE CASCADE,
    code     TEXT NOT NULL,      -- sprint, olympic, half, full, custom
    label    TEXT,
    legs     JSONB NOT NULL,     -- [{"sport":"swimming","m":1500}, …] по порядку
    PRIMARY KEY (event_id, code)
);
```

Этапы лежат в JSON: по ним не фильтруют, их только показывают. Фильтр идёт по коду формата. Дистанции этапов в `event_distances` не пишутся — беговые корзины триатлон не находят.

### 6.4 Специфичные характеристики

| Характеристика | Где хранить | Когда |
|---|---|---|
| Бассейн или открытая вода | дисциплина (`pool`, `open_water`) | вместе с плаванием |
| Длина бассейна | не хранить | источники дают редко, фильтровать по ней не будут |
| Покрытие в велоспорте | дисциплина (`road`, `mtb`, `gravel`) | вместе с велоспортом |
| Набор высоты | не хранить, пока его не даёт подключённый источник; тогда — одна необязательная колонка у дистанции | по факту |
| Порядок и длины этапов | `event_formats.legs` | вместе с триатлоном |

**Рекомендация.** Не заводить колонки под характеристики, которых нет ни в одном подключённом источнике: колонка без данных — это фильтр, ведущий в пустую выдачу.

### 6.5 Сравнение

| | 6.1 Минимум | 6.2 Нормализация | 6.3 Гибрид |
|---|---|---|---|
| Плавание, велоспорт | да | да | да |
| Фестиваль | нет | да | с шага 2 |
| Триатлон | нет | да | с шага 3 |

| Риск для беговых событий | минимальный | высокий | минимальный |

## 7. Стратегия миграции

**Факт.** Все подключённые источники отдают только бег (§2.4). Значение по умолчанию `running` для существующих строк верно по построению, а не по догадке.

**Факт.** В PostgreSQL 17 добавление колонки с постоянным значением по умолчанию не переписывает таблицу.

Порядок шага 1:

1. Текст миграции показывается владельцу и утверждается до создания файла.
2. Миграция добавляет колонку; код, который её не знает, продолжает работать — откат выката без отката схемы возможен.
3. Новый код пишет и читает `sport`; пустое значение в `fields` и в `payload` означает `running`.
4. Проверка: содержимое `events` и `event_distances` до и после совпадает, кроме новой колонки; эталоны разбора и экранов не изменились; `content_hash` записей не изменился (иначе все записи будут считаться изменёнными).
5. Выкат — по отдельному разрешению, после резервной копии, как в `deploy/README.md`.

Что не трогается: `event_merges` и связанные таблицы (96 слияний), `dedup_candidates`, `users.filters`, `user_profiles`.

**Рекомендация.** На шаге 1 интерфейс не меняется вовсе. Это отделяет риск данных от риска экранов: эталоны остаются нетронутыми, и любое расхождение в тестах означает ошибку.

**Вопрос.** Что видит нынешний пользователь без выбранного вида спорта, когда в каталоге появятся заплывы: только бег (поведение не меняется, но новое надо найти) или всё (новое видно сразу, но «Найти забег» начнёт показывать не забеги)?

## 8. Влияние на нормализацию и дедупликацию

Настройки дедупликации в рамках исследования не менялись. Автослияние остаётся выключенным; всё ниже — предложения.

### 8.1 Нормализация

| Место | Что произойдёт | Предложение |
|---|---|---|
| `normalize.Type` | небеговые подписи станут `other` | подпись разбирать в паре с видом спорта; для бега — прежняя карта |
| `titleStopWords` | «заплыв», «триатлон», «велогонка» останутся в названии для сравнения | не менять (см. ниже) |
| `namedDistances` | «марафон» в названии веломарафона или заплыва даст 42 195 м | именованные дистанции применять только к бегу |
| дистанции из названия | «Велогонка 100» дистанции не даст, «Заплыв 5 км» даст | оставить; проверять на данных источника |

**Факт.** `title_norm` хранится в `events` и в `fields`. Комментарий к `simKey` (`internal/dedup/sim.go`): стоп-слова для сравнения добавляются там, а не в `TitleNorm`, чтобы не менять хранимое.

**Рекомендация.** Список `titleStopWords` не расширять: изменение `TitleNorm` меняет нормализованные поля всех записей, и первый прогон после выката покажет изменения по всему каталогу. Слова вида спорта при необходимости убирать в `simKey` — это не затрагивает базу.

### 8.2 Сложные случаи

| Случай | Что будет сейчас | Предлагаемое правило |
|---|---|---|
| Два старта разных видов спорта в один день в одном городе | пара попадёт в `/dupes`, если названия схожи не ниже 0,3 | разные виды спорта — отдельные события, пара не создаётся |
| Триатлон и забег одного фестиваля | то же; у общих названий схожесть высокая | то же правило; если одна сторона — многоэтапный вид, пара допустима только как кандидат, без признака `WouldAuto` |
| Несколько дистанций одного старта | одно событие, дистанции объединяются | без изменений |
| Серия с этапами | сворачивается по `GroupKey` внутри источника | без изменений |
| Один источник даёт триатлон одним событием, другой — тремя | три кандидата на одно событие; лимит `MaxPerEvent` = 3 | решает администратор; автоматически такие пары не сливать никогда |
| Одинаковые названия, разные дисциплины одного вида спорта | кандидат | оставить кандидатом: дисциплину источники путают, запрещать пару по ней нельзя |

### 8.3 Предлагаемые изменения правил

1. Пятое условие в `Decide`: вид спорта сторон совпадает. Не совпадает — `Separate` с причиной `sport`.
2. Исключение: одна из сторон — многоэтапный вид. Пара остаётся кандидатом, `WouldAuto` всегда `false`.
3. `WouldAuto` дополнительно требует равного вида спорта.
4. В `event.Fold` вид спорта берётся из первой записи по приоритету источников и не смешивается; дисциплина — как сейчас тип.
5. Перебор пар можно сузить до одного вида спорта — число сравнений не вырастет с ростом каталога.

**Предположение.** Пороги 0,7 и 0,3 откалиброваны на парах беговых событий (план 05-07, комментарий в `DefaultConfig`). Для других видов спорта они не проверены.

**Рекомендация.** Перед любым разговором об автослиянии для нового вида спорта — отдельная размеченная выборка пар этого вида, как делалось для бега.

**Вопрос.** Вносить правило «разные виды спорта — отдельные события» до первого небегового источника или после, когда будут реальные пары для проверки?

**Предположение.** Рост `parsed` у Tristyle после добавления видов спорта переведёт прогон в `suspect` (порог 5× медианы) — это ожидаемая остановка, а не поломка.

## 10. Концепция интерфейса в Telegram

### 10.1 Три варианта

| | A. Сначала выбор спорта | B. Общая лента | C. Лента по интересам |
|---|---|---|---|
| Путь нового пользователя | на шаг длиннее | как сейчас | как сейчас, если интересы заданы в анкете |
| Путь нынешнего бегуна | добавляется шаг в каждый поиск | не меняется, но в выдаче появляется чужое | не меняется |
| Пустая выдача | вероятнее: выбран вид спорта без событий в городе | маловероятна | средне |
| Дистанции и дисциплины | контекст известен, корзины свои | корзины не определены | зависят от числа выбранных видов |
| Новые экраны | выбор спорта, меню дисциплин | значок и строка спорта в карточке и списке | фильтр спорта, заполнение из анкеты |
| Зависимость от анкеты | нет | нет | да; анкету заполняют не все |

### 10.2 Критерии выбора

1. Нынешний сценарий поиска забега не становится длиннее.
2. Пользователь, не заполнявший анкету, получает рабочий поиск.
3. Фильтр не ведёт в пустую выдачу (принцип уже действует: кнопки городов и типов строятся по фактическим событиям).
4. Число новых и изменённых экранов.

По критериям 1 и 2 проигрывает A, по критерию 3 — A, по критерию 4 — C. Ни один вариант не выигрывает по всем четырём.

**Рекомендация.** Вид спорта — ещё один фильтр в существующей сводке, с множественным выбором и пунктом «Все виды»; механика общей ленты (B) с возможностью сузить. Заполнение из анкеты (элемент C) — отдельной явной кнопкой, не автоматически. Обязательного первого шага (A) нет. Это соответствует критериям 1–3 и требует меньше экранов, чем C целиком.

**Вопрос.** Какой из критериев владелец считает главным? От этого зависит, остаётся ли рекомендация в силе.

### 10.3 Главное меню

Состав кнопок сохраняется: поиск, настройки, профиль, поддержка. Меняется подпись первой: «Найти забег» перестаёт быть точной, когда в каталоге появится второй вид спорта.

### 10.4 Фильтры

| Фильтр | Предложение |
|---|---|

### 10.6 Сохранение бегового поиска

## 12. Аналитика

### 12.1 Три слоя

| Слой | Источник | Есть сейчас |
|---|---|---|
| Заявленные интересы | `user_profiles.sports` | да, `/stats` |
| Фактическое поведение | действия в боте | нет |
| Агрегаты | счётчики без идентификаторов | только по анкете |

### 12.2 Метрики и что для них нужно

| Метрика | Нужные данные | Идентификатор пользователя |
|---|---|---|
| Пользователи по видам спорта (интерес) | анкета | не нужен, уже есть |
| Пересечение интересов | анкета, пары видов | не нужен; при малых группах — тот же порог «меньше 5» |
| Поиски по видам спорта | счётчик показов списка по дню и виду | не нужен |
| Популярные дисциплины | тот же счётчик с дисциплиной | не нужен |
| Города с высоким спросом | тот же счётчик со страной и городом | не нужен |
| Поиски без результатов | счётчик показов экрана «ничего не нашлось» | не нужен |
| Открытия карточек | счётчик по дню и виду | не нужен |
| Конверсия «выбор спорта → поиск» | два счётчика | не нужен, если считать события, а не людей |
| Переходы к регистрации | кнопка регистрации — ссылка, Telegram о нажатии не сообщает | недоступно без собственного адреса-перенаправления |
| Удержание по направлениям | даты активности каждого пользователя | нужен |

### 12.3 Предложение

Одна таблица суточных счётчиков без идентификаторов пользователей:

```
usage_daily(day, kind, sport, discipline, country_code, city_key, n)
```

Она закрывает все метрики, кроме удержания и переходов к регистрации.

**Рекомендация.** Удержание и переходы к регистрации сейчас не делать. Первое требует хранить историю действий по пользователям, второе — собственного веб-адреса, которого в инфраструктуре нет (`MVP.md`: без webhook и обратного прокси). Заменитель перехода к регистрации — открытие карточки.

**Факт.** `PROJECT.md` перечисляет, что хранится о пользователях. Счётчики без идентификаторов этот перечень не расширяют; история действий по пользователям — расширила бы.

**Вопрос.** Достаточно ли счётчиков без пользователей, или удержание нужно настолько, что владелец готов хранить даты активности по пользователям?

**Предположение.** При двух пользователях любая метрика пока равна шуму. Счётчики имеет смысл включить заранее, чтобы данные накопились к моменту выбора второго вида спорта.

### Выбор первого нового вида спорта

| Критерий | Плавание (открытая вода) | Велоспорт | Триатлон |

| Сложность модели | низкая | низкая | высокая (шаг 3 схемы) |

## 14. Риски и альтернативы

| Риск | Чем грозит | Как снижается |
|---|---|---|
| Чрезмерная универсализация | модель из пяти таблиц ради одного вида спорта; беговое событие усложняется без пользы | шаги схемы только по факту появления источника (§6.3) |
| Усложнение дедупликации | шум в `/dupes`, рост числа сравнений | условие равенства вида спорта; перебор внутри вида; автослияние выключено |
| Снижение качества данных | небеговые источники хуже структурированы; пустые дистанции | вид спорта выключен до приёмки; пороги оценки прогона уже действуют по источнику |
| Рост нагрузки на источники | больше запросов к тем же сайтам | задержка между запросами уже в `Policy`; один запрос списка на вид спорта |
| Стоимость поддержки | `MVP.md` §13: «операционная нагрузка — главный ресурс»; каждый адаптер ломается при смене вёрстки | один новый источник за раз; не подключать источник ради десятка событий |
| Усложнение интерфейса | лишний шаг для бегуна; фильтры, ведущие в пустоту | вид спорта — необязательный фильтр; меню только по фактическим событиям |
| Смешение спорта и дисциплины | несопоставимые фильтры и статистика | пара «вид спорта + дисциплина»; соответствие кодов анкеты таблицей |
| Миграционный риск | порча каталога, 96 слияний | шаг 1 не переписывает строки; проверка «до и после»; резервная копия перед выкатом |
| Влияние на беговые события | изменение `title_norm`, `content_hash`, эталонов | новые поля — в конец с `omitempty`; стоп-слова не трогать; интерфейс на шаге 1 не менять |
| Преждевременное расширение | Phase 6 не закрыта, пользователей двое, спрос не измерен | этап B первым; счётчики до выбора вида спорта |

### Альтернативы целиком

| Альтернатива | За | Против |
|---|---|---|
| Отдельный бот на каждый вид спорта | беговой бот не трогается | прямо исключено заданием; тройная поддержка; анкета и аудитория не общие |
| Только расширить `event_type` значениями `swim`, `bike`, `tri` | одна строка в схеме | закрепляет смешение спорта и дисциплины; дисциплины плавания и велоспорта выразить негде |
| Не расширяться, пока не выросла аудитория бега | ноль риска и работы | не проверяет гипотезу о спросе на другие виды |
| Гибрид по шагам (рекомендуется) | первый шаг дешёвый и обратимый | триатлон откладывается |
