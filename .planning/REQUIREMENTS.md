# Requirements: Telegram-бот — агрегатор забегов

**Defined:** 2026-09-25
**Core Value:** Полный, актуальный и без дублей каталог забегов
**Source of truth:** `MVP.md` (при расхождении прав он)

## v1 Requirements

Требования первого релиза (MVP). Каждое отображено на одну фазу роадмапа.

### Discovery (источники и аудит VPS)

- [x] **DISC-01**: Для каждого из 2–3 кандидатов в источники выполнена проверка **с VPS**: доступность, `robots.txt`, ToS, API, JSON и JSON-LD, sitemap и RSS, HTML, допустимые rate limits, антибот-защита, реальные поля, способ получения списка событий, наличие стабильного `external_id`, ссылки на регистрацию (команды выполняет владелец, см. DISC-03)
- [x] **DISC-02**: Утверждён набор из 2–3 источников; неудобный или недоступный кандидат заменён другим; обход CAPTCHA и антибот-защиты не проектируется
- [x] **DISC-03**: Аудит VPS выполнен только чтением и записан без секретов: назначение, `Listen`/`Allow` и `ufw` у `tinyproxy`; синхронизация часов; состояние Docker и Compose; swap; открытые порты. Никаких изменений на VPS. Read-only блоки запускаются через обёртку с отдельным ключом проекта после утверждения владельцем (`MVP.md` §7.4): инструменты готовят команды только на чтение, запускают утверждённые блоки и анализируют вывод
- [x] **DISC-04**: Итоговый отчёт содержит для каждого источника способ получения данных, наличие `external_id`, частоту обновления, число запросов на цикл и ограничения, признак «содержит только российские соревнования» (основание для предварительного статуса кандидата на fallback `country_code = RU`; окончательное подтверждение — санити-проверка в Phase 3), а также перечень решений для Phase 3

### Foundation (основа)

- [x] **FND-01**: Go-модуль (Go 1.27.1) с одним бинарником и подкомандами `bot`, `worker`, `migrate`, `healthcheck`
- [x] **FND-02**: Схема PostgreSQL 17 из `MVP.md` (раздел 4) применяется миграциями `goose`, встроенными в бинарник; созданы все таблицы и индексы MVP
- [x] **FND-03**: Доменные типы `event` и слой `store` на `pgx/v5` + `pgxpool`; весь SQL находится только в `internal/store`
- [x] **FND-04**: Пакет `normalize`: `title_norm`, `city_key` (ASCII-slug, словарь синонимов), даты, время и часовой пояс (IANA), дистанции в метрах, отображение типа забега; `country_code` (ISO 3166-1 alpha-2; «Россия» и «Russia» → `RU`), `region` и `city` канонического события; `description` обрезается до 1000 символов по границе слова
- [x] **FND-05**: Тестовая инфраструктура с реальной PostgreSQL 17: юнит-тесты `normalize` и интеграционный тест upsert
- [x] **FND-06**: Конфигурация через переменные окружения; секреты не попадают в репозиторий (`.env` вне репозитория и в `.gitignore`)

### Ingestion (сбор данных)

- [x] **ING-01**: `Fetch` с таймаутами, повторами (3 попытки, экспоненциальный backoff с jitter, `Retry-After`), лимитом размера ответа, rate limit на хост и `User-Agent` с контактом; значения конфигурируемы
- [x] **ING-02**: `Parse` — чистая функция без сети; для каждого источника есть фикстуры в `testdata/` и golden-тесты
- [x] **ING-03**: `Validate` отклоняет записи без обязательных полей или с датой вне `[сегодня−1 день, сегодня+3 года]`; отклонённые считаются
- [x] **ING-04**: Upsert `source_events` идемпотентен по `(source_id, external_id)`; сохраняются `payload`, `content_hash`, `first_seen_at`, `last_seen_at`; неизменённая запись обновляет только `last_seen_at`
- [x] **ING-05**: Создание канонического `events` и `event_distances` из `source_events`; поля выбираются по приоритету источника; `updated_at` меняется только при изменении канонических полей
- [x] **ING-06**: Каждый запуск источника записывается в `ingest_runs` со статусом и счётчиками `fetched`, `parsed`, `rejected`, `out_of_scope`, `upserted`, `error`
- [x] **ING-07**: Статус прогона `ok`/`suspect`/`failed` определяется автоматически (медиана последних 7 прогонов `ok`, доля отклонённых, даты вне диапазона, доля NULL); **прогоны `suspect` и `failed` ничего не применяют**; пороги конфигурируемы; есть ручное принятие нового базового уровня
- [x] **ING-08**: Состояние наблюдения `source_events` (`active`/`missing`/`gone`) меняется только по здоровым прогонам и только для записей с `start_date ≥ сегодня`; `gone` влияет только на `events.is_listed`, **никогда не меняет `events.status`**; записи не удаляются
- [x] **ING-09**: Планировщик запускает каждый источник раз в 6 часов со случайным сдвигом и общим таймаутом прогона, корректно останавливается по сигналу
- [x] **ING-10**: Сырые ответы сохраняются на диск вне PostgreSQL с ограничением количества и TTL
- [x] **ING-11**: `country_code` определяется так: явная страна источника (нормализованная); иначе fallback `RU` только для источника, который Phase 1 предварительно признала кандидатом (одни российские соревнования по структуре источника), после санити-проверки на реальных данных в Phase 3, окончательно подтверждающей это; запись с явно иной страной сохраняется в `source_events` с `match_state = out_of_scope` и события не создаёт; при неопределённой стране без подтверждённого источника молчаливого fallback нет
- [x] **ING-12**: Добавление нового источника не требует изменения общего интерфейса ingestion и основной архитектуры pipeline; источник подключается через предусмотренный source adapter/parser contract (source-specific код добавлять разрешено); второй и (если утверждён) третий источники подключены
- [x] **ING-13**: Описание события в БД не длиннее 1000 символов, изображения не скачиваются и не сохраняются (в схеме нет полей и файлов изображений); проверяется тестом на фикстуре с длинным описанием

### Bot (Telegram-поиск)

- [x] **BOT-01**: Бот на long polling (`go-telegram/bot`) отвечает на `/start` и открывает сценарий «Найти забег»
- [x] **BOT-02**: Пользователь фильтрует по дате (пресеты и месяц), городу (кнопки топ-10 из БД и текстовый ввод), дистанции (корзины) и типу; по умолчанию — будущие даты по всей России; регион в SQL есть, в интерфейсе нет
- [x] **BOT-03**: Состояние фильтров хранится в `users.filters` с версией `filters_v`; устаревший callback обрабатывается понятным сообщением
- [x] **BOT-04**: Список с пагинацией `LIMIT/OFFSET` по стабильному порядку `start_date, id`; листание через `editMessageText`; `callback_data` до 64 байт; роутинг по префиксу; на каждый callback есть `answerCallbackQuery`
- [x] **BOT-05**: Карточка события: название, даты и время, город и адрес, тип, дистанции, короткое описание (до 1000 символов), кнопка регистрации, названия источников со ссылками
- [x] **BOT-06**: В выдаче только события с `is_listed` и без `merged_into_id`; события со статусом `cancelled` и `postponed` **не скрываются** и показываются явно с пометкой `[ОТМЕНЁН]` или `[ПЕРЕНЕСЁН]` в списке и в карточке
- [x] **BOT-07**: Админ-команда `/runs` (последние прогоны по источникам) доступна только `ADMIN_TG_IDS`
- [x] **BOT-08**: О пользователях хранятся Telegram ID, настройки поиска и ответы добровольной анкеты: пол, возрастная группа, страна и город проживания, виды спорта. Для поддержки хранятся связка «сообщение бота в группе поддержки → Telegram ID автора» с временем и отметка ожидания обращения (Telegram ID и время). Текст обращений и ответов, username, имя, телефон и другие данные из Telegram в базе не сохраняются; имя и username автора бот показывает в сообщении в группе поддержки.
- [x] **BOT-09**: Ошибки Telegram API (блокировка бота, `TooManyRequests`, «message is not modified») обрабатываются без падения

### Deduplication (дедупликация)

- [x] **DDP-01**: Кандидаты для сопоставления выбираются по стране и пересечению диапазонов дат
- [x] **DDP-02**: Схожесть названий считается в Go (без `pg_trgm`); схема оценки и пороги **конфигурируемы**; значения 0,7 / 0,4 — исходная стартовая гипотеза; по калибровке 05-07 пороги по умолчанию High = 0,7, Low = 0,3 (при 0,4 терялись пары `c33`–`c35`)
- [x] **DDP-03**: Высокая уверенность → автоматическая связь; средняя → отдельное событие плюс запись в `dedup_candidates`; низкая → отдельное событие. Примечание (D-25 Phase 5): алгоритм и калибровка реализованы, автослияние в production выключено (`DEDUP_AUTO_MERGE=false`); это не разрешение на включение
- [x] **DDP-04**: Совпадение хоста и пути регистрации используется только как дополнительный сигнал и не является самостоятельным основанием для автоматического слияния
- [x] **DDP-05**: Записи одного источника автоматически не склеиваются, если парсер не задал `group_key`; дистанция не участвует в идентичности события
- [x] **DDP-06**: При слиянии `source_events` не удаляются, их `event_id` переключается на победителя, проигравшее событие получает `merged_into_id` и скрывается; цепочки слияний схлопываются до корня
- [x] **DDP-07**: `/dupes` (только `ADMIN_TG_IDS`) показывает потенциальные дубли и позволяет подтвердить или отклонить; отклонённая пара повторно не предлагается
- [x] **DDP-08**: Администратору приходит ежедневная сводка по ожидающим кандидатам вместо уведомления на каждую запись
- [x] **DDP-09**: Пороги и схема оценки откалиброваны на размеченном наборе реальных пар (порядка 30–50); автоматическое слияние на нём не даёт ложных слияний
- [x] **DDP-10**: Дистанции слитого события — объединение дистанций связанных `source_events` с допуском по метрам

Phase 7 (приняты владельцем 2026-10-03, не выполнены; основание — D-21, D-26 в 05-CONTEXT.md; решения — 07-CONTEXT.md):

- [x] **DDP-11**: Потенциальные автослияния вычисляются независимо от `DEDUP_AUTO_MERGE`; при выключенном флаге фактических автоматических слияний 0, расчёт не меняет данные каталога
- [x] **DDP-12**: Потенциальные автослияния видны администратору в `/dupes`, в логе прохода дедупликации и в `agg verify`
- [x] **DDP-13**: Тест калибровки падает, если пара с вердиктом AUTO не имеет подтверждённой метки; в наборе есть размеченные пары третьего источника и Беларуси либо документально подтверждено отсутствие пересечений в проверенном наборе
- [x] **DDP-14**: Процедура отмены слияния описана и проверена на тестовой базе
- [x] **DDP-15**: По каждому замечанию L1–L5 ревью Phase 5 есть результат: воспроизведение и доказательства, затем исправление с тестом либо решение владельца

### Profile (анкета и профиль)

Приняты 2026-10-04 (Phase 9, Pending; источник — 09-CONTEXT.md, решения владельца D-01…D-16; добровольная анкета из четырёх вопросов и профиль `/profile`):

- [x] **PRF-01**: Анкета предлагается один раз на `/start`. Критерий: второй `/start` при любом статусе — главное меню; одна строка профиля на пользователя
- [x] **PRF-02**: Можно пропустить всю анкету и любой вопрос. Критерий: «Пропустить» — меню и `skipped`; «Пропустить вопрос» не пишет в БД
- [x] **PRF-03**: Отказ ничего не ограничивает. Критерий: при `skipped`, `not_started`, `in_progress` сценарии S-01…S-17 проходят; отличия — только экран первого `/start` и кнопка профиля в меню
- [x] **PRF-04**: Пол `m` / `f`, шесть возрастных групп, восемь видов спорта. Критерий: экраны и хранимые значения соответствуют D-04; иное значение кодек отвергает
- [x] **PRF-05**: Любой ответ можно изменить через `/profile`. Критерий: для каждого из четырёх полей изменение сохраняется, растёт `profile_v`
- [x] **PRF-06**: Профиль независим от настроек поиска. Критерий: действия с профилем не меняют строку `users`; действия с фильтрами не меняют строку `user_profiles`
- [x] **PRF-07**: Устаревшие кнопки `u:` не меняют данные. Критерий: изменяющая — уведомление без записи; навигационная — экран по текущему состоянию
- [x] **PRF-08**: Город текстом не попадает в поиск. Критерий: при отметке ожидания текст сохраняется как город проживания, фильтр города не меняется; после её истечения текст идёт в поиск
- [x] **PRF-09**: Ответы не попадают в логи и свободным текстом в `callback_data`. Критерий: проверка логов в тестах
- [x] **PRF-10**: Контракт и эталоны утверждены владельцем до кода. Критерий: отметка в документах фазы

### Support (поддержка)

Приняты 2026-10-06 (Phase 11, Pending; источник — 11-CONTEXT.md, решения владельца D-01…D-22; поддержка через бота: обращение уходит в закрытую группу, ответ участника группы бот доставляет пользователю):

- [x] **SUP-01**: Контракт экранов поддержки, требования SUP и формулировки о хранимых данных утверждены владельцем до изменения кода и эталонов. Критерий: строка `CONTRACT APPROVED:` в документах фазы
- [x] **SUP-02**: Поддержка включается идентификатором группы в конфигурации; без него кнопки и команды нет, остальной бот работает как раньше. Критерий: при пустой `SUPPORT_CHAT_ID` главное меню — три кнопки, `/support` отвечает как неизвестная команда, прежние эталоны не меняются; неверное значение — ошибка старта без повтора значения
- [x] **SUP-03**: Два входа — кнопка «💬 Поддержка» и `/support`; приглашение с «Отмена»; следующее сообщение в течение 10 минут — обращение; одно сообщение — одно обращение. Критерий: после отправки режим выключен, следующий текст идёт в поиск
- [x] **SUP-04**: Режим снимают «Отмена», `/start` и истечение 10 минут; режимы «жду город» и «жду обращение» не действуют одновременно. Критерий: после снятия текст идёт в поиск; вход в один режим снимает другой; отметка перепроверяется под блокировкой строки
- [x] **SUP-05**: Принимается только текст до 2000 символов; остальное отклоняется: фото, видео, файлы, голосовые, стикеры и альбомы в режиме ввода получают короткий отказ. Критерий: отклонённое сообщение в группу не попадает; вне режима ввода нетекстовые сообщения бот не замечает, как раньше
- [x] **SUP-06**: Лимит — 5 обращений в час от одного пользователя, считается по связкам. Критерий: шестое обращение за час получает отказ и не пересылается; через час отправка снова возможна
- [x] **SUP-07**: Обращение приходит в группу поддержки одним сообщением бота, из которого видно, от кого оно; пользователь получает подтверждение. Критерий: одно обращение — одно сообщение в группе и одна связка; подтверждение говорит, что ответ придёт в этот чат, и не обещает срок
- [x] **SUP-08**: В группе бот реагирует только на ответ (reply) на своё сообщение с обращением; ответить может любой участник; остальные сообщения, команды, кнопки и поиск в группе не работают. Критерий: обычное сообщение, команда и кнопка в группе не вызывают ни ответа, ни записи; чужая группа игнорируется
- [x] **SUP-09**: Ответ доставляется пользователю текстом от имени бота с кнопкой «Ответить»; кто ответил, пользователь не видит; нетекстовый ответ не доставляется; кнопка включает тот же режим ввода. Критерий: в сообщении пользователю только текст ответа и кнопка; после «Ответить» следующее сообщение — новое обращение; режима «чат» нет
- [x] **SUP-10**: Недоставленный ответ молча не теряется. Критерий: при ошибке доставки и при нетекстовом ответе бот отвечает в группе на сообщение отвечавшего
- [x] **SUP-11**: В базе — только связка «сообщение бота в группе → Telegram ID автора» с временем и служебная отметка ожидания; текст обращения и ответа не хранится и в логи не пишется. Критерий: проверка таблиц и логов в тестах
- [x] **SUP-12**: Экраны поддержки ничего не говорят о данных пользователя и о том, кто и как прочитает сообщение; документы описывают хранимое как факт. Критерий: тексты контракта и эталоны S-26…S-35; BOT-08, `PROJECT.md`, `MVP.md`
- [x] **SUP-13**: Эталоны приняты владельцем локально, production-приёмка пройдена в Telegram; выкат, миграция, переменная в `.env` и создание группы — по отдельным разрешениям владельца. Критерий: отметки в документах фазы

## Out of Scope

Явные исключения, чтобы не возвращаться к ним без причины.

| Feature | Reason |
|---------|--------|
| Redis, Kafka, Elasticsearch, OpenSearch, PostGIS, Kubernetes | Преждевременная инфраструктура; PostgreSQL достаточно |
| Микросервисы | Один бинарник и один VPS достаточны |
| ML-сопоставление, эмбеддинги | Ручная очередь достаточна на масштабе MVP |
| Веб-админка | Хватает `/dupes` и `/runs` в боте |
| Автоматическая регистрация на забег | Вне ядра ценности, юридические риски |
| Копирование изображений и больших текстов | Авторские права; описание не длиннее 1000 символов |
| Сбор данных участников | Персональные данные; объект — только публичная информация о соревнованиях |
| Обход CAPTCHA и антибот-защиты | Недопустимо; источник с такой защитой заменяется |
| Слой `usecase` | Тонкий проброс без логики |
| Webhook и reverse proxy | Достаточно long polling |
| Использование `tinyproxy` для запросов к источникам | Не входит в архитектуру проекта |
