### DDP-11: потенциальные автослияния без миграции

- **D-05 (would_auto, без миграции БД):** `would_auto` вычисляется **в памяти прохода** `dedup.Pass` — теми же правилами, что ветка автослияния `Decide` (NameSim не ниже `High` без бонуса ссылки, пересечение дат, равный непустой `CityKey`, `UniquePartner`), но **независимо от `c.AutoMerge`**. Новых таблиц, колонок и миграций нет.
- **D-06 (одна точка правды):** `Decide` вычисляет признак `Reasons.WouldAuto` при любом `c.AutoMerge`; вердикт `AutoMerge` по-прежнему только при `c.AutoMerge && WouldAuto`. Отдельной «теневой» копии правил нет — расхождение критериев признака и реального автослияния невозможно по построению.
- **D-07 (как признак доходит до /dupes и agg verify) — согласовано владельцем 2026-10-03:** `/dupes` (процесс `bot`) и `agg verify` (SQL на VPS) не видят памяти прохода (процесс `worker`). Предлагается: признак `would_auto` пишется в **уже существующее** поле JSON `dedup_candidates.reasons` той же записью `UpsertCandidate`, что и сегодня (схема не меняется, данные каталога — `events`, `source_events`, `event_distances` — не меняются). Альтернатива «только память и лог» не выполняет DDP-12 в части `/dupes`. Старые reasons без ключа читаются как false; pending-кандидаты получают актуальный признак первым же проходом (Pass перезаписывает reasons всех оставшихся pending и удаляет остальные).
- **D-08 (видимость, DDP-12):** лог прохода `dedup pass` получает поле `would_auto=<n>`; карточка кандидата в `/dupes` — строку о том, что автослияние слило бы эту пару; `agg verify` — счётчик pending-кандидатов с `reasons->>'would_auto' = 'true'` (07-05).
- **D-09 (лимит MaxPerEvent) — решение владельца 2026-10-03:** лимит `MaxPerEvent` сохраняется; скрытые из выдачи потенциальные AUTO-пары считаются отдельно. Счётчики прохода: `would_auto` — пары прохода с признаком (пары, пропущенные как отклонённые по корням, не оцениваются и не входят); `would_auto_shown` — записаны или обновлены кандидатом; `would_auto_hidden` — пропущены лимитом; `would_auto_decided` — `UpsertCandidate` вернул 0 (пара уже решена); при включённом флаге ещё `would_auto_merged`, `would_auto_deferred`. Инвариант: `would_auto = shown + hidden + decided + merged + deferred`.

### Гарантия нуля фактических слияний при DEDUP_AUTO_MERGE=false

- **D-10:** Гарантия многослойная, каждый слой проверяется тестом:
  1. **Код:** вызов `MergeEvents(..., "auto", ...)` есть только в ветке `if c.AutoMerge` в `pass.go`; `Decide` возвращает вердикт `AutoMerge` только при `c.AutoMerge`. Признак `WouldAuto` не участвует ни в одном условии слияния.
  2. **Unit-тест `Decide`:** для каждой пары табличных тестов и калибровочного набора при `AutoMerge=false` вердикт никогда не `AutoMerge`, а `WouldAuto` совпадает с вердиктом при `AutoMerge=true`.
  3. **Интеграционный тест `Pass` (PostgreSQL 17):** каталог с заведомыми парами `would_auto` при `AutoMerge=false` — снимок `events` (все колонки), `source_events` (`event_id`, `match_state`, `fields`), `event_distances` до и после прохода побайтно равен; `merged_into_id IS NOT NULL` — 0; ни у одного события нет записей двух источников (`match_state = 'auto'` — не признак слияния: так ingest помечает привязку записи к своему событию); `would_auto` в логе и в `reasons` равен ожидаемому числу. Второй проход идемпотентен.
  4. **Статическая проверка в тестах:** число вызовов `MergeEvents` с `"auto"` в непроверочном коде — ровно один, внутри ветки `c.AutoMerge` (grep-проверка в тесте пакета).
  5. **Конфигурация:** тест `DefaultConfig().AutoMerge == false` и `LoadConfig` без переменной — `false` (есть, сохраняется); `dedup_auto_merge=false` в строке `started` логов `bot` и `worker` (есть).
  6. **Production (только после выката, вне этой фазы):** `agg verify` — `events_merged` не растёт без ручных решений, `dedup_auto_merge_*=false`, счётчик `would_auto` виден.

### DDP-13: калибровка

- **D-11 (M2):** перебор пар окна выносится в одну функцию пакета `dedup` над `[]Side` (окно, страна, порядок, `UniquePartner`); её вызывают `Pass` и `TestCalibration`. Дублирование `windowPairs`/`countPartners` в тесте удаляется.
- **D-12:** `TestCalibration` падает, если в окне фикстур есть пара с `WouldAuto`, не размеченная в `calibration.json` подтверждённой меткой (`proposed=false`).
- **D-13 («Лига Героев» и Беларусь) — участие владельца** (факт 2026-10-03: BY-события в фикстурах есть только у ПроБЕГа — 10 строк `country_code: BY` в `prepared.golden.json`; у Марафонца и в фикстуре heroleague — нет): фикстура `internal/ingest/sources/heroleague/testdata/event_list.json` подключается к калибровке; исполнитель готовит пары с предложенной меткой (`proposed=true`), владелец проверяет. События Беларуси: пары размечаются, если в фикстурах есть пересечения; иначе отсутствие пересечений фиксируется в README калибровки с методом проверки (DDP-13 допускает оба исхода). Пороги не меняются без отдельного решения.

### DDP-14: отмена слияния

- **D-14 (исследование до процедуры) — решение владельца 2026-10-03: b+c** (служебная отмена в Go + журнал слияний, миграция `00005`; реализация и проверка только локально, production не читается и не меняется; см. 07-UNMERGE.md): слияние (`MergeEvents`) переносит `source_events.event_id` проигравшего на победителя и пересобирает поля победителя свёрткой `event.Fold` (Go); журнала слияний нет. Поэтому чистым SQL точно отменить можно не каждое слияние: для проигравшего с одной записью источника её id есть в кандидате (`dedup_candidates.source_event_id`), для цепочек и автослияний исходная принадлежность записей не сохраняется, а поля победителя после отката нужно пересвернуть. План 07-04 начинается с инвентаризации (что восстановимо по данным, что нет) и вариантов для владельца:
  - а) рунбук только для восстановимого случая (ручное слияние через кандидата, проигравший с одной записью) + пересвёртка полей существующим кодом записи события;
  - б) служебная подкоманда отмены в Go с тестом (выкат — вместе с фазой);
  - в) журнал слияний (миграция `00005`) — точная отмена будущих слияний; противоречит духу «без миграции» только для DDP-11, решение отдельное.
  Процедура проверяется на тестовой базе (DDP-14); на production не выполняется.

### DDP-15: замечания L1–L5

- **D-15:** порядок для каждого: сначала воспроизведение (падающий тест или документированный сценарий), затем исправление с тестом либо решение владельца. Риск не принимается без владельца (в том числе L1).
  - **L1** — «Да, слить» пересчитывает корни: подтверждение должно сливать ровно показанные администратору корни (или отказывать, если корень изменился).
  - **L2** — `MarkCandidatesNotified` отмечает кандидатов, созданных после подсчёта сводки: отметка только вошедших в сводку.
  - **L3** — ошибка `Pass` откатывает весь проход, след только `WARN post-apply failed`, общий контекст 5 минут: счётчик ошибок прохода (D-21 Phase 5) и отдельный тайм-аут; поведение «каталог прогона уже записан» сохраняется.
  - **L4** — `GroupKey` серии ПроБЕГа без места: исправление меняет ключи и даст разовый всплеск `changed` после выката — **открыто, решение владельца в 07-03 (задача 3)** до исправления.
  - **L5** — при слиянии `match_state = manual` перезаписывается в `auto`, берётся статус победителя: исправление с тестом; статус — проверить, нужен ли выбор (источники статус не выставляют).
