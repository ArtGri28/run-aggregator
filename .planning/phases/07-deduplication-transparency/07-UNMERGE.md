## Что меняет слияние (по коду `internal/store/dedup.go`, `MergeEvents`)

| Шаг | Что происходит | Что остаётся для отмены |
|---|---|---|
| Перенос записей | `UPDATE source_events SET event_id = <победитель>, match_state = …` для всех записей проигравшего; список перенесённых id (`RETURNING id`) нигде не сохраняется | **исходная принадлежность записей не хранится** |
| Проигравший | `merged_into_id = <победитель>`, `is_listed = false`; поля, дистанции и `created_at` проигравшего не меняются | событие проигравшего целиком, «замороженное» на момент слияния |
| Цепочка | события, слитые раньше в проигравшего, перевешиваются на победителя (`merged_into_id` в один шаг) | **кто в кого сливался раньше — не хранится** |
| Победитель | поля пересобираются `event.Fold` по всем записям (Go), `is_listed` пересчитывается | исходные поля победителя не хранятся; их можно пересобрать тем же `Fold` по его записям |
| Кандидаты | кандидат пары — `confirmed` с `decided_by`/`decided_at`; прочие pending с участием проигравшего удаляются | у ручного слияния через `/dupes` остаётся `dedup_candidates.source_event_id` |

Записи источников после слияния продолжают обновляться прогонами (их `fields` меняются вместе с источником), а событие проигравшего — нет.

## Следы, по которым связь восстановима

1. **Кандидат `/dupes`.** `Pass` создаёт кандидата `(source_event_id = первая запись стороны с бо́льшим id, event_id = сторона с меньшим id)`, а `ConfirmCandidate` сливает бо́льший корень в меньший. Значит, у ручного слияния `dedup_candidates.source_event_id` — **первая запись проигравшего** (корни сторон между экраном и подтверждением не меняются — 07-03, L1).
2. **Одна транзакция прогона.** Прогон пишет запись и создаёт её событие в одной транзакции (`Runner.apply` → `UpsertSourceEvent`, `SaveEventFor`); `now()` в PostgreSQL — время начала транзакции, поэтому `events.created_at` события = `source_events.first_seen_at` записи, которая его создала. В одном прогоне это время общее у всех новых записей — однозначность даёт сочетание с названием и датой.
3. **Поля записи.** `source_events.fields` записи и колонки события, созданного из неё одной (`title_norm`, `start_date`), совпадают, пока источник не изменил запись.

## Классы

| Класс | Признак в данных | Что можно восстановить |
|---|---|---|
| **Класс A** | слито вручную через `/dupes` (подтверждённый кандидат с `decided_by`); проигравший найден **однозначно** по записи кандидата (п. 1–3: `created_at = first_seen_at`, равные `title_norm` и `start_date`), и запись сопоставлена только ему; проигравший сам ни разу не был победителем (нет подтверждённых кандидатов с его `event_id`) — то есть у него была ровно одна запись | точно: вернуть запись проигравшему, снять `merged_into_id`, пересобрать поля обоих событий существующим кодом записи события, пересчитать `is_listed` |
| **Класс B** | связь с кандидатом есть, но проигравший раньше поглощал другие события (цепочка) или сопоставление неоднозначно | не точно: какие ещё записи были у проигравшего, по данным не установить; дерево можно было бы собрать рекурсивно по кандидатам, но это не проверяемо без журнала |
| **Класс C** | связи с подтверждённым ручным кандидатом нет: автослияние (`MergeEvents` с `auto`, без кандидата), прямой вызов `MergeEvents`, либо запись источника изменилась так, что п. 2–3 не сходятся | нет: исходная принадлежность записей неизвестна |

Допущение классов: автослияний на production не было (`DEDUP_AUTO_MERGE=false` с Phase 5); иначе поглощения без кандидатов могли бы скрыть класс B за классом A.

## Запрос инвентаризации (только чтение)

Каждое слитое событие (`merged_into_id IS NOT NULL`) — класс A, B или C. Запрос ничего не меняет: только `SELECT`. Этот же текст выполняет тест `TestUnmergeInventory` (`internal/store/unmerge_test.go`), читая его из этого файла.

```sql
WITH manual AS (
    SELECT dc.id AS cid, dc.source_event_id AS r, dc.event_id AS w
    FROM dedup_candidates dc
    WHERE dc.state = 'confirmed' AND dc.decided_by IS NOT NULL
),
link AS (
    SELECT m.id AS l, manual.cid, manual.r
    FROM events m
    JOIN source_events se ON se.first_seen_at = m.created_at
    JOIN manual ON manual.r = se.id
    WHERE m.merged_into_id IS NOT NULL
      AND se.fields->>'title_norm' = m.title_norm
      AND se.fields->>'start_date' = to_char(m.start_date, 'YYYY-MM-DD')
)
SELECT m.id AS event_id,
       m.merged_into_id AS root_id,
       CASE
           WHEN NOT EXISTS (SELECT 1 FROM link WHERE link.l = m.id) THEN 'C'
           WHEN (SELECT count(*) FROM link WHERE link.l = m.id) = 1
                AND (SELECT count(*) FROM link x WHERE x.r = (SELECT r FROM link WHERE link.l = m.id)) = 1
                AND NOT EXISTS (SELECT 1 FROM manual WHERE manual.w = m.id) THEN 'A'
           ELSE 'B'
       END AS class,
       (SELECT min(r) FROM link WHERE link.l = m.id) AS record_id
FROM events m
WHERE m.merged_into_id IS NOT NULL
ORDER BY m.id;
```

## Реализация (задача 3, локально)

- **Журнал (c):** миграция `migrations/00005_merge_log.sql` — `event_merges` (победитель, проигравший, способ, кто, когда, `undone_at`/`undone_by`), `event_merge_records` (перенесённые записи и их `match_state` до слияния), `event_merge_chain` (события, перевешенные с проигравшего). `MergeEvents` пишет журнал в той же транзакции. Прошлые слияния журнала не имеют.
- **Отмена (b):** `store.UndoMerge(ctx, loserID, adminID, fold, apply)` — одна транзакция под `LockDedup`:
  - есть действующая запись журнала — отмена по журналу: записи возвращаются с прежним `match_state` (`out_of_scope`, выставленный после слияния, сохраняется), события цепочки — под проигравшего; отказ, если те же записи перенесло более позднее действующее слияние (отменять с последнего) или записи уже не у текущего корня;
  - журнала нет — только класс A по запросу инвентаризации (`inventoryQuery` в `internal/store/unmerge.go` — тот же текст, что выше); B и C — отказ `ErrNotUndoable` без изменений;
  - затем у проигравшего снимается `merged_into_id`, поля проигравшего и корня пересобираются `event.Fold` их записей, `is_listed` пересчитывается, пара отклоняется (`dedup_candidates` → `rejected`, `decided_by` = отменивший) — проход больше её не предложит;
  - `apply = false` — только проверки и результат, без изменений.
- **Подкоманда:** `aggregator unmerge <id>` — проверка (строка `UNMERGE event=… mode=journal|legacy class=… merge=… root=… records=… chain=… applied=false`); `aggregator unmerge -apply -by <tg_id> <id>` — отмена. В `agg` и `deploy/` не выведена (D-03; план 07-05).
