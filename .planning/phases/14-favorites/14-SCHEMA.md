## Текст миграции

Имя файла — `migrations/00010_favorites.sql`.

```sql
-- +goose Up
-- Избранное пользователя (Phase 14, D-01): пара «пользователь — старт».
-- Добавление в избранное включает сообщения об этом старте; отдельного
-- признака согласия нет (D-14). Записывается событие, корневое на момент
-- добавления; более позднее слияние разрешается при чтении (D-04).
-- Запись о прошедшем старте остаётся (D-03).
CREATE TABLE favorites (
    tg_id      BIGINT NOT NULL CHECK (tg_id > 0),
    event_id   BIGINT NOT NULL REFERENCES events(id),
    created_at TIMESTAMPTZ NOT NULL,  -- по часам бота: от него считается напоминание (D-09)
    PRIMARY KEY (tg_id, event_id)
);
CREATE INDEX favorites_event ON favorites (event_id);

-- Очередь исходящих сообщений пользователям. Строки создают применение
-- прогона источника (изменения избранных стартов) и бот (напоминания);
-- отправляет только бот. Текста сообщения в таблице нет: payload — что
-- изменилось у старта, текст собирает бот при отправке.
-- UNIQUE (tg_id, dedup_key): одно сообщение на старт за прогон, одно
-- напоминание на дату старта.
CREATE TABLE outbox (
    id         BIGSERIAL PRIMARY KEY,
    tg_id      BIGINT NOT NULL CHECK (tg_id > 0),
    kind       TEXT NOT NULL CHECK (kind ~ '^[a-z][a-z_]{1,31}$'),
    event_id   BIGINT REFERENCES events(id),
    dedup_key  TEXT NOT NULL CHECK (char_length(dedup_key) BETWEEN 1 AND 100),
    payload    JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ NOT NULL,
    claimed_at TIMESTAMPTZ,  -- бот взял сообщение в отправку; без sent_at и done_at исход неизвестен, повторно не шлётся
    sent_at    TIMESTAMPTZ,  -- Telegram принял сообщение
    done_at    TIMESTAMPTZ,  -- закрыто без доставки, причина — в outcome
    outcome    TEXT CHECK (outcome ~ '^[a-z][a-z_]{1,31}$'),
    UNIQUE (tg_id, dedup_key),
    CHECK (sent_at IS NULL OR done_at IS NULL),
    CHECK ((done_at IS NULL) = (outcome IS NULL))
);
CREATE INDEX outbox_pending ON outbox (id) WHERE claimed_at IS NULL AND done_at IS NULL;

-- +goose Down
DROP TABLE outbox;
DROP TABLE favorites;
```

## Что проверено

- 2026-10-10 блок выполнен целиком — раздел Up, затем раздел Down — на локальной тестовой базе (PostgreSQL 17.11, схема версии 9 после `TestMigration00009`) между `BEGIN` и `ROLLBACK`, с остановкой на первой ошибке. Ошибок нет.
- После раздела Up в транзакции созданы: таблица `favorites` с первичным ключом `favorites_pkey`, внешним ключом `favorites_event_id_fkey`, проверкой `favorites_tg_id_check` и индексом `favorites_event`; таблица `outbox` с первичным ключом `outbox_pkey`, внешним ключом `outbox_event_id_fkey`, уникальностью `outbox_tg_id_dedup_key_key`, проверками `outbox_tg_id_check`, `outbox_kind_check`, `outbox_dedup_key_check`, `outbox_outcome_check`, `outbox_check`, `outbox_check1` и индексом `outbox_pending`.
- После раздела Down обеих таблиц нет. После `ROLLBACK` база прежняя: версия схемы 9, шестнадцать таблиц, таблиц `favorites` и `outbox` нет.
- На production текст не выполнялся: исполнитель запросов к production не выполняет. Имена `favorites` и `outbox` в миграциях `00001`–`00009` не заняты.

## Что меняется

- Две новые таблицы. Существующие таблицы, колонки, индексы и ограничения не меняются; строки не переписываются.
- **`favorites`** — пара «Telegram ID — событие» и время добавления по часам бота. Пишет только бот: нажатие «⭐ В избранное» создаёт строку, «✖️ Убрать из избранного» удаляет. Индекс по событию — для поиска подписчиков изменившегося старта.
- **`outbox`** — очередь исходящих сообщений. Строки об изменениях и о пропавших стартах пишет применение прогона источника в своей транзакции; строки напоминаний и сообщений администратору о предохранителе пишет бот; отправляет и отмечает только бот. Частичный индекс — по ожидающим строкам.
- **Текста сообщений в очереди нет.** `payload` хранит, что изменилось у старта (прежнее и новое значение даты, признака даты-заглушки и статуса, признак «появилась ссылка»); текст бот собирает при отправке из строки события.
- **Внешнего ключа на `users` у избранного нет:** строки `users` у нажавшего кнопку может не быть (поддержка и карточка доступны без `/start`), а избранное от неё зависеть не должно. `tg_id` проверяется только на положительность, как в таблицах поддержки.
- **Пригодность для Phase 10.** Вид сообщения (`kind`) проверяется по формату, а не закрытым списком; событие необязательно; содержимое — `payload`. Так очередь примет и рассылки Phase 10 без новой миграции. Ничего сверх этого для Phase 10 не закладывается: колонок расписания, сегментов и текста рассылки нет.
- **Отметки.** `claimed_at` — бот взял сообщение; `sent_at` — Telegram принял; `done_at` с `outcome` — закрыто без доставки. Строка с `claimed_at` без `sent_at` и `done_at` — «исход неизвестен»: повторно не берётся (гарантия «не более одного раза», раздел 8 контракта).

## Блокировки

Упрощение: обе таблицы ссылаются на событие внешним ключом. Вставка строки избранного или очереди берёт по строке события блокировку `FOR KEY SHARE`. Запись прогона берёт строку каждого записываемого события запросом `SELECT … FOR UPDATE` (`internal/store/events.go:331` и `:548`) и держит до конца своей транзакции, а вся запись прогона — одна транзакция (`internal/ingest/runner.go:192`). `FOR KEY SHARE` с `FOR UPDATE` несовместим, поэтому вставка ждёт конца транзакции записи прогона.

- **Потолок.** Нажатие «⭐ В избранное» и создание напоминаний ботом, попавшие на запись прогона того же старта, ждут её конца — секунды, пока идёт запись одного прогона; запись прогона каждого источника — раз в шесть часов. На время ожидания создания напоминаний отправка сообщений стоит. Предела ожидания базы у обработчиков нажатий нет. Нажатие дожидается и выполняется; состояние не портится.
- **Что не ждёт.** Строки очереди, которые пишет сам прогон, — они в той же транзакции. Чтение раздела и карточки. Удаление из избранного. Отправка уже созданных сообщений.
- **Альтернативы — вопрос Q-10 контракта; предлагаются, не рекомендуются.** (б) Убрать оба `REFERENCES events(id)` из блока sql: ожидания нет, меняется только текст миграции; цена — целостность держит код (добавление проверяет событие, чтение соединяет с событиями, строки событий в проекте не удаляются), очистка тестовой базы называет новые таблицы поимённо. (в) Заменить в записи события `FOR UPDATE` на `FOR NO KEY UPDATE`: ожидания нет, ключи остаются; цена — меняется код записи событий, который фаза обязалась не трогать, планы 14-02…14-07 перепланируются.

## Совместимость

- Прежний образ с новой схемой работает: новых таблиц он не читает и не пишет. Поэтому откат образа после миграции безопасен. Кнопки `w:` из сообщений нового образа прежний образ встречает ответом «Кнопка устарела — нажмите /start».
- Новый образ со старой схемой не работает в части избранного: раздел, кнопка избранного и цикл отправки обращаются к таблицам, которых нет. Миграция применяется при выкате нового образа, до его запуска; порядок шагов — в плане 14-07.
- События, их дистанции, записи источников, журнал слияний, кандидаты дублей, пользователи и профили миграция не затрагивает.

## Откат

- Откат — возврат прежнего образа; схема остаётся новой, таблицы — на месте вместе с избранным пользователей. После повторного выката нового образа избранное на месте; сообщения `change` и `gone` старше 72 часов бот закроет как просроченные.
- Обратная миграция на production не выполняется. Раздел Down нужен для локальной разработки и тестов миграций.
- Что делает Down: удаляет таблицы `outbox` и `favorites` целиком. **Это удаляет избранное всех пользователей и очередь сообщений без возможности восстановления, кроме как из резервной копии, — поэтому на production раздел Down не выполняется.**
