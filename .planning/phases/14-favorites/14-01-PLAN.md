Событие с записями двух источников скрывается, только когда пропало из обоих. Запись, найденная снова, возвращает событие в выдачу. Прогоны `suspect` и `failed` наблюдение не выполняют: пропусков и скрытий по ним нет. Прогон, потерявший больше половины записей относительно базы, получает `suspect` (`LowRatio` в `internal/ingest/quality.go`). Запись, вышедшая за пределы каталога (`out_of_scope`), скрывает событие в том же прогоне.
- Пометка «(дата уточняется)» стоит в начале названия лыжных записей Tristyle с датой-заглушкой (Phase 13, D-23, D-30); адаптер не ставит её повторно, если слова «дата уточняется» уже есть в названии — так бывает и в названиях от организатора (`internal/ingest/sources/tristyle/parse.go:109`: условие пометки — слов в названии ещё нет и дата — заглушка). Отсюда второй случай: организатор сам написал «дата уточняется» в названии при точной дате — адаптер пометку не ставит, а слова в названии есть. Отдельного признака в схеме нет.
- Блокировки при записи прогона: запись события берёт его строку запросом `SELECT … FOR UPDATE` (`internal/store/events.go:331` — `saveEventTx`, `:548` — `SaveEventFor`) и держит до конца транзакции, а вся запись прогона — одна транзакция (`internal/ingest/runner.go:192`). Вставка строки с внешним ключом на событие берёт по строке события `FOR KEY SHARE`; с `FOR UPDATE` он несовместим, поэтому вставка ждёт конца транзакции записи прогона. Предела ожидания базы у обработчиков нажатий нет. Строки событий в проекте не удаляются: запроса удаления из `events` нет ни в коде, ни в миграциях.
- Слияние схлопывает цепочки `merged_into_id` до одного шага; корень даёт `store.RootEventID`. Карточка слитого события открывает корень.
- Прогон каждого источника — раз в шесть часов; прогоны `suspect` и `failed` к каталогу не применяются; принятие `suspect` кнопкой выполняется в процессе бота тем же кодом записи (`Runner.Accept`). Запись прогонов, проход дедупликации и слияния идут под одной блокировкой (`LockDedup`).
- Бот и воркер — разные процессы; у воркера нет токена Telegram и перечня администраторов.
- Отправка сообщений ботом — `send` в `internal/bot/tg.go`; ответ 403 распознаётся как блокировка (`classify`, `kindBlocked`), 429 — с `retry_after`. Циклы бота с подставным временем — `internal/alert` и `internal/dedup/digest.go` (сводка в 10:00 по Москве).
- Снимок вызова Bot API (`renderCall`, `internal/bot/snapshot_test.go`) содержит метод, `parse_mode`, текст и клавиатуру; для ответа на нажатие — текст уведомления и `show_alert`. Признак «без звука» в снимок не попадает: его тест проверяет отдельно.
- Строки `users` у нажавшего кнопку может не быть (поддержка доступна и без `/start`); избранное не должно от неё зависеть.
- Каталог тестов бота — 133 беговых события сохранённой страницы Марафонца и пять лыжных событий сохранённых страниц Tristyle (у трёх — пометка «(дата уточняется)»); «сегодня» — 2026-09-29 (`fixtureToday`).

## Черновики для контракта

Это предложения исполнителю; окончательный текст — в контракте после ответа владельца.

**Callback.** Новый префикс `w` (избранное и слежение), без версии фильтров: избранное от фильтров не зависит.

| Данные | Что делает |
|---|---|
| `w:o` | раздел «Избранное», первая страница (правка сообщения) |
| `w:p:{стр}` | страница раздела |
| `w:e:{id}:{стр}` | карточка из раздела; «Назад» ведёт на `w:p:{стр}` |
| `w:n:{id}` | «Открыть старт» из сообщения бота: карточка новым сообщением, само сообщение остаётся; «Назад» ведёт на `w:p:1` |
| `w:a:{id}` | добавить в избранное |
| `w:x:{id}` | убрать из избранного |

Нажатие `w:a` и `w:x` меняет запись, показывает уведомление и правит только клавиатуру того сообщения, где нажата кнопка: строка «⭐ В избранное» меняется на «✖️ Убрать из избранного» и обратно; текст сообщения не трогается. Правило правки клавиатуры: заменяется кнопка с данными `w:a` либо `w:x` этого события, где бы в клавиатуре она ни стояла; все остальные кнопки сохраняются на своих местах — и «Открыть старт» в сообщении об изменении, и ссылка регистрации, и «Назад» в карточке. Так одна пара кнопок работает в карточке из списка, из результатов запроса, из раздела и в сообщении бота. Подписи обеих кнопок избранного одни и те же в карточке и в сообщении бота: иначе после нажатия подпись в сообщении сменилась бы на подпись карточки. Обе кнопки задают состояние, а не переключают его: повторное нажатие устаревшей кнопки ничего не ломает.

сообщение об изменении и напоминание не отправляются, если к моменту отправки пользователь убрал старт из избранного или старт стал недоступен; сообщение D-17 не отправляется, если к моменту отправки старт вернулся в выдачу, прошёл либо убран из избранного; скрытия входят в счёт предохранителя вместе с изменениями; бот отправляет не больше одного сообщения в секунду на всех пользователей (потолок 3600 в час); сообщение об изменении старше 72 часов не отправляется; закрытые строки очереди удаляются через 30 дней; напоминание не шлётся о скрытом старте, а о перенесённом (статус `postponed`) — по принятому варианту Q-11; точная дата, названная меньше чем за семь дней до старта, напоминания не даёт; напоминание отправляется в день «за семь дней» с 10:00 до конца суток по Москве — бот, не работавший весь этот день, напоминание не шлёт; прошедший старт в избранное не добавляется; предел считается по будущим стартам; гарантия отправки — «не более одного раза»: сообщение, отправка которого оборвалась (перезапуск бота или обрыв связи во время вызова Bot API), повторно не шлётся и может не дойти; сбой до вызова Bot API (ошибка базы при подготовке сообщения) сообщение не теряет — отметка взятия снимается, и оно уходит позже, а если не удалось и снятие отметки, сообщение не уходит никогда; **Следствия правил, которые пользователь может заметить** (в контракте — отдельным списком в разделе «Уточнения плана», владелец видит их при утверждении):

- (а) Повторное сообщение о ссылке. Запись источника, давшая старту ссылку, ушла в `gone`, ссылка у старта исчезла, затем запись вернулась — придёт ещё одно сообщение «появилась ссылка». Правило D-05 «появилась годная ссылка» сравнивает состояние до и после прогона и прошлых сообщений не помнит.
- (б) Слияние сообщений не даёт. Дата или ссылка корневого старта изменились из-за слияния или отмены слияния — сообщения нет: сообщения создаёт только применение прогона источника.
- (в) Второе напоминание при слиянии в день напоминания. Ключ напоминания — корневое событие и дата старта. Если избранный старт слит с другим после отправки напоминания в тот же день «за семь дней», корень меняется, и о том же старте придёт второе напоминание. Упрощение: потолок — одно лишнее напоминание на слияние в этот день; автослияние выключено, слияния делает администратор вручную. Убрать можно, запоминая напоминания по всей группе слитых событий, — это отдельный запрос по цепочке слияний, в фазу не входит.
- (г) Перенесённый старт. Напоминание шлётся только о старте в статусе «состоится»; об отменённом не шлётся по D-11, о перенесённом — по ответу на Q-11.

## Черновик текста миграции

Имя файла — `migrations/00010_favorites.sql`. Текст проверен 2026-10-10 на локальной тестовой базе выполнением разделов Up и Down в одной транзакции с откатом.

```sql
-- +goose Up
-- Избранное пользователя (Phase 14, D-01): пара «пользователь — старт».
-- Добавление в избранное включает сообщения об этом старте; отдельного
-- признака согласия нет (D-14). Записывается событие, корневое на момент
-- добавления; более позднее слияние разрешается при чтении (D-04).
-- Запись о прошедшем старте остаётся (D-03).
CREATE TABLE favorites (
    tg_id      BIGINT NOT NULL CHECK (tg_id > 0),
    event_id   BIGINT NOT NULL REFERENCES events(id),
    created_at TIMESTAMPTZ NOT NULL,  -- по часам бота: от него считается напоминание (D-09)
    PRIMARY KEY (tg_id, event_id)
);
CREATE INDEX favorites_event ON favorites (event_id);

-- Очередь исходящих сообщений пользователям. Строки создают применение
-- прогона источника (изменения избранных стартов) и бот (напоминания);
-- отправляет только бот. Текста сообщения в таблице нет: payload — что
-- изменилось у старта, текст собирает бот при отправке.
-- UNIQUE (tg_id, dedup_key): одно сообщение на старт за прогон, одно
-- напоминание на дату старта.
CREATE TABLE outbox (
    id         BIGSERIAL PRIMARY KEY,
    tg_id      BIGINT NOT NULL CHECK (tg_id > 0),
    kind       TEXT NOT NULL CHECK (kind ~ '^[a-z][a-z_]{1,31}$'),
    event_id   BIGINT REFERENCES events(id),
    dedup_key  TEXT NOT NULL CHECK (char_length(dedup_key) BETWEEN 1 AND 100),
    payload    JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ NOT NULL,
    claimed_at TIMESTAMPTZ,  -- бот взял сообщение в отправку; без sent_at и done_at исход неизвестен, повторно не шлётся
    sent_at    TIMESTAMPTZ,  -- Telegram принял сообщение
    done_at    TIMESTAMPTZ,  -- закрыто без доставки, причина — в outcome
    outcome    TEXT CHECK (outcome ~ '^[a-z][a-z_]{1,31}$'),
    UNIQUE (tg_id, dedup_key),
    CHECK (sent_at IS NULL OR done_at IS NULL),
    CHECK ((done_at IS NULL) = (outcome IS NULL))
);
CREATE INDEX outbox_pending ON outbox (id) WHERE claimed_at IS NULL AND done_at IS NULL;

-- +goose Down
DROP TABLE outbox;
DROP TABLE favorites;
```

Существующие таблицы не меняются. Прежний образ с новой схемой работает: новых таблиц он не читает и не пишет. Вид сообщения (`kind`) проверяется по формату, а не закрытым списком, событие необязательно, содержимое — `payload`: так очередь пригодна и для рассылок Phase 10 без новой миграции; ничего сверх этого для Phase 10 не закладывается.

Блокировки (показать владельцу при утверждении схемы, раздел `## Блокировки` в `14-SCHEMA.md`). Упрощение: обе таблицы ссылаются на событие внешним ключом; вставка строки избранного или очереди берёт по строке события `FOR KEY SHARE` и ждёт, пока запись прогона, держащая по этому событию `FOR UPDATE`, не завершит транзакцию. Потолок: нажатие «В избранное» и создание напоминаний ботом, попавшие на запись прогона, ждут её конца — секунды, пока идёт запись одного прогона; строки очереди, которые пишет сам прогон, не ждут — они в той же транзакции. Варианты без ожидания — в вопросе Q-10; при варианте «без внешних ключей» из блока sql убираются оба `REFERENCES events(id)`, остальное не меняется.
