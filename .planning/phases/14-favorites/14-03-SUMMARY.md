## Как устроен шаг

Порядок внутри транзакции прогона (`Runner.write`; та же функция — у `Run` при `ok` и у `Accept`):

1. `LockDedup` — прежний.
2. **Снимок «до»** (`watchBefore`): `WatchStates` в точке сохранения — один запрос `SELECT id, title, start_date, status, registration_url FROM events e` + `futureListed()` на UTC-дату часов прогона (как у наблюдения). Ошибка — запись `watch failed` в лог, шага в этом прогоне нет.
3. `apply`, `MarkSeen`, `observe` — прежние, без изменений.
4. **Шаг** (`watch`), одна точка сохранения: снимок «после» тем же запросом; события снимка «до», которых нет в снимке «после», → `HiddenEvents` — один запрос `id = ANY($1) AND NOT is_listed AND merged_into_id IS NULL` (пустой перечень — без запроса); `event.WatchDiff(before, after, hidden)`; предохранитель; по одному `INSERT … SELECT … FROM favorites … ON CONFLICT (tg_id, dedup_key) DO NOTHING` на изменение (не больше 20 на прогон). Ошибка любого запроса откатывает только точку сохранения и пишется в лог; `write` её не возвращает, каталог применяется.

Цена: на чтение — два запроса по снимку и не больше одного по скрытым; запроса на событие нет. На тестовой базе со снимком 803 старта запрос снимка выполняется за 0,28 мс (`EXPLAIN ANALYZE`, последовательный просмотр). Записей в очередь — по запросу на изменившийся старт, не больше порога предохранителя.

Лог шага — только счётчики: `msg=watch run_id=… changed=… gone=… queued=…` (если было что-то), `msg="watch held" … changed=… gone=… queued=0 threshold=20`, `msg="watch failed" run_id=… err=…`. Названий, идентификаторов событий и пользователей нет (`TestWatchRun/log` проверяет белым списком).

## Строка очереди (читает план 14-04)

| Вид | Когда | Ключ повтора | Содержимое `payload` |
|---|---|---|---|
| `change` | изменились ссылка, дата (или признак заглушки), статус | `change:{прогон}:{событие}` | `{"link":true, "date":{"from":"ГГГГ-ММ-ДД","to":"ГГГГ-ММ-ДД","from_tbd":true,"to_tbd":true}, "status":{"from":"scheduled","to":"cancelled"}}` — только изменившиеся части; `false` у признаков не пишется |
| `gone` | старт скрыт этим прогоном (D-17) | `gone:{прогон}:{событие}` | `{}` |

`event_id` — корневое событие; `created_at` — часы прогона (у `Accept` — часы принятия). Обратно строка читается `event.ParseChange(kind, event_id, payload)`; незнакомые ключи не мешают. Название и дату бот берёт из строки события при отправке.

## Пять пунктов особого внимания

1. **Снимок «до/после».** Снимок берёт только корневые события (`futureListed`: `merged_into_id IS NULL`), поэтому изменение записи слитого события видно как изменение корня, а подписчик слитого получает строку о корне (`TestEnqueueChange`, `TestWatchRun/merged-two-sources`, `gone-two-sources`). Событие с записями двух источников: поля читаются из строки события, то есть уже после свёртки — смена даты во второй записи при дате в первой строк не даёт, ссылка из второй записи при пустой первой даёт «появилась ссылка», смена даты первой записи — «дата» (`merged-two-sources`). Дата-заглушка — `DateTBD` по названию снимка; заглушка первого числа → точная дата того же числа — изменение (`TestWatchDiff`). «Появилась годная ссылка» — `!ValidURL(до) && ValidURL(после)`; замена и исчезновение ссылки — нет (`TestWatchDiff`, `fields`). Скрытие — один раз: скрытый старт не входит в следующие снимки «до» (`gone`: третий прогон строк не добавляет; возвращение — без строки; повторное скрытие — новая строка с новым прогоном); прошедший старт в снимок не входит (`TestWatchStates`, `gone-past`).
2. **`suspect` и `failed`.** `suspect` не вызывает `write` — снимков нет (`suspect-accept`, `gone-suspect`: пропуск записи не считается). `failed` откатывает транзакцию целиком (`failed`). Принятие `suspect` идёт через ту же `write` — строка с номером принятого прогона (`suspect-accept`). Оговорка: сбой записи в тесте происходит в `apply`, до шага, поэтому «откат уже записанных строк очереди» тестом не показан; гарантия следует из того, что строки пишутся в точке сохранения внутри транзакции прогона.
3. **Предохранитель.** `watchFuse = 20`, условие `len(changes) > 20`, где `changes` — изменения полей и скрытия вместе по всему снимку каталога. Ровно 20 (19 изменений + 1 скрытие) — строки есть; 21 (20 + 1) — строк нет ни об изменениях, ни о скрытии; 21 одних скрытий — то же; `watch_held` в метриках = сумма, только у сработавшего прогона; статус `ok`, каталог применён (`fuse`, пробы `watch-fuse`, `watch-gone-fuse`).
4. **Повторный прогон тех же данных строк не создаёт.** Причина — сравнение: у повторного прогона снимки «до» и «после» равны (`TestWatchTracer`: `rerun=0`). `UNIQUE (tg_id, dedup_key)` с `ON CONFLICT DO NOTHING` защищает повтор того же прогона и того же события (`TestEnqueueChange`); у нового прогона ключ другой, так что от повтора данных защищает именно сравнение, а не уникальность.
5. **Цена.** Два запроса снимка и один по скрытым на прогон, без запроса на событие; 0,28 мс на 803 стартах; записи — не больше 20 запросов.

## Старт пропал: как и когда

- **Где обнаруживается.** В `Runner.write` после `observe`: события снимка «до», которых нет в снимке «после», проверяются `HiddenEvents`; скрытые и не слитые дают изменение «пропал» и строку `gone` каждому подписчику. Наблюдение не менялось: шаг только читает его итог. Статус события не меняется (`gone`, `gone-out-of-scope`: статус `scheduled`).
- **Когда.** Запись становится `gone` при `missed_runs >= OBSERVE_GONE_RUNS` (3) и `now() - last_seen_at >= OBSERVE_GONE_AFTER` (72 ч) одновременно. При прогонах раз в шесть часов это первый здоровый прогон после 72 часов отсутствия — примерно через трое суток после исчезновения старта из календаря (двенадцатый-тринадцатый пропуск подряд, если все прогоны здоровые: 72 часа с последнего появления при шаге шесть часов); при сбоях прогонов — позже. Строка создаётся в этом прогоне.
- **Границы.** Два источника — скрытие, только когда пропал из обоих; строка в прогоне второго (`gone-two-sources`). Переименование записи — для бота пропажа: строка придёт. Выход записи за пределы каталога (`out_of_scope`) скрывает старт в том же прогоне — строка без задержки (`gone-out-of-scope`). Старт, пропавший меньше чем за трое суток до даты, строки не даёт: он пройдёт раньше, чем станет `gone`; прошедший старт наблюдение не трогает (`gone-past`). Прогоны `suspect` и `failed` наблюдения не выполняют — скрытий и строк нет (`gone-suspect`). Скрытия входят в счёт предохранителя вместе с изменениями; скрытие не больше 20 стартов из-за сбоя источника предохранитель не останавливает.
- **Слитое событие.** Слияние и отмена слияния вне прогона строк не создают (`merge-outside-run`); подписчик слитого события получает `gone` о корне (`gone-two-sources`).

## Статус (D-08)

Изменение статуса обнаруживается сравнением (`TestWatchDiff`: все направления между `scheduled`, `cancelled`, `postponed`) и записывается в очередь с прежним и новым значением (`TestEnqueueChange`). Сквозного пути через прогон нет и в `TestWatchRun` такого случая нет: источники статус не передают — подготовка записи ставит `scheduled`, запись события берёт статус из базы. В production сообщение об изменении статуса не сработает, пока источники не начнут передавать статус (оговорка D-08); настоящую отмену пользователь увидит как сообщение «старт пропал» (D-17).

## Пометки «Упрощение:»

- `store.WatchStates`: снимок — один запрос по всем будущим стартам каталога (сейчас сотни строк); потолок — при десятках тысяч стартов сравнивать только события, затронутые прогоном.
- `store.EnqueueChange`: получатели определяются в момент записи; пользователь, добавивший старт между записью и фиксацией транзакции, сообщения об этом изменении не получит; потолок — проверка при добавлении.
- `Runner.watch`: шаг в точке сохранения; при его сбое сообщения этого прогона теряются — следующий прогон изменений и скрытий уже не увидит.
- `watchFuse`: законное массовое изменение или исчезновение пользователям не сообщается; частичный сбой источника, скрывший не больше 20 стартов, даст подписчикам «старт пропал из календаря».
- `event.DateTBD`: источник, помечающий заглушку иначе, не распознаётся; название, где организатор сам написал «дата уточняется» при точной дате, считается заглушкой.
- «Пропал» — любое скрытие внутри прогона (все записи `gone` либо запись вышла за пределы каталога); причину шаг не различает.
