# Phase 13: текст миграции (13-01)

**Статус:** утверждён владельцем 2026-10-09 («С миграцией согласен», D-27)
**Основа:** 13-CONTEXT.md, решение D-11: дисциплина лыж хранится в `events.event_type` новыми значениями; закрытый список в схеме заменяется проверкой формата, перечень допустимых значений — в справочнике кода. Текст утверждается владельцем до создания файла миграции; в плане 13-01 файла в `migrations/` нет. План 13-02 создаёт файл извлечением блока ниже без изменений.

## Текст миграции

Имя файла — `migrations/00009_event_type_format.sql`.

```sql
-- +goose Up
-- Дисциплина события хранится в event_type; у каждого вида спорта свои
-- значения. Допустимые значения — в справочнике кода; здесь проверяется
-- только формат, как у events.sport.
ALTER TABLE events DROP CONSTRAINT events_event_type_check;
ALTER TABLE events ADD CONSTRAINT events_event_type_check
    CHECK (event_type ~ '^[a-z][a-z_]{1,31}$');

-- +goose Down
-- Прежний закрытый список. NOT VALID: строки с дисциплинами других видов
-- спорта остаются на месте, проверяются только новые и изменяемые строки.
ALTER TABLE events DROP CONSTRAINT events_event_type_check;
ALTER TABLE events ADD CONSTRAINT events_event_type_check
    CHECK (event_type IN ('road', 'trail', 'cross', 'track', 'obstacle', 'other')) NOT VALID;
```

## Что проверено

- Имя ограничения. Миграция `00001` задаёт проверку `event_type` без имени; имя присваивает PostgreSQL. На локальной тестовой базе (PostgreSQL 17, схема после миграции `00008`) запрос к каталогу `pg_constraint` по таблице `events` показал имя `events_event_type_check` и определение `CHECK (event_type = ANY (ARRAY['road', 'trail', 'cross', 'track', 'obstacle', 'other']))`. Рядом стоит `events_sport_check` с тем же форматом, что предлагается здесь.
- На production имя не проверялось: исполнитель запросов к production не выполняет. PostgreSQL даёт такое имя по правилу «таблица_колонка_check», поэтому расхождение маловероятно; проверка имени тем же запросом к каталогу — шаг владельца перед миграцией (план 13-05).
- `DROP CONSTRAINT` записан без `IF EXISTS` намеренно: если имя на production другое, миграция остановится с ошибкой и откатится целиком, а не оставит прежний закрытый список рядом с новой проверкой.

## Что меняется

- Строки не переписываются. Шесть прежних значений (`road`, `trail`, `cross`, `track`, `obstacle`, `other`) формату соответствуют; при добавлении новой проверки PostgreSQL один раз читает таблицу `events`, чтобы убедиться в этом, данные не меняет.
- После миграции схема принимает любое значение формата `^[a-z][a-z_]{1,31}$`: строчная латинская буква, затем от одной до 31 строчной буквы или подчёркивания. Коды дисциплин лыж — `ski` и `rollerski` — формату соответствуют.
- Перечень допустимых значений переезжает из схемы в справочник кода: у каждого вида спорта свой набор дисциплин, значение вне набора своего вида спорта запись не получает (план 13-02, тест справочника). Проверка формата остаётся в схеме как защита от мусора.
- Колонки, индексы, значения по умолчанию и остальные ограничения таблицы не меняются.

## Совместимость

- Прежний образ с новой схемой работает: он пишет только шесть прежних значений, все они формату соответствуют. Поэтому откат образа после миграции безопасен.
- Новый образ со старой схемой не работает для лыжных записей: значение `ski` закрытый список отвергнет. Миграция применяется при выкате нового образа, до первого прогона источников, как миграция `00008` в Phase 12 (`deploy/README.md`); порядок шагов — в плане 13-05.
- Беговые строки, их дистанции, записи источников, журнал слияний и кандидаты дублей миграция не затрагивает; это проверяется сравнением «до и после» (D-12).

## Откат

- Откат — возврат прежнего образа; схема остаётся новой. Прежний образ с новой схемой работает (раздел «Совместимость»); лыжные события он не показывает, потому что лыжи в его справочнике выключены.
- Обратная миграция на production не выполняется. Раздел Down нужен для локальной разработки и тестов миграций.
- Что делает Down: возвращает закрытый список как `NOT VALID`. Данные он не удаляет и не переписывает: строки с дисциплинами лыж остаются в таблице, прежний список проверяется только у новых и изменяемых строк. Без `NOT VALID` обратная миграция при наличии хотя бы одной лыжной строки завершилась бы ошибкой, а удалять события ради отката нельзя.
- После Down лыжные строки нельзя изменить, не сменив им значение `event_type`: прогон источника, обновляющий такую строку, получит ошибку проверки. Это ещё одна причина не выполнять Down на production.
