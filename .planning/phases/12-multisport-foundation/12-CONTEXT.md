## Phase Boundary

У каждого события каталога появляется вид спорта, а в коде — единый справочник видов спорта. Все существующие события получают вид «бег». Пользователь разницы не видит: экраны, тексты и выдача бота не меняются.

<decisions>
## Implementation Decisions

### Справочник
- **D-01:** Справочник видов спорта — в коде, один на проект (Р-3). У вида спорта: код, название, значок, признак «включён».
- **D-02:** Коды: `running`, `skiing`, `swimming`, `cycling`, `multisport`. В этой фазе включён только `running`; остальные заведены выключенными и нигде не показываются.
- **D-03:** OCR и трейл остаются значениями `event_type` у бега (Р-1, Р-10). Перечень `event_type` в этой фазе не меняется.

### Данные
- **D-04:** Таблица `events` получает колонку `sport` со значением по умолчанию `running`; существующие строки не переписываются. Проверка в схеме — по формату кода, не закрытым списком: новый вид спорта не требует миграции.
- **D-05:** Запись источника получает необязательное поле вида спорта; пустое значение означает «бег». Адаптеры в этой фазе его не заполняют.
- **D-06:** Нормализованные поля прежних записей (`source_events.fields`), их `payload` и `content_hash` после выката побайтно те же: первый прогон не должен показать изменений по каталогу.
- **D-07:** В слитом событии вид спорта берётся из первой записи по приоритету источников и не смешивается с другими.

### Выдача
- **D-08:** Бот показывает только события включённых видов спорта — во всех запросах: список, счётчик, города, страны, типы, текстовый поиск, подсказки городов. Событие выключенного вида спорта не видно нигде, включая карточку по прямой кнопке из старого сообщения.
- **D-09:** Экраны и тексты не меняются: ни один существующий эталон не правится, новых сценариев контракта нет.

### Дедупликация
- **D-10:** Настройки и правила дедупликации не меняются; автослияние выключено. Правило «разные виды спорта — отдельные события» — в фазе первого нового вида спорта, когда появятся реальные пары.

### Проверка и выкат
- **D-11:** Критерий готовности — «до и после»: содержимое `events` (кроме новой колонки), `event_distances`, `source_events.fields`, `event_merges` и `dedup_candidates` на копии данных совпадает до и после миграции и первого прогона.
- **D-12:** Текст миграции утверждается владельцем до создания файла. Выкат и миграция в production — отдельным планом, по разрешению владельца на каждый шаг, после резервной копии.

### На усмотрение исполнителя
- Где лежит справочник (пакет `internal/event` — рядом с `Type`) и имена его полей.
- Как именно «бег» записывается в `fields`, чтобы выполнялось D-06.
- Один общий фрагмент SQL для отбора по включённым видам спорта вместо правки каждого запроса.
- Нужен ли индекс по виду спорта: при нынешнем объёме — нет.

</decisions>

## Текст миграции (утверждён владельцем 2026-10-09)

```sql
-- +goose Up
-- Вид спорта события. Существующие события — бег: все источники до этой
-- миграции отдавали только его. Допустимые коды — в справочнике кода;
-- здесь проверяется только формат.
ALTER TABLE events ADD COLUMN sport TEXT NOT NULL DEFAULT 'running'
    CHECK (sport ~ '^[a-z][a-z_]{1,31}$');

-- +goose Down
ALTER TABLE events DROP COLUMN sport;
```

Добавление колонки с постоянным значением по умолчанию не переписывает таблицу. Прежняя версия кода с новой схемой работает: колонку она не читает и не пишет, новые строки получают `running`.

</schema_draft>
