<domain>
## Phase Boundary

Администратор может отправить из бота текстовое сообщение (уведомление или приглашение на забег) пользователям, отобранным по городу проживания и/или виду спорта из профиля, — только тем, кто сам включил уведомления.

Не входят: автоматические уведомления о новых, перенесённых и отменённых забегах (USR-02); карточка забега из каталога как содержание рассылки; фото, видео и файлы; отбор по стране, полу, возрасту и рассылка «всем согласившимся»; отбор по городу, введённому свободным текстом без ключа каталога; лимит частоты на пользователя; отложенная отправка по расписанию; очередь исходящих сообщений в базе и продолжение рассылки после перезапуска; хранение текста рассылки; статистика открытий и переходов; счётчики согласий в `/stats`.

</domain>

<decisions>
## Implementation Decisions

### Содержание
- **D-01:** Администратор отправляет свободный текст; ссылку вставляет сам. Карточка забега из каталога не делается.
- **D-02:** Только текст, до 2000 единиц UTF-16 (как в поддержке). Форматирование и ссылки, набранные администратором, сохраняются.

### Согласие
- **D-03:** Согласие отдельное, выключено по умолчанию, хранится новой колонкой (текст миграции утверждается владельцем до создания файла).
- **D-04:** Включить можно в двух местах: переключатель на экране профиля и один вопрос в конце анкеты.
- **D-05:** Вопрос задаётся только завершившим анкету: у пропустившего нет ни города, ни видов спорта, отбирать его не по чему.
- **D-06:** Пользователям, прошедшим анкету раньше, бот ничего не задаёт и не присылает: они остаются без уведомлений, пока сами не включат в профиле.
- **D-07:** В каждом сообщении рассылки — кнопка «Отключить уведомления»; нажатие выключает согласие сразу, без подтверждения.
- **D-08:** Ответ Telegram «бот заблокирован» при отправке выключает согласие этого пользователя.

### Отбор получателей
- **D-09:** Признаки: город и/или вид спорта. Заданы оба — получатель должен подходить по обоим.
- **D-10:** Город — только с ключом каталога, в паре со страной. Город без ключа в отбор не попадает.
- **D-11:** Получатель — пользователь с включённым согласием и завершённой анкетой. Рассылки без признака отбора нет.

### Запуск администратором
- **D-12:** Запуск — админской командой в личке бота, по шагам: отбор → текст → предпросмотр с числом получателей → подтверждение словом. Отмена возможна на любом шаге до подтверждения.
- **D-13:** Число получателей в предпросмотре показывается точно, без порога «меньше 5»: администратор должен видеть, кому уйдёт сообщение. Списка получателей и их идентификаторов предпросмотр не содержит.
- **D-14:** После отправки администратор получает итог: отправлено, не доставлено.

### Что хранится
- **D-15:** Журнал рассылок: время, признаки отбора, число получателей, число доставленных. Текст сообщения и список получателей не хранятся.
- **D-16:** Лимита частоты рассылок нет: отправляет только администратор.

### Интерфейс и приёмка
- **D-17:** Контракт новых экранов утверждается владельцем до кода; эталоны правятся только вручную; существующие эталоны меняются только там, где на экран добавляется переключатель или вопрос.
- **D-18:** Экраны бота по-прежнему ничего не обещают о данных; текст вопроса о согласии говорит только о том, что бот будет присылать приглашения.

### На усмотрение исполнителя
- Имя команды, префикс callback, имена колонок и таблицы журнала.
- Отправка по одному сообщению с паузой в пределах лимитов Telegram, без очереди в базе. Известный потолок: перезапуск бота во время рассылки обрывает её, журнал покажет неполное число доставленных.
- Меняет ли переключатель согласия `profile_v`.
- Где хранится незавершённый черновик администратора (отбор и текст до подтверждения).

</decisions>

## Сверка 2026-10-23 (возобновление фазы)

Владелец 2026-10-23: «Начинаем фазу 10». Решения D-01…D-18 остаются в силе, кроме отмеченного ниже. С 2026-10-06 в коде изменилось:

- **Очередь исходящих есть** (`outbox`, миграция `00010`; Phase 14, 20, 21). Бот берёт из неё одну строку в секунду (`notifyEvery`), переживает перезапуск, ответ 403 закрывает строку как `blocked`. Решение «без очереди в базе» (раздел «На усмотрение исполнителя») устарело: рассылку выгоднее отправлять через очередь. Строка на получателя, вид `broadcast`.
- **Видов спорта в каталоге четыре** (бег, лыжи, плавание, велоспорт). Отбор идёт по видам спорта профиля (`user_profiles.sports`: run, trail, ocr, bike, swim, ski, tri, row) — это интересы пользователя, а не вид спорта события.
- **Подписка на новые старты** (Phase 20) уже присылает автоматическую подборку по фильтрам. Рассылка Phase 10 — другое: свободный текст администратора.
- **Пользователей 98** (2026-10-23). Сколько из них завершили анкету и кто включит согласие — неизвестно. По D-06 в первый день получателей будет 0, пока люди не включат уведомления сами.
- **Экраны** ничего не обещают о данных пользователя. Запись в ROADMAP про «обезличенную статистику» устарела, её правка — при планировании.

### Новые вопросы

- **Q-1. Отправка через очередь `outbox`.** Рекомендую да: рассылка не оборвётся при перезапуске бота, 403 и темп уже обработаны. Темп общий для всего бота — одно сообщение в секунду, 100 получателей ≈ 2 минуты. Напоминания и подборки идут в ту же очередь и встанут за рассылкой.
- **Q-2. Текст рассылки и D-15 («текст не хранится»).** Через очередь текст лежит в базе, пока сообщения не разосланы. Варианты:
  - (а) текст хранится в журнале рассылки, пока её строки не закрыты, затем стирается — рекомендую;
  - (б) текст хранится навсегда.
- **Q-3. Остаются ли D-05 и D-06?** Вопрос о согласии — только в конце анкеты и переключателем в профиле; прошедших анкету раньше бот не спрашивает. Рекомендую оставить: иначе это незапрошенное сообщение.
- **Q-4. Отбор по видам спорта профиля** (8 значений анкеты) — подходит? Рекомендую да; в мастере рассылки — те же названия, что в анкете.
- **Q-5. Правовой вопрос.** Отдельное согласие, выключенное по умолчанию, и отказ в каждом сообщении соответствуют обычной практике для рассылок (в РФ — ст. 18 закона «О рекламе», предварительное согласие). Юридически это не проверялось. Достаточно ли для первых рассылок, или проверить до запуска?

### Два вида рассылки (решение владельца 2026-10-23)

Владелец спросил, можно ли писать всем без согласия; после разбора рисков (блокировка бота за спам, ст. 18 закона «О рекламе», новая цель обработки ответов анкеты) — «Да, делаем два вида рассылки».

- **D-19. Объявление** — сообщение о самом боте (новые возможности, переезд, технические работы).
  - Получатели — все пользователи бота, кроме отказавшихся; отбора по анкете нет.
  - В каждом сообщении кнопка «🔕 Не присылать объявления»: нажатие сразу ставит отказ.
  - Согласия не требует. Рекламы и приглашений на старты в объявлении нет — это правило для администратора, текст мастера о нём напоминает.
  - В предпросмотре администратор видит дату прошлого объявления. Жёсткого лимита частоты нет (D-16), договорённость — не чаще раза в несколько недель.
- **D-20. Приглашение** — приглашение на старты по городу и/или виду спорта (D-01…D-13).
  - Получатели — только включившие уведомления (D-03…D-11).
  - Кнопка «🔕 Отключить уведомления».
- **D-21. Независимость.** Отказ от объявлений не выключает приглашения, и наоборот. Ответ «бот заблокирован» закрывает строку очереди; у приглашений он также выключает согласие (D-08).

### Проект схемы (миграция `00015_broadcasts.sql`, файл не создан)

```sql
-- +goose Up
ALTER TABLE user_profiles
    ADD COLUMN notify_opt_in       BOOLEAN NOT NULL DEFAULT false,  -- приглашения: согласие, выключено по умолчанию
    ADD COLUMN notify_changed_at   TIMESTAMPTZ,
    ADD COLUMN announce_opt_out    BOOLEAN NOT NULL DEFAULT false,  -- объявления: отказ
    ADD COLUMN announce_changed_at TIMESTAMPTZ;

CREATE TABLE broadcasts (
    id           BIGSERIAL PRIMARY KEY,
    kind         TEXT NOT NULL CHECK (kind IN ('announce', 'invite')),
    admin_tg_id  BIGINT NOT NULL CHECK (admin_tg_id > 0),
    created_at   TIMESTAMPTZ NOT NULL,
    filter       JSONB NOT NULL DEFAULT '{}'::jsonb,  -- у приглашения: {"country":"RU","city_key":"tula","sports":["run"]}
    text         TEXT CHECK (char_length(text) BETWEEN 1 AND 4096),  -- NULL после рассылки (Q-2 а)
    recipients   INTEGER NOT NULL CHECK (recipients >= 0),
    finished_at  TIMESTAMPTZ,
    CHECK (kind = 'invite' OR filter = '{}'::jsonb)
);

-- +goose Down
DROP TABLE broadcasts;
ALTER TABLE user_profiles
    DROP COLUMN announce_changed_at, DROP COLUMN announce_opt_out,
    DROP COLUMN notify_changed_at, DROP COLUMN notify_opt_in;
```

- Строка `user_profiles` есть у каждого пользователя: создаётся в транзакции `/start` (миграция `00006`).
- Получатели — строки `outbox` вида `broadcast` с `payload {"b": <id>}`; доставлено и не доставлено считаются по исходам этих строк. Отдельного списка получателей нет.
- **Q-6. Схему утверждаешь?** После ответов — контракт экранов: мастер рассылки у администратора (выбор вида, отбор для приглашения, текст, предпросмотр, подтверждение), переключатели в профиле (приглашения и объявления), вопрос в конце анкеты, сообщения объявления и приглашения с кнопками отказа, итог для администратора. Код — после утверждения контракта.

## Ответы владельца 2026-10-23

Владелец: «Q-1…Q-5 по рекомендациям, схему утверждаю».

- Q-1: рассылка — через очередь `outbox`, вид `broadcast`.
- Q-2 (а): текст хранится в `broadcasts.text`, пока строки рассылки не закрыты, затем стирается.
- Q-3: D-05 и D-06 остаются; вопрос о приглашениях — только в конце анкеты и переключателем в профиле. Объявления доходят до всех, кроме отказавшихся.
- Q-4: отбор приглашений — по восьми видам спорта анкеты.
- Q-5: юридическая проверка не проводится; для приглашений на платные старты сторонних организаторов — до первой такой рассылки (раздел Deferred).
- Q-6: схема `00015_broadcasts.sql` утверждена в редакции раздела «Проект схемы» выше.
