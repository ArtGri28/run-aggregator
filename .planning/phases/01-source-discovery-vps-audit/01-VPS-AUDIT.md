# Phase 1: аудит VPS (только чтение)

Источник истины: MVP.md. Связанный отчёт: `01-SOURCES-REPORT.md`.

## 1. Как выполнялся аудит

Дата прогона: 2026-09-28 (дата изменения файла `vps_audit_out.txt`). Запуск — обёрткой `run_block.sh` по разрешению владельца (MVP §19 решение 33 заменило решение 28: инструменты запускают только утверждённые владельцем read-only блоки через обёртку с отдельным проектным ключом и непривилегированным пользователем `runagg`; административных прав у них нет).

Скрипт `vps_audit.sh` (`01-COMMANDS.md` §4) только читает локальное состояние VPS: не делает исходящих сетевых запросов, не устанавливает и не перезапускает ничего, не пишет файлы. Он подаётся в `ssh <алиас> 'bash -s'` через stdin — на VPS не создаётся ни одного файла. В этом прогоне (прогон 2) использовалась автоматическая обёртка `~/run-agg-phase1/bin/run_block.sh` (вне репозитория, MVP §7.4, решение 33) вместо построчного ручного запуска из §0 `01-COMMANDS.md`. Обёртка выполняет тот же блок из белого списка тем же способом (stdin, без файлов на VPS) и с теми же проверками: до запуска `safety_lint` и `getrun_gate`, после — `redaction_check` и `owner_leak_check`; владелец по-прежнему читает блок (`run_block.sh show vps_audit.sh`) и утверждает его (`approve`) до первого запуска и после любого изменения. По существу это тот же read-only процесс, что описан в `01-COMMANDS.md`, только запуск автоматизирован.

Функция `rd()` (замена публичных адресов на метки) выполняется на стороне VPS до того, как вывод попадает на экран владельца. `redaction_check` и `owner_leak_check` выполняются на ноутбуке владельца. Сырой вывод — `vps_audit_out.txt` (217 строк) — хранится вне репозитория (`$HOME/run-agg-phase1/`), не коммитится, прошёл обе проверки (`REDACTION OK`, `OWNER LEAK OK`). Инструменты подключались к VPS только через обёртку (MVP §7.4, решение 33): отдельный проектный ключ с `restrict`, пользователь `runagg` без привилегий, белый список блоков, запуск только после `approve` владельца; анализ ниже сделан только по уже очищенному выводу.

## 3. tinyproxy (MVP §12.3)

**Происхождение.** `dpkg -l tinyproxy*` подтверждает установку; `apt-mark showmanual` — пакет отмечен `manual`. Дата установки по `/var/log/dpkg.log*`: 2026-09-06. Конфигурационный файл (`stat /etc/tinyproxy/tinyproxy.conf`) не менялся с 2022-06-05 — то есть текущий конфиг старше даты установки пакета; перенесён ли он с прежнего хоста или это переустановка поверх сохранённого файла, не установлено (см. §5).

**Статус юнита.** `systemctl show`: `LoadState=loaded`, `ActiveState=active`, `SubState=running`, `UnitFileState=enabled` — процесс запущен и включён в автозагрузку.

**Кто пользуется (только агрегаты, IP клиентов и список хостов не приводятся).** Лог tinyproxy недоступен для чтения пользователю `runagg` (строка «НЕДОСТУПНО (нет прав)»): число соединений, число различных клиентов и число клиентов вне RFC1918/loopback в этом прогоне не получены; топ запрашиваемых хостов (подраздел 03b) — тоже НЕДОСТУПНО. Фактическая история использования не проверена, это открытый вопрос (§5), а не находка о риске.

**Listen / Bind.** Директива `Listen` в allowlist вывода отсутствует → по умолчанию все интерфейсы (`0.0.0.0`); подтверждено строкой «Порты» в §2: `ss` показывает `0.0.0.0:8888` и `[::]:8888`.

**Allow / Deny.** `Allow 127.0.0.1`, `Allow ::1`; строк `Deny` нет.

**BasicAuth.** 0 строк (только счётчик; содержимое не запрашивалось и не печаталось).

**Upstream.** 0 строк (только счётчик).

**ConnectPort.** Директивы нет в allowlist вывода → не задана; по документации tinyproxy при отсутствии `ConnectPort` для `CONNECT` разрешены все порты.

**Переменные прокси в окружении.** `http_proxy`, `https_proxy`, `HTTP_PROXY`, `HTTPS_PROXY`, `no_proxy` — в ssh-сессии аудита не заданы (зафиксирован только факт «задана/не задана», значения не печатались); строк с `proxy` в `/etc/environment` — 0 (только счётчик).

**ufw для порта 8888 и политика по умолчанию.** `ufw status verbose`/`ufw status numbered`: `inactive`. `/etc/default/ufw`: `DEFAULT_INPUT_POLICY="DROP"`, не применяется, пока `ufw` выключен. `iptables -S`: `-P INPUT ACCEPT` — отдельного правила, блокирующего порт 8888, нет.

Вердикт «открытый прокси»: нет

Разбор четырёх условий (по «Как читать блок tinyproxy», `01-COMMANDS.md` §4 — «открытый прокси» = все четыре условия одновременно):
1. слушает не на loopback — ДА (`0.0.0.0`/`[::]`, все интерфейсы);
2. нет ограничений `Allow` — НЕТ (`Allow 127.0.0.1`, `Allow ::1` заданы — доступ ограничен этими адресами);
3. `BasicAuth` = 0 — ДА;
4. порт не закрыт фаерволом — ДА (`ufw` неактивен, `iptables` не блокирует 8888).

Условие 2 не выполняется, поэтому формально это не «открытый прокси» по определению плана. Оговорка: внешнюю достижимость порта 8888 с самого VPS проверить нельзя — такая проверка потребовала бы исходящего запроса через сам прокси с другой машины, это использование сервиса, а не аудит, и в read-only блок не входит; решение о такой проверке остаётся за владельцем (§5). Отдельно фиксируется структурный риск: у tinyproxy нет резервного барьера на уровне сети — единственная защита это прикладной `Allow` самого процесса; при ошибке в конфигурации или уязвимости в самом tinyproxy отсутствие правила `ufw`/`iptables` на порт 8888 не даёт второго уровня защиты (defence-in-depth).

Варианты безопасного закрытия — только предложение для Phase 6 (PRD-07), выполняются исключительно с подтверждения владельца: ограничить `Listen` значением `127.0.0.1`, сохранить или сузить `Allow`, закрыть порт 8888 в `ufw` при его включении, либо отключить сервис, если он не нужен владельцу для других задач. Проект (бот, worker) tinyproxy не использует и использовать не будет (MVP §12.3, решение 22).

## 4. Изменения на VPS

Блоки `vps_audit.sh`, `src_probe_marathonec.sh`, `src_probe_rest.sh`, `src_probe_getrun.sh` из `01-COMMANDS.md` — только чтение: не устанавливают пакеты, не перезапускают и не включают/выключают сервисы, не меняют файлы и конфигурацию, не делают исходящих сетевых запросов к самому VPS (только `probe`/`dns` к сайтам-кандидатам, не к VPS). `safety_lint` по каждому прогонному блоку — `SAFETY OK`. На VPS не создано ни одного файла: скрипты подавались через stdin, `tee` пишет только на ноутбук владельца. Команды `apt update`/`apt upgrade`, `systemctl restart`/`enable`/`disable`, `ufw enable`, установка пакетов в ходе аудита не выполнялись.

Отдельно, честно и не мимоходом: чтобы прогон 2 можно было запускать автоматической обёрткой `run_block.sh`, а не построчно вручную, владелец **отдельно, из собственной root-сессии, вне read-only блоков этой фазы**, один раз выполнил административную настройку самого VPS (MVP §19, решение 33): создал непривилегированного пользователя `runagg` (собственная основная группа, без дополнительных групп, пароль заблокирован, shell `/bin/bash`), добавил узкий `/etc/sudoers.d/run-agg`, разрешающий ровно шесть read-only команд (`ufw status verbose`, `ufw status numbered`, `iptables -S`, `ip6tables -S`, `sshd -T`, `ss -H -tulpn`), и одну строку `authorized_keys` с флагом `restrict` для отдельного проектного SSH-ключа. Это реальное и осознанное изменение состояния VPS — но это инфраструктура самого механизма автоматического запуска read-only аудита, а не действие скриптов `vps_audit.sh`/`src_probe_*.sh`: этой настройкой не менялись ни пакеты, ни firewall, ни systemd-юниты приложений, ни Docker. Владелец проверял её сам (эта настройка требует root, а у инструментов административного доступа к VPS нет, MVP §7.4): PREFLIGHT-прогон до создания `runagg` и VERIFY-прогон после — оба подтверждены владельцем.

Подтверждение владельца (2026-09-29): на VPS выполнялись только read-only команды из `01-COMMANDS.md` (`vps_audit.sh`, `src_probe_marathonec.sh`, `src_probe_rest.sh`, `src_probe_getrun.sh`) — они изменений не вносили; создание пользователя `runagg` и узкого `sudoers` (описано выше) было отдельным согласованным bootstrap-шагом для самой инфраструктуры запуска, а не действием этих read-only блоков, и после этого bootstrap-шага инфраструктура не менялась.

## 5. Открытые вопросы

1. Внешняя достижимость порта 8888 tinyproxy с внешнего клиента не проверялась (потребовала бы исходящего использования прокси, что выходит за рамки read-only аудита); решение о такой проверке и о судьбе tinyproxy — Phase 6, PRD-07, только с подтверждения владельца.
2. Разрешение владельца на системное обновление (24 обновления в кэше, из них 3 security) и перезагрузку (`reboot-required: YES`) — MVP §18, до Phase 6.
3. Лог tinyproxy и связанные агрегаты (число клиентов, топ хостов) недоступны пользователю `runagg` без расширения прав (группа `tinyproxy` или root) — фактическая история использования сервиса не проверена.
4. `docker info`/`ps`/`system df` недоступны пользователю `runagg` (намеренно не в группе `docker`) — содержимое контейнеров не проверено; решение о проверке — за владельцем.
5. `System clock synchronized: no` при активном `systemd-timesyncd` и `Packet count: 0` на момент среза — не установлено, синхронизировались ли часы позже среза; повторная проверка в динамике — задача Phase 6.
6. Происхождение конфигурации tinyproxy: пакет установлен 2026-09-06, но конфигурационный файл не менялся с 2022-06-05 — конфигурация старше установки; перенесена ли она с прежнего хоста или это переустановка поверх сохранённого файла, не установлено.

Подтверждение владельца (2026-09-29, при аудите безопасности фазы): блоки прогона 2 (`vps_audit.sh`, `src_probe_rest.sh`, `src_probe_getrun.sh`) в их финальной версии были прочитаны (`run_block.sh show`) и утверждены (`approve`) до запуска.
