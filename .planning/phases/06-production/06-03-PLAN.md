- Bash для шагов 6–7 и статуса: бэкап не зависит от образа приложения и `IMAGE_TAG` (RESEARCH).

- Причина `COPY FAIL reason=mark` закреплена S2: копия доставлена, запись `backup_copy` не удалась; код 2.
- `SIZE WARN` в подписи — вторая строка; первая строка подписи остаётся ровно по контракту (S6).
- Отправка не зависит от исхода ротации; код при `ROTATE ABORT` — 3 при удавшейся отправке, 2 при неудавшейся (S2).
- Повторная отправка — повторный запуск `backup.sh`; режима «только отправка» нет.
- `backup-status.sh`: код 1 при `STATUS WARN`; значения `none` и `unknown`; строки `WARN <ключ>`; хвост лога не печатается.
- Режим `cron` отказывает при несинхронизированных часах; `backup.sh` проверяет часы сам при каждом запуске (06-02).
- `getChat` подтверждает, что бот видит канал; право публикации подтверждает первая отправка в 06-04 (A6). Идентификатор канала — `^-?[0-9]+$`.
- Активный алерт `backup_size_warn` (S4): при `DECISION size_warn=alert` здесь пишется только вызов `mark backup_size_warn` в полосе 40–50 МБ (обе границы включены; выше 50 МБ отметки нет — там сработает просрочка `backup_copy`); третью компоненту `mark` добавляет 06-02, алерт держит 06-06. Сбой этой отметки на код запуска не влияет — S4 этого не задаёт, принято здесь. При `log` ничего не пишется.
- Режимов отката в `backup-apply.sh` нет (S7): откат `cron` и `telegram` — удаление `/etc/cron.d/aggregator-backup` и `/etc/aggregator-backup/telegram.curl` командой `rm` в root-консоли отдельным разрешением владельца (06-04); слов подтверждения для отката в таблице раздела 2 нет.
