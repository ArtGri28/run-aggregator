# Phase 19: Usage Metrics — обсуждение

**Дата:** 2026-10-20
**Статус:** утверждено владельцем 2026-10-20: «Q-1…Q-4 по рекомендациям, схему утверждаю». Отчёт — отдельной командой `/activity`; `/stats` и его эталон не меняются.
**Основание:** владелец 2026-10-20: «Давай сделаем измерение удержания и как часто пользователи используют бот»; `.planning/research/NEXT-STEPS-2026-10.md`, идея 17.

## Что есть сейчас

- В `users` есть только `created_at` и `last_seen_at`. `last_seen_at` обновляется лишь при чтении и изменении фильтров (`touchUser`); открытие карточки, избранное и поиск его не трогают.
- Mini App в `users` не пишет ничего: её посещения сейчас не видны.
- По двум меткам времени можно посчитать «всего», «новых за 7 дней» и «последний раз заходили». Но нельзя узнать, сколько раз человек заходил, и нельзя отличить вернувшегося от того, кто зашёл один раз.

## Предлагаемые решения

- **D-01. Отметка «был сегодня».** На каждый апдейт пользователя в боте (`chatMW`) и на каждый запрос Mini App с проверенным `initData` в базу пишется одна строка «день — Telegram ID — бот / Mini App», не больше одной строки на человека в день. Что именно человек делал, не записывается.
- **D-02. Срок хранения — 90 дней**, как у заявок. Старые строки удаляет worker.
- **D-03. Счётчики действий — без Telegram ID**: за день хранятся только числа. Действия: поиск текстом, открытие карточки, добавление в избранное (отдельно для бота и Mini App), напоминание отправлено.
- **D-04. `/activity`** — отдельная команда только для администраторов (Q-4); `/stats` не меняется. Не администратор получает ответ неизвестной команды.
- **D-05. BOT-08 и PROJECT.md** дополняются фактом: «для подсчёта активности хранятся дни, когда пользователь открывал бота или Mini App (Telegram ID и дата), 90 дней». Экраны пользователя не меняются и ничего не обещают о данных.
- **D-06.** До выката истории нет: активность считается с первого дня после выката. Первую неделю цифры удержания неполные; экран пишет «с <дата>».

## Проект схемы (миграция `00012_usage.sql`, файл не создан)

```sql
-- +goose Up
CREATE TABLE user_days (
    day   DATE    NOT NULL,
    tg_id BIGINT  NOT NULL,
    bot   BOOLEAN NOT NULL DEFAULT false,
    app   BOOLEAN NOT NULL DEFAULT false,
    PRIMARY KEY (day, tg_id)
);

CREATE TABLE usage_counters (
    day    DATE    NOT NULL,
    metric TEXT    NOT NULL,
    n      INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (day, metric)
);

-- +goose Down
DROP TABLE usage_counters;
DROP TABLE user_days;
```

Запись: `INSERT … ON CONFLICT (day, tg_id) DO UPDATE SET bot = user_days.bot OR EXCLUDED.bot, app = …`. Счётчик: `… ON CONFLICT (day, metric) DO UPDATE SET n = usage_counters.n + 1`. Дата берётся в московском времени.

## Вопросы владельцу

- **Q-1. Ежедневные строки с Telegram ID (D-01).** Рекомендую. Без них нельзя посчитать ни «как часто заходят», ни «вернулись». Альтернатива — только счётчики без ID: видно «сколько заходило сегодня», а частоту и удержание не видно.
- **Q-2. Срок 90 дней (D-02)** — или другой?
- **Q-3. Список действий в D-03** — так оставить или что-то добавить или убрать?
- **Q-4. Раздел в `/stats` (D-04)** — или отдельной командой `/activity`, чтобы анкета осталась как есть? Рекомендую отдельную команду: эталон `stats.txt` тогда не меняется.

## Не входит

- графики и выгрузки;
- история по отдельному пользователю на экранах;
- метки источника входа (`?start=src_…`) — Phase 20 вместе с «Поделиться стартом».
