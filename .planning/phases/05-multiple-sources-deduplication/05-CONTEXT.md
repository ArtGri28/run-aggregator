## Implementation Decisions

### Уже зафиксировано до обсуждения (не пересматривать)
- ПроБЕГ — утверждённый второй источник (Phase 1, 01-SOURCES-REPORT §4.2): общий календарь `https://probeg.org/races/` по месяцам, `external_id` — число из `/event/<n>/`, Crawl-delay 30 с, `country_policy: no_fallback` (без определённой страны событие не создаётся).
- Контракт источника, прогон, оценка качества, защита первого прогона (D-05 Phase 3: первый прогон — `suspect`, принятие кнопкой или CLI), алерты и `/runs` (Phase 4) переиспользуются без изменений.
- Схема уже содержит `dedup_candidates` и `events.merged_into_id` (миграция 00001); выдача скрывает `merged_into_id IS NOT NULL`.
- REQUIREMENTS DDP-01…10 (кандидаты по стране и пересечению дат, схожесть названий в Go без `pg_trgm`, конфигурируемые пороги 0,7/0,4 как стартовая гипотеза, совпадение ссылки регистрации — только доп. сигнал, записи одного источника не склеиваются без `group_key`, дистанция не участвует в идентичности, слияние не удаляет `source_events`, цепочки схлопываются до корня, объединение дистанций с допуском по метрам).

### ПроБЕГ: страна и охват
- **D-01:** Страна определяется по **справочнику городов РФ в репозитории** (открытый источник — выбирает исследование, например ОКТМО/открытые данные). Город из строки есть в справочнике → RU; нет или неоднозначен → событие не создаётся (no_fallback), запись считается в счётчиках прогона. Отдельные запросы страниц событий не делаются. Одноимённые города других стран (Беларусь, Казахстан и т. п.) — через явный список исключений/неоднозначностей.
- **D-02:** Горизонт — **12 месяцев вперёд** (текущий + 11): 12 запросов за прогон, пауза между запросами ≥ 30 с (Crawl-delay), ~6 минут на прогон. Год даты восстанавливается по месяцу выборки.
- **D-03:** Еженедельные серии (паркраны, «5 вёрст» и подобные, отдельная запись на каждую дату) — **одно событие на ближайшую дату** серии. Нужен признак серии (`group_key` источника или правило распознавания); следующая дата заменяет прошедшую при следующих прогонах.
- **D-04:** Первый прогон ПроБЕГа — `suspect` и принимается вручную (как Марафонец), с санити-проверкой: сколько строк отсеяно по стране, сколько серий свёрнуто.

### Правила слияния
- **D-05:** Даты: **допуск ±1 день** для попадания пары в кандидаты `/dupes`; **автоматическое слияние — только при пересечении диапазонов дат** (с учётом многодневных).
- **D-06:** **Совпадение `city_key` обязательно для автослияния.** Разный или пустой город — максимум кандидат в `/dupes`.
- **D-07:** Поля слитого события — **по полю, первое непустое по приоритету источников**; приоритет задаётся конфигурацией (по умолчанию Марафонец выше ПроБЕГа: у него тип и ссылки регистрации). Дистанции — объединение (DDP-10), источники — все.
- **D-08:** **Автослияние выключено до калибровки**: пока на размеченном наборе не получено 0 ложных слияний (DDP-09), все пары выше нижнего порога идут в `/dupes`. Включается параметром конфигурации, без правки кода.

### `/dupes`, сводка, калибровка
- **D-09:** `/dupes` (только `ADMIN_TG_IDS`) показывает **по одному кандидату**: два события рядом (дата, город, название, дистанции, источник со ссылкой), оценка и сработавшие сигналы; кнопки [Слить] [Разные] [Пропустить]; после ответа — следующий кандидат в том же сообщении.
- **D-10:** [Слить] — **с подтверждением «Да, слить»** (как принятие прогона в 04-05). [Разные] — без подтверждения; отклонённая пара повторно не предлагается (DDP-07).
- **D-11:** Ежедневная сводка — **10:00 МСК, только если за сутки появились новые кандидаты**: число ожидающих и новых, кнопка [Открыть /dupes]. Время — в конфигурации.
- **D-12:** Калибровочный набор (30–50 пар): **черновик готовлю я** по реальным данным Марафонца и ПроБЕГа (явные дубли, одноимённые разные, пограничные) — файл в репозитории с предложенной меткой; **владелец проверяет и исправляет метки**. Файл становится тестом калибровки порогов. Историческая калибровка (05-07) выполнена на Марафонце и ПроБЕГе; «Лига Героев» (heroleague, D-22) в исходный набор не входила и должна пройти отдельную проверку (в том числе просмотр её пар в `would_auto`, D-21) до возможного включения автослияния.

### Решения после исследования (2026-09-30, ответы владельца на Open Questions 05-RESEARCH)
- **D-13:** Календарь ПроБЕГа берётся **одним запросом `https://probeg.org/races/year_ahead/`** (12 месяцев вперёд) вместо 12 помесячных запросов — уточнение механизма D-02, горизонт тот же. Год даты выводит `Parse` от `RawDoc.FetchedAt`.
- **D-14:** Еженедельные серии **без города не создаются** (строго по D-01), учитываются в счётчиках прогона и санити-отчёте.
- **D-15:** Строки «Забег отменён!» **пропускаются в `Parse`**; уже существующее событие уходит в missing/gone по обычной схеме. `SourceEvent.Status` не вводится.
- **D-16:** Старая кнопка слитого события **открывает корневое событие** (цепочка `merged_into_id` до корня).

### Решения по checkpoint планов (2026-10-01, владелец)
- **D-18 (05-01, option-a):** `SourceEvent.EndDate`/`GroupKey` — в конце структуры с `omitempty`, `Stats.Collapsed` — `json:",omitempty"`; payload, `content_hash` и golden Марафонца не меняются.
- **D-19 (05-05, schema-a):** `source_events.fields` — собственная структура store с явными snake_case-ключами (без status/id/служебных полей), неизвестные ключи при чтении игнорируются; миграция 00004 — по контракту outline.
- **D-20 (05-02/05-05, link-strict):** бонус совпадения ссылки регистрации меняет только score; автослияние требует `NameSim ≥ High` без бонуса. Уточнение (ревью): сортировка `/dupes` по оценке отложена в Phase 6, текущий порядок очереди — по id остаётся.

### Задел под пользовательские функции (2026-09-30, без изменения схемы)
- **D-17:** Три инварианта, чтобы будущие избранное/подписки/журнал изменений добавлялись отдельными таблицами без переделки:
  1. **Одна точка записи полей события:** любая запись канонических полей и дистанций `events` — обычный прогон, `Fold` по приоритету источников, `MergeEvents` — проходит через `saveEventTx` (`internal/store/events.go`). Там доступны старая и новая строка — будущий `event_changes` добавляется одним местом.
  2. **События не удаляются:** слияние только выставляет `merged_into_id`; приложение не выполняет `DELETE FROM events` (ни один код фазы). FK `events.merged_into_id` и `source_events.event_id` — `ON DELETE RESTRICT`; `event_distances` и `dedup_candidates` (миграция 00001) имеют `ON DELETE CASCADE`, который не срабатывает, пока события не удаляются.
  3. **Общий резолвер корня `store.RootEventID(ctx, id)`** (цепочка `merged_into_id` до корня) — используется D-16 и дедупликацией; будущие избранное и подписки резолвят через него при чтении, код слияния о них не знает.

### Решения по независимому ревью (2026-10-01, владелец)
- **D-23 (закрытие релиза, владелец, 2026-10-01):** текущий релиз завершается с ручным слиянием дублей через `/dupes`; `DEDUP_AUTO_MERGE=false` (вариант keep-off задачи 5 плана 05-08), задача 6 не выполняется. Приёмка трёх источников документируется по сохранённым логам `agg verify`. Реализация D-21 переносится в Phase 6 и остаётся обязательным условием включения автослияния. В Phase 6 также: дизайн и UX Telegram-бота (навигация, карточки забегов, пользовательский путь) и отложенные технические замечания ревью. Коммиты и деплой — только по отдельному согласованию.
- **D-25 (DDP-03, владелец, 2026-10-01):** DDP-03 принят как выполненный в состоянии «реализовано, откалибровано, выключено»: ветка автоматической связи есть в коде и тестах, в production `DEDUP_AUTO_MERGE=false` (D-23); её включение и проверка в production — Phase 6 после D-21.
- **D-24 (страны каталога: RU и BY, владелец, 2026-10-01):** агрегатор обрабатывает события России и Беларуси (реализовано коммитом `e8005e8` вне планов фазы).
  - Страна хранится в `events.country_code` (ISO alpha-2); отдельная миграция схемы не требуется — колонка и её CHECK есть с миграции 00001.
  - Беларусь входит в область обработки агрегатора: запись с явной страной BY попадает в каталог, фильтр выдачи по умолчанию — RU.
  - Ограничения по странам задаются на уровне источников: источник сам определяет страну записи и политику при её отсутствии (`Policy.CountryFallback`; у ПроБЕГа — `NoFallback` и справочник городов РФ, D-01). RU по-прежнему ставится только по субъекту РФ или справочнику, подмены страны нет.
  - Поддержка BY не означает автоматическую поддержку остальных стран: запись с любой другой явной страной остаётся `out_of_scope`; новая страна — только отдельным решением.
  - Фактическая реализация на HEAD `6d9efa3` (для сверки): общий список стран каталога — `allowedCountries = {RU, BY}` в `internal/normalize/country.go`, один на все источники; отдельного списка разрешённых стран у источника нет. Если ограничение должно быть именно пер-источниковым списком — это доработка кода, в этой фазе не выполняется.
  - D-01 (страна по справочнику городов РФ) и D-14 не меняются. Для BY-событий в правилах дедупликации отдельной калибровки не было; автослияние выключено (D-23).
- **D-21 (WouldAuto) — перенесено в Phase 6 (D-23), в этом релизе не реализуется:** потенциальные автослияния считаются независимо от `DEDUP_AUTO_MERGE`; сам флаг остаётся `false`, реальные слияния в этом релизе не включаются.
  - Расчёт: `Reasons.WouldAuto` (`json:"would_auto,omitempty"`) вычисляется в `Decide` по тем же условиям, что и автослияние: `NameSim ≥ High` без бонуса ссылки (D-20), пересечение дат (D-05), равный непустой `city_key` (D-06), `UniquePartner`. Вердикт `AutoMerge` возвращается только при включённом флаге и `WouldAuto`. При `false` ни одна пара не сливается. Инвариант (тест): для любой пары `AutoMerge` при включённом флаге ⇔ `WouldAuto` при выключенном. Строки `reasons` без поля читаются как `false`; схема БД не меняется.
  - Видимость: `/dupes` показывает признак «автослияние слило бы эту пару (сейчас выключено)»; лог `dedup pass` получает `would_auto=N` (слияния, которые выполнил бы проход при включённом флаге, с правилом «сторона — одно слияние»); `deploy-verify.sh` печатает `dedup_would_auto=pending:N|total_pending:M` и `dedup_pass_warn=N` (число `post-apply failed` за 24 часа — счётчик ошибок прохода).
  - DDP-09: тест полноты — каждая пара окна фикстур с вердиктом AUTO при включённом флаге обязана быть в `calibration.json` с подтверждённой меткой (`proposed=false`, `same`), иначе тест падает. Логика формирования пар — одна общая функция для `Pass` и теста (без дублирования).
  - Включение автослияния остаётся отдельным решением владельца (D-08) после просмотра всех `would_auto` пар на production.
- **D-22 («Лига Героев», `heroleague`):** источник (коммит `e8005e8`) остаётся в этом релизе; автослияние выключено.
  - Первый прогон отдельный: `suspect`, отдельный `sanity-report --source heroleague`, отдельное принятие baseline (кнопка или `accept-baseline --source heroleague`). Порядок: сначала ПроБЕГ и разбор `/dupes`, затем heroleague.
  - До принятия baseline источник не считается принятым: его события не попадают в каталог, а непринятый `suspect` повторяет алерт на каждый новый прогон — принятие не откладывать надолго.
  - Критерии приёмки (из плана ревью, уточняются при правке README и 05-08): `Valid` > 0; `Rejected` равно 0 или объяснено; страна у всех записей RU; `UnrecognizedRegion` ≤ 10 %; доля `out_of_scope` в общем пороге 20 % (иначе собственный `OutOfScopeMax` источника, как у ПроБЕГа).
  - Пары heroleague в калибровочный набор D-12 не входят: ещё одна причина держать автослияние выключенным и просматривать `would_auto` до его включения.
  - Изменения процедуры — отдельной правкой `deploy/README.md` и 05-08; здесь не вносятся.
- **Условия и оценки (ревью Phase 5):**
  - **L1:** количество администраторов проверить по строке `started` бота (поле `admins`; значение `ADMIN_TG_IDS` не читается). Если их больше одного — исправление до релиза: ожидаемая пара корней в callback и сверка в `ConfirmCandidate`. Результат проверки (2026-10-01): `admins=1` по строке `started` бота в сохранённых локальных логах `agg verify` (30.09 21:12; 01.10 10:42, 13:49, 13:55); значение `ADMIN_TG_IDS` не читалось. Решение: L1 отложен в Phase 6.
  - **L4** (`GroupKey` без места): оценивается отдельно при любом изменении формулы `GroupKey`. Пока ПроБЕГ не принят в production, смена бесплатна (меняет `content_hash` записей серий и golden ПроБЕГа); после принятия — разовый всплеск `changed`.
  - **M3:** расхождения `STATE.md`, `ROADMAP.md`, SUMMARY и `REQUIREMENTS.md` исправляются при подготовке изменений, без `phase.complete`.
- **Конфликты, выявленные ревью, — устранены правкой 2026-10-01** (решения D-12, D-17, D-20, D-21, D-22 по существу не менялись):
  1. Phase Boundary и Deferred: GET.RUN остаётся вне фазы; «Лига Героев» в релизе как третий источник (D-22).
  2. Phase Boundary: состав релиза — Марафонец, ПроБЕГ, «Лига Героев».
  3. D-12: калибровка 05-07 — Марафонец и ПроБЕГ; heroleague проверяется отдельно до возможного включения автослияния.
  4. D-20: сортировка `/dupes` по оценке отложена в Phase 6; очередь остаётся по id.
  5. D-17.2: уточнена формулировка про FK (CASCADE у `event_distances` и `dedup_candidates`, `DELETE FROM events` в приложении нет).
  6. `Status` обновлён на In Progress.
  7. Phase Boundary («MVP — только RU» в прежних формулировках, оговорка 4 в 05-SECURITY.md): каталог — RU и BY по D-24.
