## Summary

Phase 5 состоит из пяти независимых кусков: (1) адаптер ПроБЕГа; (2) справочник городов РФ и правки `normalize`; (3) чистое ядро дедупликации (нормализация, оценка, решение, конфиг); (4) слой хранения (слияние, кандидаты, сводка) + хук в `Runner`; (5) `/dupes`, сводка и долг Phase 4. Новых Go-зависимостей не нужно: HTML разбирает уже прямая зависимость `golang.org/x/net/html`, остальное — stdlib [VERIFIED: go.mod, `golang.org/x/net v0.59.0` в `require`].

Главное, что я выяснил на живых данных (я снял `robots.txt` и 3 страницы ПроБЕГа, а фикстуру Марафонца от 2026-09-29 прогнал через реальный `normalize.TitleNorm`): структура ПроБЕГа заметно отличается от того, что предполагали Phase 1 и CONTEXT — и это меняет план. Главные отличия: (a) есть страница `https://probeg.org/races/year_ahead/` — **весь год вперёд одним GET** (618 КБ, 379 строк), поэтому «12 запросов по месяцам» (D-02) не нужны, а URL конкретного месяца я не нашёл; (b) еженедельные серии уже свёрнуты сайтом в **групповые строки** — одна `<tr>` с десятками ссылок `/event/<n>/` через `<span>, </span>`, а у каждой недели **новый** `<n>` (пересечение id между субботами = 0); (c) у групповых строк город либо один на всю группу (и недостоверный: «Кронштадт» для 10 разных парков СПб), либо отсутствует вовсе (145 из 191 серии); (d) страна определяется не только справочником городов: в строке места **первый компонент — страна или субъект РФ** («Беларусь, …», «Московская область, …»), справочник нужен лишь для «голых» городов (163 из 364 одиночных строк); (e) `Runner.apply` → `SaveEventFor` после слияния будет **перезаписывать поля общего события данными то одного, то другого источника каждые 6 часов** — нужен пересчёт по приоритету (D-07) внутри `SaveEventFor`, иначе слияние бессмысленно; (f) глобальный порог `OutOfScopeMax = 0.20` даст ПроБЕГу `suspect` на каждом прогоне (оценка ≈ 28 %).

По дедупликации эмпирика на 364 одиночных строках ПроБЕГа × 133 Марафонца: пар в окне ±1 день — 3705; с оценкой триграммного Jaccard ≥ 0,7 — 76 (из них 46 с совпавшим `city_key`), в 0,4–0,7 — 66. Почти все совпавшие по городу пары выглядят настоящими дублями, но ≈ 1/3 пар выше порога идёт с **несовпавшим городом** (пригород, «пгт.»-префикс, «Вся Россия»): по D-06 они попадут только в `/dupes`. Эффективный лимит автослияния — порядка 46 пар из ≈ 60 настоящих дублей; на старте в очереди окажется ≈ 140 пар (из них 51 — шум одного события «Всероссийский … ЗаБег.РФ»), значит нужны ограничение кандидатов на событие и калибровка до включения ПроБЕГа в продакшн.

**Primary recommendation:** Брать ПроБЕГ одним GET `/races/year_ahead/` (требует подтверждения владельца как уточнение механизма D-02), сворачивать серии через `GroupKey` в `ingest.Prepare`, определять страну внутри `Parse` (первый компонент места + справочник RU-городов, результат — `SourceEvent.Country`); дедуп делать отдельным идемпотентным шагом `dedup.Pass` после успешной записи прогона (и после `Accept`), поля слитого события собирать внутри `SaveEventFor` из нового столбца `source_events.fields` по приоритету; `/dupes` и сводку строить по образцу `r:*` и `alert.Loop`.

### Ловушки дистанций (важно — иначе мусор в `event_distances`)

`normalize.Distances` ищет `число+единица` по всей строке. В ячейке ПроБЕГа после основной дистанции стоят скобки, которые дают ложные значения: `117,5 км (L120) (+6322м)` → лишние 6322 м (набор высоты); `… (Raccoon 3k)` → 3000 м; `5 км (старт 10-00)`; `2 км (Wedding Race)`; `триатлон, половинка (1,9 + 90 + 21,1)`; `скандинавская ходьба 5 км`, `прыжок в длину`, `толкание ядра`; `N часов`. Правило для `Parse`: на каждый `<span class="nobr">` брать **только текст до первой « (»**, отбрасывать элементы со словами «ходьба», «триатлон», «прыжок», «толкание», «каникросс» (решение — за планом; минимум — скобки) и склеивать через `, ` в `SourceEvent.Distances`. «полумарафон»/«марафон» отдельными словами `Distances` понимает сам (только если нет числовых) [VERIFIED: normalize/distance.go `namedDistances`].

### Серии (D-03) — как это устроено на самом деле

Групповая строка: в ячейке названия ≥ 2 ссылок `/event/<n>/` (после исключения ссылки «N человек»), разделённых `<span>, </span>`; у всех общая дата, общий текст города (или его нет) и дистанция `5 км`. **Каждая неделя — новые `<n>`** (пересечение id между 03.10 и 10.10/17.10/24.10 = 0 из 34/33/34 и 0 из 145) [VERIFIED: разбор снимка]. Серия видна горизонтально максимум на ~5 недель вперёд. Ключ серии = нормализованное название (`5 вёрст Бийск` одинаково каждую неделю; всего 191 различный заголовок: 46 в группах с городом, 145 без).

Рекомендация (prescriptive): `Parse` раскрывает групповую строку в записи по ссылкам и ставит `GroupKey = "series:" + normalize.TitleNorm(title)`; `ingest.Prepare` (общий код) оставляет для каждого непустого `GroupKey` **одну запись с ближайшей датой ≥ `today−1`**, остальные считает в новом `Stats.Collapsed` (не `Rejected`, не `Valid`). Так D-03 выполняется без состояния между прогонами: когда суббота прошла, в следующем прогоне ближайшей становится следующая запись с новым `external_id` (создаётся новое событие; прошлое остаётся в БД с прошлой датой, выдача его не показывает). `MarkSeen` для свёрнутых не нужен: их `source_events` не создавались.

Групповые записи **без города** (145 серий): по D-01 события не создаются — считаются `out_of_scope`. Город групповой строки у «Кронштадт» недостоверен: для групп с «федеральным» первым компонентом (`г. Санкт-Петербург, …`, `Москва`) рекомендуется ставить `City` = сам федеральный город, а не последний компонент (иначе пять вёрст в Колпино уйдут в `kronshtadt`). Это решение плана, не данных.

### Год даты (ловушка в общем `normalize.Date`)

Генерический `normalize.Date(dd.mm, now)` помещает дату в окно `[сегодня−1 мес, сегодня+11 мес)` [VERIFIED: internal/normalize/normalize.go, `yearFor`]. `year_ahead` покрывает ≈ 12 месяцев ⇒ записи за 11–12 месяцев вперёд (последняя в снимке — `07.09`, то есть 2027-09-07) получили бы прошлый год и молча стали бы «прошедшими» (`Expired`). Поэтому `Parse` сам выводит год по `doc.FetchedAt` (данные, а не часы: `RawDoc.FetchedAt` заполняет Fetcher) — **первое вхождение `dd.mm` на дату ≥ `FetchedAt−1 день`** — и отдаёт в `SourceEvent.Date` уже `dd.mm.yyyy` (формат понимает `normalize.Date`). Конец диапазона: тот же год, при `end < start` (декабрь→январь) +1 год. Граничный случай: событие ровно через 365 дней может получить прошлый год и отсеяться как `Expired`; на следующий день читается верно — допустимо.

### Влияние на D-02 (нужно подтверждение владельца)

D-02 формулирует цель («горизонт 12 месяцев») и механизм («12 запросов, ~6 минут»). URL месяца сайт не предоставляет; `year_ahead` даёт ту же цель за **один** GET (с большим уважением к Crawl-delay 30 с и без риска несогласованных срезов). Рекомендуется считать механизм уточнённым, но это решение владельца — см. «Вопросы» №1. Размер 618 КБ < `FETCH_MAX_BYTES` по умолчанию `MaxBytes: 10 << 20` [VERIFIED: internal/ingest/fetch.go:43]; Fetcher уже умеет `Get(ctx, url, crawlDelay)` как у Марафонца.

### Влияние на порог качества

Оценка по снимку: после сворачивания серий `valid` ≈ 364 + 191 = 555; `out_of_scope` ≈ 10 (Беларусь) + 145 (серии без города) = 155 ⇒ **≈ 28 %**, а `OutOfScopeMax: 0.20` по умолчанию [VERIFIED: internal/ingest/quality.go:45] ⇒ каждый прогон `suspect`. // Source: локальный прогон 2026-09-30 (рабочий код сравнения на реальных данных)
```go
func grams(s string) map[string]struct{} {
	r := []rune("  " + s + " ")
	m := make(map[string]struct{}, len(r))
	for i := 0; i+3 <= len(r); i++ {
		m[string(r[i:i+3])] = struct{}{}
	}
	return m
}
func jaccard(a, b string) float64 {
	A, B := grams(a), grams(b)
	in := 0
	for k := range A {
		if _, ok := B[k]; ok {
			in++
		}
	}
	if u := len(A) + len(B) - in; u > 0 {
		return float64(in) / float64(u)
	}
	return 0
}
```

### Оценка и решение (предлагаемая схема — конфигурируема)

### Почему нужен `source_events.fields` (главная архитектурная находка)

`Runner.apply` на каждом прогоне вызывает `SaveEventFor(ctx, id, &p.Event)` для **каждой** валидной записи; для связанной записи он **перезаписывает** `events` значениями этой записи (сохраняя только `status`) [VERIFIED: internal/store/events.go `SaveEventFor`, ветка `else`]. Комментарий в коде прямо откладывает проблему на эту фазу: «Choosing fields by source priority when an event has several source_events is Phase 5's job». После слияния Марафонец и ПроБЕГ будут по очереди (раз в 6 ч) затирать общее событие своими полями, `updated_at` дёргается, счётчик `Changed` растёт. Решение: внутри `SaveEventFor`

1. сохранить в `source_events.fields` нормализованные поля этой записи (JSON от `event.Event` без ID/дат создания) — в той же транзакции;
2. прочитать `fields` всех связанных строк события (`state <> 'gone' AND match_state <> 'out_of_scope'`, упорядочив по приоритету кодов источников);
3. если строк > 1 — подставить `event.Fold(...)` вместо `e`; далее прежний `saveEventTx`.

`Fold` (чистая, в `internal/event`): по полю — первое непустое по приоритету; **пары, зависящие друг от друга, идут из одного источника**: (`title`, `title_norm`), (даты `start_date`/`end_date`), (`region`, `city`, `city_key`, `timezone`); `event_type` — первое **не `other`** (`other` — это «пусто» после `normalize.Type`); `status` — как сейчас, из БД; дистанции — объединение с допуском `DEDUP_DISTANCE_TOL_M` (по умолчанию 100 м [ASSUMED]): элемент добавляется, если в уже взятых нет значения в пределах допуска; метка — от первого. Приоритет `priority []string` передаётся в `SaveEventFor` параметром (из `Runner.Priority`), а не глобально.

Для существующих 133 строк Марафонца `fields` = NULL до первого прогона нового образа (`apply` пишет каждую запись каждый раз) — порядок выката обязан это учесть (см. Q7). `Fold` пропускает строки без `fields`; `Pass` пары с такими строками не оценивает.

### Шаг `dedup.Pass` (идемпотентный, отдельная транзакция)

Решение **не** встраивать в транзакцию записи прогона: ошибка дедупа не должна делать здоровый прогон `failed`/откатывать каталог; следующий прогон или `Accept` просто повторит шаг. Подключение: необязательное поле `Runner.PostApply func(ctx context.Context) error` (nil в тестах), вызываемое после успешного `finish` в `Run` и после `Accept`; `newRunner` в `cmd/aggregator/main.go` устанавливает его одинаково для `worker` и `bot` (тот же приём, что Pitfall 11). Ошибка хука логируется, прогон остаётся `ok`.

Алгоритм (полная перестройка допустима: каталог — сотни событий, окно дат сортируется):
1. `pg_advisory_xact_lock(<константа>)` — прогоны источников идут в разных горутинах [VERIFIED: `Runner.Loop` запускает горутину на источник]; два `Pass` не должны пересекаться.
2. Загрузить корневые события (`merged_into_id IS NULL`) с `start_date ≥ today−1` со множеством источников (`source_id`, `group_key`), ссылкой регистрации и дистанциями.
3. Пары в окне ±1 день по стране; для каждой — правило источников, оценка, решение.
4. Авто (если включено и разрешено): `store.MergeEvents` последовательно, карта корней обновляется в памяти.
5. Кандидаты: upsert в `dedup_candidates` (`ON CONFLICT (source_event_id, event_id) DO UPDATE SET score, reasons WHERE state = 'pending'`); устаревшие `pending` (пара больше не проходит или событие слито) удаляются.
6. Включение автослияния конфигом: следующий `Pass` сам промотирует `pending`-пары, удовлетворяющие правилам авто (`decided_by = NULL`).

### Идентичность пары и «не предлагать повторно» (DDP-07)

Строка кандидата — это `(source_event_id, event_id)`, а объектов сопоставления два события. Договорённость: `event_id` — старшее (меньший id) корневое событие B, `source_event_id` — минимальный `source_events.id` у события A (A — кандидат на поглощение). Пара считается отклонённой, если существует строка `state = 'rejected'`, у которой **корни** `{COALESCE(e.merged_into_id, e.id)}` событий `source_events.event_id` и `event_id` совпадают с корнями проверяемых A и B. Цепочки схлопнуты до одного шага (DDP-06), поэтому корень — одно `COALESCE`. Побочный эффект: после отклонения A↔B и последующего легитимного слияния A с C пара (A∪C, B) остаётся заблокированной — консервативно, и это надо записать в ограничениях.

### `store.MergeEvents(ctx, loserID, winnerID, matchState, decidedBy, priority)` (одна транзакция)

1. Заблокировать `source_events WHERE event_id IN (loser, winner) ORDER BY id FOR UPDATE`, затем `events … ORDER BY id FOR UPDATE` — **тот же порядок, что в `SaveEventFor`** (сначала `source_events`, потом `events`), иначе тупик при параллельной записи прогона.
2. Проверить: оба события корневые и различны; иначе `ErrNotMergeable`.
3. `UPDATE source_events SET event_id = winner, match_state = <'auto'|'manual'> WHERE event_id = loser` (строки не удаляются — DDP-06).
4. `UPDATE events SET merged_into_id = winner, is_listed = false WHERE id = loser`; `UPDATE events SET merged_into_id = winner WHERE merged_into_id = loser` (схлопывание цепочки).
5. Пересобрать поля победителя через `event.Fold` (и `replaceDistances`).
6. Кандидаты: строки пары → `confirmed` (`decided_at`, `decided_by`), остальные `pending` с участием проигравшего удалить.
Победитель — корневое событие с меньшим `id` (стабильные ссылки бота); направление не зависит от приоритета источников — приоритет действует на поля, не на идентичность.

### Карточка слитого проигравшего

`onCard` отдаёт «недоступно» для `MergedIntoID != nil` [VERIFIED: internal/bot/list.go `case !e.IsListed || e.MergedIntoID != nil`]. MVP §4.5 хочет, чтобы старые ссылки не ломались; дешёвое улучшение — открыть корень вместо `goneScreen` (решение плана).

**Формат (рекомендация).** `internal/dedup/testdata/calibration.json` — массив записей, адресующих события **по ключам источника**, а не по id БД:

`label` ∈ `same | different`; `proposed: true` — метка предложена мной, владелец меняет на `false` после проверки. Тест `TestCalibration` (без БД) строит события из двух зафиксированных фикстур (`marathonec/testdata/calendar-beg.html` + `probeg/testdata/…`) через `Parse`+`Prepare` (оба пакета импортируются **только из `_test.go`**), считает `Score`/`Decide` при конфиге по умолчанию и утверждает: (1) ни одна пара `different` не получает решение «авто»; (2) каждая `same` достигает как минимум «кандидат»; (3) печатает матрицу ошибок для подбора порогов. ### Pattern 1: страна внутри `Parse`, а не «молчаливый fallback»
**What:** `Parse` знает вёрстку места и справочник, поэтому сам заполняет `SourceEvent.Country = "Россия"` (или оставляет пусто). Политика источника остаётся `NoFallback`.
**When to use:** ПроБЕГ; не меняет общий `Prepare`/`Country`.
```go
// Source: adapted from normalize.Country (internal/normalize/place.go) — пример логики, не готовый код
func resolvePlace(raw string) (region, city, country string) {
	parts := splitTrim(raw) // по «,» с учётом NBSP
	if len(parts) == 0 { return }
	city = normalize.City(parts[len(parts)-1])
	switch canon, kind := normalize.ClassifyRegion(parts[0]); kind {
	case normalize.RegionForeign:
		return parts[0], city, ""        // Prepare отнесёт к out_of_scope как foreign
	case normalize.RegionRF:
		return canon, city, "Россия"
	}
	if normalize.IsRFCity(city) {       // новая функция; ambiguous → false
		return "", city, "Россия"
	}
	return "", city, ""                 // NoFallback ⇒ out_of_scope
}
```

### Pattern 2: сворачивание серий по `GroupKey` в общем `Prepare`
**What:** записи с одинаковым непустым `GroupKey` в одном прогоне → остаётся одна с ближайшей датой ≥ `today−1`; остальные — в `Stats.Collapsed`. Одновременно это единственный легальный способ склейки внутри источника (DDP-05).

### Pattern 3: слияние через «Fold при записи», а не «пост-исправление»
См. Q4. Альтернатива «SaveEventFor затёр, `Pass` вернул» даёт двойную запись с `updated_at`/`Changed` на каждом прогоне и нарушает ING-05.

### Pattern 4: `/dupes` как `r:*`
Админ-проверка в каждом обработчике, подтверждение второй кнопкой, `b.show` для редактирования того же сообщения, `answerCallbackQuery` через общий `b.cb`.

### Anti-Patterns to Avoid
- **Менять общий `yearFor`/`normalize.Date` под ПроБЕГ** — ломает тесты Phase 2 и другие источники; год считает `Parse`.
- **Брать город групповой строки как город события** без оговорки — «Кронштадт» для всех парков СПб.
- **Делать `dedup.Pass` частью транзакции прогона** — сбой дедупа превратит здоровый прогон в `failed`.
- **Хранить в `title_norm` специальную нормализацию дедупа** — `title_norm` детерминирован от `title` (MVP §6) и индексируется как раз так.
- **Использовать сам хост+путь регистрации как условие авто-слияния** (DDP-04).
- **Вычислять метрику по байтам** — кириллица многобайтовая.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| HTML-таблица | регулярки по `<tr>` | `golang.org/x/net/html` (как `marathonec/parse.go`) | вложенные теги, стрей-`</a>`, `&nbsp;` |
| Сравнение пар в БД | `pg_trgm`/SQL-схожесть | Go-функция + выборка окна | запрещено DDP-02; SQL только в `store` |
| Поиск цикла слияния | рекурсивный CTE | `COALESCE(merged_into_id, id)` | цепочки схлопнуты (DDP-06) |
| Конфиг из env | ещё один парсер | `setValue`-образец из `ingest/config.go` | уже обрабатывает `Duration`/`float64`/`int`, не печатает значение |
| Повторный цикл по расписанию | свой планировщик | копия скелета `alert.Loop.Run` | проверенные отмена и тики |
| Блокировка пересекающихся `Pass` | флаги в памяти | `pg_advisory_xact_lock` | два процесса (`bot` — `Accept`, `worker`) |
| Тестовая БД | моки `store` | `storetest.Open` (реальный PostgreSQL 17) | как во всех фазах [VERIFIED: internal/store/storetest] |
| Даты/время | свой календарь | `time` + `time.FixedZone`/`LoadLocation("Europe/Moscow")` | `time/tzdata` уже импортирован в `main.go` |

**Key insight:** «одинаковое соревнование» в двух источниках записано по-разному в названии, городе и датах, поэтому ценность даёт не сложная метрика, а аккуратные ворота (страна, окно дат, непересечение источников, город для авто) и отсекатели шума (`MAX_PER_EVENT`, ≤ 1 партнёр ≥ high).

## Common Pitfalls

### Pitfall 1: Год в датах без года у края горизонта
**What goes wrong:** `normalize.Date` кладёт `dd.mm` в окно −1/+11 месяцев; событие через 11–12 месяцев получает прошлый год и исчезает как `Expired`.
**Why:** окно рассчитано на «на месяц вперёд».
**How to avoid:** год выводит `Parse` по `FetchedAt` (первое вхождение ≥ `FetchedAt−1 день`), в `Date` уходит `dd.mm.yyyy`; end < start ⇒ +1 год.
**Warning signs:** `expired` у ПроБЕГа заметно больше нуля; последние строки `year_ahead` (июль–сентябрь) пропадают.

### Pitfall 2: Ссылка «N человек» принимается за событие или название
**What goes wrong:** в каждой обычной строке две ссылки `/event/<n>/` (название и «Планирует участвовать … 1 человек»); счётчик «групповой строки» по числу ссылок даёт 107 ложных групп из 181.
**How to avoid:** название — первая ссылка; группа — ≥ 2 ссылок **после** исключения ссылок с текстом `^\s*\d+ человек`; опирайтесь на `<span>, </span>`.

### Pitfall 3: Ложные дистанции из скобок
**What goes wrong:** `(+6322м)`, `(Raccoon 3k)`, `(старт 10-00)`, `скандинавская ходьба 5 км` попадают в `event_distances`.
**How to avoid:** брать текст span до « (»; фильтровать неходовые виды; golden-тест на реальных значениях из снимка.

### Pitfall 4: Город групповой строки
**What goes wrong:** у 145 из 191 серий города нет (строка `colspan=2`), у остальных он один на всю группу и недостоверен.
**How to avoid:** без города ⇒ out_of_scope (D-01); для групп с федеральным первым компонентом использовать сам федеральный город; считать оба случая в санити-отчёте.

### Pitfall 5: `OutOfScopeMax = 0.20` ⇒ `suspect` навсегда
**What goes wrong:** ≈ 28 % записей ПроБЕГа вне каталога по построению ⇒ каждый прогон в `suspect`, каталог не обновляется.
**How to avoid:** `Policy.OutOfScopeMax` для ПроБЕГа (или явно поднятый env); проверить на первом реальном прогоне.

### Pitfall 6: Ни один источник не «владеет» слитым событием
**What goes wrong:** `SaveEventFor` на каждом прогоне затирает общее событие полями текущей записи.
**How to avoid:** `fields` + `Fold` внутри `SaveEventFor` (Q4). Регрессионный тест: два прогона двух источников подряд оставляют `updated_at` и счётчик `Changed` равными 0 на втором проходе.

### Pitfall 7: Дубль-канон из-за префиксов поселения
**What goes wrong:** `пгт.`, `п.г.т.`, `c.` (латинская) не снимаются ⇒ `city_key` `pgt-nyrob` ≠ `nyrob` ⇒ D-06 запрещает авто, хотя это один и тот же город.
**How to avoid:** расширить `cityPrefixes`; добавить тест-таблицу на реальных написаниях.

### Pitfall 8: Стоп-слова делают разные события одинаковыми
**What goes wrong:** `TitleNorm` удаляет `марафон`/`полумарафон`/`забег`; «Саратовский марафон» и «Саратовский полумарафон» (того же дня, города) дадут 1,00. Формально это, скорее всего, одно и то же событие-уикенд, но возможны разные.
**How to avoid:** включить в калибровочный набор жёсткие негативы такого вида; при необходимости штраф за конфликт формата-маркера (`марафон` против `полумарафон`) только в названии — не по дистанциям (DDP-05).

### Pitfall 9: Шум одного события и дубли внутри источника
**What goes wrong:** «Всероссийский … ЗаБег.РФ» порождает ≈ 51 пару; в ПроБЕГе есть настоящий внутренний дубль («Беговая забава»).
**How to avoid:** `DEDUP_MAX_PER_EVENT`, правило «≤ 1 партнёр ≥ high» для авто, отказ пар с общим источником.

### Pitfall 10: Два `Pass` одновременно и тупик блокировок
**What goes wrong:** воркер и бот (`Accept`) вызывают `Pass`; `MergeEvents` лочит в другом порядке, чем `SaveEventFor`.
**How to avoid:** `pg_advisory_xact_lock`; порядок блокировок: `source_events` → `events`, по возрастанию id.

### Pitfall 11: Сводка шлётся повторно или не шлётся
**What goes wrong:** без сохранённого состояния перезапуск в 10:30 шлёт дважды; без `notified_at` — каждое утро про одно и то же.
**How to avoid:** условие по `MAX(notified_at)`, запись только после успешной отправки.

### Pitfall 12: Включение автослияния «задним числом»
**What goes wrong:** после `DEDUP_AUTO_MERGE=true` уже накопленные `pending` остаются в очереди.
**How to avoid:** `Pass` промотирует `pending`-пары, удовлетворяющие правилам авто (решение закреплено в Q4).

### Pitfall 13: Конфиг не доходит до контейнеров
**What goes wrong:** переменная в `.env` есть, но в `docker-compose.yml` её нет ⇒ сервис использует умолчания; `bot` и `worker` рассинхронизируются по порогам/приоритету.
**How to avoid:** добавить `DEDUP_*` в оба сервиса одним изменением; тест/скрипт сверки не нужен — достаточно проверки в плане.

```go
// Название: первая <a href="/event/N/"> в ячейке №3; ссылки «N человек» не считаются.
var participantsRe = regexp.MustCompile(`^\s*\d+\s+человек`)

func titleLinks(td *html.Node) (links []link) {
	for n := range td.Descendants() {
		if isElem(n, atom.A) && strings.HasPrefix(attr(n, "href"), "/event/") {
			if txt := text(n); !participantsRe.MatchString(txt) {
				links = append(links, link{id: eventID(attr(n, "href")), title: strings.TrimSpace(txt)})
			}
		}
	}
	return
}
```

### Решение по паре (чистая функция)
```go
// Source: правила D-05, D-06, D-08, DDP-03…05 (проект)
type Verdict int
const (
	Separate Verdict = iota // < low
	Candidate
	AutoMerge
)
func Decide(p Pair, c Config) (Verdict, Reasons) {
	if !p.SourcesDisjoint || p.Country != p.Other.Country || !p.DatesWithin(1) {
		return Separate, nil
	}
	s := p.NameSim
	if p.LinkMatch && s >= c.Low { s = min(1, s+c.LinkBonus) }
	switch {
	case s < c.Low:
		return Separate, nil
	case c.AutoMerge && s >= c.High && p.DatesOverlap &&
		p.CityKey != "" && p.CityKey == p.Other.CityKey && p.UniquePartner:
		return AutoMerge, reasons(p, s)
	}
	return Candidate, reasons(p, s)
}
```

## Open Questions

1. **D-02: один GET `/races/year_ahead/` вместо 12 запросов по месяцам — согласен ли владелец?**

   - Known: D-01 однозначен (без города события нет).
   - Recommendation: оставить; санити-отчёт показывает число.
3. **Статус «Забег отменён!» из ПроБЕГа (2 строки):** вводить `SourceEvent.Status`?
   - Known: `SaveEventFor` сохраняет статус из БД и источником не меняется (MVP: только явный статус источника).
   - Recommendation: да, аддитивное поле + правило «явный `cancelled` от источника применяется»; иначе отменённые забеги покажутся обычными. Можно отложить, но тогда зафиксировать как известное ограничение.
4. **Состав `ru_cities_ambiguous.txt` и включать ли регион во вторую колонку справочника.** Recommendation: начать с 6–8 очевидных имён; регион — опционально.
5. **Поведение `onCard` для слитого проигравшего:** показывать корень или «недоступно»? Recommendation: корень (MVP §4.5).
6. **Сигнал «Сайт» из ПроБЕГа как резервная ссылка регистрации?** Recommendation: нет (это сайт организатора, не регистрация); использовать только ссылку «Регистрация».

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |

| V5 Input Validation | **yes** | строгий `parseCallback` (id — `num`, без ведущих нулей, ≤ int64); HTML источника — недоверенные данные (`x/net/html`, лимит `MaxBytes`); выход в Telegram — `plain`, усечение `cut`, без `parse_mode` |

### Known Threat Patterns for {Go + PostgreSQL + Telegram bot + HTML scraping}

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Подделка `d:y:<id>` не-админом | Spoofing / Elevation | `isAdmin(q.From.ID)` в `onDupe` на каждом вызове (по образцу `onRun`) |
| Необратимое слияние по ошибочному клику | Tampering | подтверждение «Да, слить» (D-10), авто выключен до калибровки (D-08), `decided_by/decided_at`, `source_events` не удаляются (откат — ручной SQL) |
| Гонка: двойное нажатие / два админа | Tampering | статус `pending` проверяется внутри транзакции `MergeEvents`, advisory-lock на `Pass` |
| SQL-инъекция | Tampering | только параметризованный pgx, SQL только в `internal/store` |
| Инъекция текстом названия в сообщение (разметка, ссылки) | Tampering / Info | `plain`-режим, `cut`, URL только из проверенных ссылок (`validURL`) |
| Вредоносная/раздутая страница источника | DoS | `FETCH_MAX_BYTES` (10 МиБ), таймауты Fetcher; структура проверяется по селекторам, а не по словам; `ErrStructureNotFound` ⇒ `failed` |
| Перегрузка сайта источника | (этика/надёжность) | один GET на прогон, интервал 6 ч, Crawl-delay 30 с, UA с контактом владельца (контакт в репозиторий/логи не попадает) |
| Раскрытие секретов в фикстуре | Info | из снимка убран csrf-токен формы; `sanity`: проверить остальные значения как в README Марафонца |
