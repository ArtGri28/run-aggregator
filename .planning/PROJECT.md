# Telegram-бот — агрегатор забегов

## What This Is

Telegram-бот, который регулярно собирает соревнования по бегу из нескольких источников, приводит их к единому формату, находит дубли и даёт единый поиск. Пользователь ищет забеги по дате, городу, дистанции и типу, не заходя на множество сайтов, и переходит по ссылке на регистрацию. Pet-project для одного владельца; MVP работает только с соревнованиями в России (`country_code = RU`), но модель данных международная: каноническое событие содержит `country_code`, `region` и `city`.

Подробный зафиксированный план — `MVP.md` в корне проекта. Он **источник истины**: при расхождении с этим файлом прав `MVP.md`.

## Core Value

Полный, актуальный и без дублей каталог забегов. Ценность проекта — качество данных (полнота, актуальность, нормализация, отсутствие дублей, стабильность сбора), а не количество функций бота.

### Out of Scope

- Redis, Kafka, Elasticsearch, OpenSearch, PostGIS, Kubernetes — преждевременная инфраструктура, PostgreSQL достаточно
- Prometheus и Grafana — хватает логов, `ingest_runs` и алертов в Telegram
- Mini App, веб-админка, рекомендации, автоматическая регистрация на забег — вне ядра ценности
- Несколько стран — модель международная, но данные и интерфейс только Россия
- Цена, `registration_status`, `lat/lon`, геокодинг, поиск по радиусу — ненадёжные или пока бесполезные данные; добавляются отдельными миграциями
- История изменений, избранное, пользовательские уведомления — отложено после MVP
- ML-сопоставление и эмбеддинги — ручная очередь достаточна на масштабе MVP
- Копирование изображений и больших текстов источников, сбор данных участников — права и персональные данные
- Обход CAPTCHA и антибот-защиты — не проектируется; источник с такой защитой заменяется
- CI — не входит в MVP

## Context

- **Проблема:** информация о забегах разбросана по многим сайтам.
- **Кандидаты в источники:** GET.RUN, Runlist, Марафонец. Не утверждены: нужна проверка доступности с VPS, `robots.txt`, ToS, API и структуры (Phase 1). Цель — 2–3 качественных источника, а не именно эти три.
- **VPS владельца:** Варшава, 4 vCPU AMD EPYC, 4 ГБ RAM, 30 ГБ NVMe, Ubuntu Server 24.04, 300 Мбит/с. Считается достаточным для MVP, заранее не увеличивается. Telegram API с него доступен.
- **Находки аудита VPS:** нет плагина `docker compose`; `tinyproxy` слушает на всех интерфейсах (не входит в проект, менять только с отдельного подтверждения); часы не синхронизированы; нет swap; ожидается перезагрузка и обновления (не выполнять без разрешения).
- **Главные риски:** доступность российских сайтов с зарубежного IP, поломки парсеров при изменении вёрстки, ложные слияния разных событий, рост диска из-за `payload`.
- **Репозиторий и Git:** приватный удалённый репозиторий создаёт владелец. Политика Git (решение владельца): `commit_docs = true`; GSD и исполнитель самостоятельно делают коммиты (артефактов, кода, миграций, Docker и остальных файлов проекта); обычный push разрешён в remote этого проекта; force-push, `reset --hard`, удаление веток и remote возможны только с отдельного подтверждения; теги отключены; в сообщениях коммитов нет упоминаний ИИ.

## Constraints

- **Tech stack**: Go 1.27.1, PostgreSQL 17, `pgx/v5` + `pgxpool`, `goose`, `go-telegram/bot`, остальное стандартная библиотека — минимум зависимостей; новые только с явного одобрения
- **Архитектура**: один бинарник (`bot`, `worker`, `migrate`, `healthcheck`), без слоя `usecase`, весь SQL в `internal/store` — простота
- **Инфраструктура**: Docker Compose (`postgres`, `bot`, `worker`) на одном VPS, long polling, без webhook и reverse proxy — достаточно для MVP
- **Данные**: `Parse` — чистая функция; `suspect` и `failed` прогоны ничего не применяют; `gone` никогда не означает `cancelled` (`events.status` и состояние наблюдения `source_events` независимы); `country_code = RU` только по правилам из `MVP.md` (явное значение источника, fallback `RU` для источника — кандидата, признанного Phase 1 и подтверждаемого санити-проверкой в Phase 3, иная страна — `out_of_scope`); описание не длиннее 1000 символов, изображения не сохраняются — защита каталога от порчи
- **Безопасность**: секреты только в окружении, не в репозитории и документации; данные пользователей — только Telegram ID и настройки поиска
- **Системные изменения на VPS**: только с отдельного разрешения владельца (обновление, перезагрузка, установка пакетов, swap, `tinyproxy`); `unattended-upgrades` не входят в MVP
- **Доступ к VPS**: инструменты запускают только read-only блоки Phase 1 через обёртку `run_block.sh` с отдельным ключом проекта; блоки утверждает владелец, при ошибке остановка, секреты не печатаются; любые изменения VPS только по отдельному разрешению (`MVP.md` §7.4, решение 33) — безопасность
- **Юридические и технические**: `robots.txt`, ToS, rate limits проверяются до подключения каждого источника; не собирать данные участников; описания до 1000 символов
