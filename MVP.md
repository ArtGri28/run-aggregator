# MVP: Telegram-бот — агрегатор забегов

**Статус:** зафиксировано, источник истины для GSD (`PROJECT.md`, `REQUIREMENTS.md`, `ROADMAP.md`)
**Дата:** 2026-09-25
**Как менять:** только осознанно, с записью в разделе «Журнал решений». Всё, что здесь не описано, в MVP не входит.

---

## 1. Цель и проблема

Информация о соревнованиях по бегу разбросана по многим сайтам, пользователю приходится искать забеги на каждом отдельно.

**Решение.** Telegram-бот регулярно собирает соревнования из нескольких источников, приводит их к единому формату, находит дубли и даёт единый поиск.

**Ключевой принцип.** Ценность проекта не в количестве функций бота, а в качестве каталога:
1. полнота;
2. актуальность;
3. качество нормализации;
4. отсутствие дублей;
5. стабильность сбора данных.

Архитектура в первую очередь обеспечивает качество данных. Когда решение для бота и решение для данных конфликтуют, выигрывают данные.

## 2. Scope

### 2.1 Входит в MVP
- Сбор данных из **2–3 качественных источников** (кандидаты: GET.RUN, Runlist, Марафонец; окончательный выбор после Phase 1, см. раздел 7).
- Единая нормализованная модель, **соревнования в России и Беларуси** (D-24 Phase 5; остальные страны — вне MVP), но модель международная (`country_code`, `region`, `city`).
- Дедупликация между источниками с очередью потенциальных дублей.
- Поиск в Telegram: дата, город, дистанция, тип; список, карточка, пагинация.
- Ссылка на регистрацию и ссылки на источники в карточке.
- Админ-команды `/dupes` и `/runs`, доступные только `ADMIN_TG_IDS`.
- Наблюдаемость: `ingest_runs`, проверки качества прогона, структурные логи, heartbeat; алерты админу в Telegram появляются с Phase 4, когда существует бот.
- Бэкапы с шифрованием и проверкой восстановления, runbook.

### 2.2 Типы забегов
`road` (шоссе), `trail` (трейл), `cross` (кросс), `track` (стадион), `obstacle` (OCR), `other`.
**Ultra не тип.** Это свойство дистанции: событие имеет ультра-дистанцию, если `max(distance_m) > 42195`. Выводится запросом.

### 2.3 Не входит (non-goals)
Redis, Kafka, Elasticsearch, OpenSearch, PostGIS, Kubernetes, Prometheus и Grafana, Mini App, микросервисы, ML-сопоставление и эмбеддинги, веб-админка, рекомендации, автоматическая регистрация на забег, страны кроме России и Беларуси, цены и `pricing`, `registration_status`, `lat/lon`, геокодинг, поиск по радиусу, история изменений (`event_changes`), избранное, пользовательские уведомления, копирование изображений и больших текстов источников, CI, отдельные таблицы стран, регионов, городов и типов, webhook и reverse proxy.

Если discovery покажет, что что-то из этого абсолютно необходимо для базовой работы, решение принимается явно и записывается в журнал.

## 3. Архитектура

```
Telegram ⇄ Bot (long polling) ──► store ──► PostgreSQL ◄── store ◄── Worker
                                                                        ▲
                             Scheduler → Fetch → RawDoc → Parse → SourceEvent
                                              → Validate → Normalize → Match ─┘
                                        (сайты-источники, каждый в своём пакете)
```

- **Bot** не ходит на сайты, **Worker** не зависит от Telegram (кроме алертов админу). Общее — только PostgreSQL.
- **PostgreSQL** единственное основное хранилище (**PostgreSQL 17**).
- **Один бинарник, подкоманды:** `bot`, `worker`, `migrate`, `healthcheck`. Один Docker-образ, разные `command`.
- **Слоя `usecase` нет.** `internal/store` — единственное место с SQL. Интерфейсы объявляются на стороне потребителя и только там, где нужны для тестов. Слои и абстракции добавляются, когда появляется реальная сложность, а не заранее.

### 3.1 Стек
| Что | Решение | Примечание |
|---|---|---|
| Язык | **Go 1.27.1**, зафиксирован в `go.mod` и в production Docker-образе | |
| БД-драйвер | `pgx/v5` + `pgxpool` | `sqlc` не используем, пока запросов не станет заметно больше ~50 |
| Миграции | `pressly/goose` | SQL-файлы, `embed.FS`, запуск подкомандой `migrate` |
| Telegram | `go-telegram/bot` | long polling через `b.Start(ctx)`, роутинг `WithCallbackQueryDataHandler` с `MatchTypePrefix`, типизированные ошибки API |
| Логи | `log/slog` | стандартная библиотека |
| HTTP, JSON, embed | стандартная библиотека | |
| Планировщик, rate limiter, конфиг | **стандартная библиотека** (цикл с тикером, затвор с `time.Sleep`, `os.Getenv`) | отдельные библиотеки не добавляем |
| HTML-парсер | **не добавляем**, пока первый источник не потребует HTML-парсинга; тогда решение принимается отдельно (`golang.org/x/net/html` или `goquery`) | |

Новая зависимость без явного одобрения не добавляется.

### 3.2 Структура проекта
```
cmd/aggregator/main.go       подкоманды: bot | worker | migrate | healthcheck
internal/
  event/        домен: Event, Distance, Filter, Status, Type
  store/        pgx, весь SQL, embed-миграции
  ingest/       scheduler, runner, fetch (rate limit, retry), проверки прогона
    sources/<name>/          Fetch + Parse, testdata/ с golden-файлами
  normalize/    название, город (словарь), дата, дистанция, часовой пояс
  match/        кандидаты, схожесть, пороги
  bot/          роутер, экраны, клавиатуры, кодек callback
  alert/        уведомления админу
migrations/
```
Структура рабочая, не догма: пакеты объединяются или делятся по факту.

## 4. Модель данных

### 4.1 Таблицы
```
sources(id, code UNIQUE)              приоритеты и интервалы источников — в коде

ingest_runs(id, source_id, started_at, finished_at,
            status: running|ok|suspect|failed,
            fetched, parsed, rejected, out_of_scope, upserted, error)

source_events(id, source_id, external_id, url, payload jsonb, content_hash,
              first_seen_at, last_seen_at,
              state: active|missing|gone, missed_runs,
              event_id NULL, match_state: new|auto|manual|candidate|out_of_scope,
              last_run_id,
              UNIQUE(source_id, external_id))

events(id, title, title_norm,
       start_date NOT NULL, end_date NULL, start_time NULL, timezone NULL,
       country_code, region NULL, city NULL, city_key NULL, address NULL,
       event_type, status: scheduled|cancelled|postponed,
       description NULL (≤1000 символов), registration_url NULL,
       is_listed, merged_into_id NULL, created_at, updated_at)

event_distances(event_id, distance_m INTEGER, label NULL,
                PK(event_id, distance_m))

dedup_candidates(id, source_event_id, event_id, score, reasons jsonb,
                 state: pending|confirmed|rejected, created_at,
                 UNIQUE(source_event_id, event_id))

users(tg_id PK, filters jsonb, filters_v, created_at, last_seen_at)

heartbeats(component PK, beat_at)
```

Таблицу миграций ведёт `goose`.

### 4.2 Обоснование полей `events`
| Поле | Зачем в MVP |
|---|---|
| `title`, `title_norm` | показ и дедуп (`title_norm` — детерминированная функция от `title`) |
| `start_date`, `end_date` | многодневные события; фильтр по датам |
| `start_time` | карточка; NULL, если источник не дал |
| `timezone` | IANA-имя (`Europe/Moscow`, `Asia/Yekaterinburg`), определяется словарём город/регион → зона, иначе NULL. Время показывается как местное, без пересчёта. Дёшево хранить сейчас, трудно восстанавливать потом |
| `country_code`, `region`, `city`, `city_key`, `address` | международная модель; `country_code` определяется по правилам раздела 6; `city_key` — фильтр и нормализация; регион в SQL и модели, но не в UI |
| `event_type`, `status` | фильтр и карточка |
| `description` | короткий текст для карточки, до 1000 символов, обрезка по слову |
| `registration_url` | главное действие пользователя |
| `is_listed`, `merged_into_id` | видимость и слияние |
| `created_at`, `updated_at` | технические; `updated_at` меняется только при изменении канонических полей |

**Сознательно отсутствуют:** `lat`, `lon` (без геокодинга и радиуса пусты, колонку добавляет мгновенная миграция, координаты источника сохраняются в `payload`), `registration_status`, цена, версии и история.

### 4.3 Дистанции
- `distance_m` целое число метров, не строка. Допуск при слиянии (42,2 км и 42 195 м — одна дистанция).
- Дистанции канонического события — объединение дистанций связанных `source_events`. Пересобираются при изменении.
- Дистанция **не участвует в идентичности** события. Событие с 5 и 10 км — одно событие.
- Задел на будущее: цена добавится как `price_minor` и `currency` на `event_distances` отдельной миграцией. Временные ступени цены в MVP не моделируются.

### 4.4 Статус события и состояние наблюдения (строго разделены)
| | Значения | Кто меняет | Что означает |
|---|---|---|---|
| **`events.status`** | `scheduled`, `cancelled`, `postponed` | только явный статус источника | судьба самого соревнования |
| **`source_events.state`** | `active`, `missing`, `gone` | наблюдение за выдачей источника | видит ли источник эту запись |

Правила:
- **`gone` никогда не означает `cancelled`.** Исчезновение записи из источника не меняет `events.status`.
- Исчезновение влияет только на `events.is_listed`: событие скрыто из поиска, если **все** связанные `source_events` в `gone`. Оно остаётся в БД.
- Переход состояния наблюдения — только по **здоровым** прогонам (`ok`), и только для записей с `start_date ≥ сегодня` (прошедшие события легитимно исчезают из выдач):
  - запись не найдена в здоровом прогоне → `missing`, `missed_runs++`;
  - `missed_runs ≥ 3` и прошло не менее 72 часов с `last_seen_at` → `gone`;
  - запись снова найдена → `active`, `missed_runs = 0`.
- Прогоны `suspect` и `failed` не меняют ни счётчики, ни состояния.
- Перенос с новой датой меняет дату события. `postponed` ставится, когда источник явно сообщает о переносе без новой даты.
- Значения порогов (3 прогона, 72 часа) — стартовые, конфигурируемые.

### 4.5 Слияние событий
- `source_events` **никогда не удаляются**, в том числе после слияния канонических событий (история для отладки и пересчёта).
- При слиянии `event_id` у `source_events` проигравшего события переключается на победителя. Проигравшее событие остаётся как запись с `merged_into_id` и `is_listed = false`, чтобы старые ссылки и callback не ломались.
- Цепочки слияний схлопываются до корня.
- Подтверждение и отклонение кандидатов сохраняются в `dedup_candidates`. Отклонённая пара повторно не предлагается.

### 4.6 Индексы (стартовый набор)
- `events(start_date, id)` и `events(city_key, start_date, id)`, частичные: `WHERE is_listed AND merged_into_id IS NULL`;
- `events(country_code, start_date)` для кандидатов дедупа;
- `event_distances(distance_m, event_id)`;
- `source_events(event_id)`, `source_events(state, last_seen_at)`;
- `ingest_runs(source_id, started_at DESC)`.

Диапазон дистанций: `EXISTS`-подзапрос по `event_distances`. При медленной работе допустимо денормализовать `min/max` — по факту, не заранее.

### 4.7 Совместимость с будущим
Избранное (`favorites`), пользовательские подписки (`user_alerts`) и `event_changes` добавляются отдельными таблицами и ничего не ломают. `lat/lon`, цена, `registration_status` добавляются `ALTER TABLE`.

## 5. Ingestion pipeline

```
Scheduler → Fetch → RawDoc → Parse → SourceEvent → Validate → Normalize → Match/Deduplicate → PostgreSQL
```

| Стадия | Отвечает за | Свойства |
|---|---|---|
| **Fetch** | получить документ, соблюдая ограничения | сеть, rate limit, retry, лимит размера |
| **RawDoc** | результат Fetch | `URL`, `Body []byte`, `FetchedAt time.Time` |
| **Parse** | `RawDoc → []SourceEvent` | **чистая функция**, без сети, тестируется на сохранённых файлах |
| **Validate** | обязательные поля, разумные значения | название, парсимая дата, дата в `[сегодня−1 день, сегодня+3 года]` |
| **Normalize** | `title_norm`, `city_key`, метры, тип, часовой пояс | детерминирована, перезапускается поверх `payload` без повторной загрузки |
| **Match** | связать с каноническим событием или создать новое | см. раздел 9 |

### 5.1 Исходные данные
- `source_events.payload jsonb` содержит распарсенные поля источника «как есть». Пишется всегда.
- **Сырой HTML/JSON** хранится на диске, вне PostgreSQL: последние N документов на источник, с TTL. Для MVP допустимо упрощение: только последний ответ на источник плюс один предыдущий. Бесконечно HTML не копится.

### 5.2 Источник в коде
Каждый источник — свой пакет `internal/ingest/sources/<name>/` с `Fetch` и `Parse` и каталогом `testdata/` (`*.html`, `*.json` плюс golden-файлы ожидаемого результата). Тесты не ходят в сеть. Добавление источника: пакет, фикстуры, строка регистрации. Общая логика нормализации живёт в `normalize`, не в парсерах. Подключение нового источника **не требует изменения общего интерфейса ingestion и основной архитектуры pipeline**: источник подключается через предусмотренный source adapter/parser contract. Source-specific код добавлять разрешено, общий код (например, словарь синонимов городов) может дополняться.

Стабильный `external_id` обязателен. Если у источника его нет, используется нормализованный URL или другой устойчивый идентификатор, и это фиксируется в отчёте Phase 1.

### 5.3 Надёжность (стартовые значения, конфигурируемые)
| Что | Значение |
|---|---|
| HTTP-таймаут | 30 с общий, 10 с на подключение |
| Размер ответа | не более 10 МБ (`io.LimitReader`) |
| Retry | до 3 попыток на сетевые ошибки, 5xx и 429 (с учётом `Retry-After`), не на 4xx |
| Backoff | от 2 с, удвоение, full jitter, потолок 30 с |
| Rate limit | 1 запрос/с на хост, 1 одновременный запрос на хост, разные хосты параллельно (до 4) |
| Расписание | каждый источник раз в 6 часов со случайным сдвигом |
| Общий таймаут прогона | 30 минут |
| `User-Agent` | идентифицирует бота и содержит контакт |
| Сбор деталей | условный GET (`ETag`, `If-Modified-Since`); страницы деталей перезапрашиваются только при изменении хеша записи из списка |

Circuit breaker не добавляется. Его функцию выполняют рост интервала после подряд идущих сбоев и алерт.

### 5.4 Качество прогона
Статус прогона определяется автоматически. Стартовые значения, конфигурируемые, калибруются на реальных данных:
- база: медиана `parsed` за последние 7 прогонов со статусом `ok`, не менее 3 прогонов. Пока базы нет, действуют абсолютные проверки: `parsed ≥ 1`, доля `rejected ≤ 30 %`;
- **`suspect`:** `parsed` меньше 50 % базы; `parsed` больше 5× базы; `rejected/fetched` больше 20 %; доля дат вне допустимого диапазона больше 5 %; рост доли NULL по ключевым полям;
- **`failed`:** ошибка загрузки после ретраев, `parsed = 0`, паника парсера.

**`suspect` и `failed` прогоны ничего не применяют** — ни новых записей, ни изменений состояния наблюдения, ни статусов. Никакого массового удаления или отмены. Легитимный скачок объёма разблокируется вручную подкомандой (`worker accept-baseline --source X`), точный интерфейс определяется в Phase 3.

### 5.5 `ingest_runs`
Для каждого запуска источника: источник, `started_at`, `finished_at`, статус, `fetched`, `parsed`, `rejected`, `out_of_scope`, `upserted`, `error`. Это основа мониторинга качества, запрашивается обычным SQL.

## 6. Нормализация

- **`title_norm`:** нижний регистр, `ё→е`, отбрасывание года, номеров изданий («XV»), упоминаний дистанций («10 км») и общих слов («забег», «марафон» как стоп-слов при сравнении).
- **`city_key`:** ASCII-slug (`moscow`, `saint-petersburg`). Правила: очистка («г.», «город», скобки), `ё→е`, регистр; словарь синонимов («СПб», «Питер», «Санкт-Петербург», английские написания). Неизвестный город получает slug транслитерацией. ASCII-ключ помещается в 64 байта `callback_data`. Словарь хранится в коде (встроенный JSON или Go-литерал), отдельной таблицы городов нет.
- **Регион:** нормализованное имя; надёжность ниже, чем у города, поэтому в интерфейсе не используется.
- **Даты и время:** дата, время старта и часовой пояс хранятся раздельно (раздел 4.2). Россия имеет несколько часовых поясов, поэтому один `timestamp` не используется.
- **Дистанции:** метры целым числом, допуск при сравнении; распознавание «21,1 км», «полумарафон», «42.2 km» и подобного.
- **Тип:** отображение из разнородных обозначений источника в шесть значений, неизвестное → `other`.
- **Страна (`country_code`, ISO 3166-1 alpha-2).** MVP работает с Россией и Беларусью (D-24 Phase 5; остальные страны — вне MVP); `region` и `city` — тоже часть канонического события. Правила определения `country_code`:
  1. Если источник явно указывает страну, используется её нормализованное значение.
  2. Если страны в данных нет, но источник российский и **Phase 1 предварительно признала его кандидатом на fallback `RU`** (по структуре источника содержит только российские соревнования), fallback `RU` допускается. Окончательное подтверждение даёт санити-проверка на реальных данных в Phase 3 (ING-11): пока она не пройдена, статус остаётся предварительным.
  3. Если данные явно указывают страну вне каталога (не RU и не BY), событие не попадает в каталог автоматически: запись сохраняется в `source_events` с `match_state = out_of_scope`, событие не создаётся. Расширение на другие страны потом сводится к перематчингу.
  4. Если страну определить нельзя, а источник не признан кандидатом на fallback `RU`, молчаливого fallback нет: правило для такого источника выбирается в Phase 1.
- **Описание и изображения.** `description` при нормализации ограничивается **максимум 1000 символами** (обрезка по границе слова). Изображения в MVP **не скачиваются и не сохраняются**, в канонических таблицах для них нет полей.

Нормализация детерминирована, правила можно менять и пересчитывать поверх сохранённого `payload`.

## 7. Источники

### 7.1 Кандидаты
GET.RUN, Runlist, Марафонец. **Не считаются утверждёнными.** Цель MVP — 2–3 качественных источника, а не обязательное использование этих трёх. Неудобный или недоступный источник заменяется другим.

### 7.2 Порядок проверки (Phase 1, обязательна перед написанием парсера)
Порядок предпочтений: **официальный API → JSON / JSON-LD (schema.org `Event`) / встроенный JSON → sitemap / RSS → HTML → скрапинг как последний вариант.**

Для каждого кандидата проверяется:
1. доступность **с нашего VPS в Варшаве** (не с рабочей машины);
2. `robots.txt`;
3. ToS и ограничения на автоматический сбор;
4. официальный API;
5. JSON, JSON-LD, встроенный JSON;
6. sitemap и RSS;
7. структура HTML-страниц;
8. допустимые rate limits и разумная частота;
9. антибот-защита (Cloudflare, captcha, отдача другой версии страницы);
10. реальные поля и способ получения списка событий;
11. наличие стабильного `external_id`;
12. наличие ссылок на регистрацию;
13. как часто обновляются данные;
14. нужно ли посещать страницу каждого события, сколько HTTP-запросов потребуется;
15. авторские права на описания и изображения; персональные данные на страницах;
16. содержит ли источник только российские соревнования (основание для предварительного статуса кандидата на fallback `country_code = RU`, раздел 6; окончательное подтверждение — санити-проверка в Phase 3).

### 7.3 Ограничения
- **Не обходить CAPTCHA и другую защиту от ботов.** Если источник требует обхода или запрещает автоматический сбор, он не подключается.
- **Не собирать данные участников** (стартовые протоколы, списки регистрации). Основной объект — публичная информация о самих соревнованиях.
- Описания обрезаются до 1000 символов, изображения не копируются, всегда сохраняется ссылка на источник и показывается его название.
- Не юридическое заключение, а перечень технических ограничений, которые нужно учесть до подключения.
- Парсер не пишется до завершения проверки источника.

### 7.4 Кто выполняет проверки с VPS
Владелец делегирует инструментам (Claude, GSD) запуск **только read-only** блоков Phase 1 с VPS на следующих условиях (решение 33, 2026-09-27; до этого все команды выполнял владелец):
1. **Отдельный доступ проекта.** Ключ `~/.ssh/run_agg_vps` создан только для этого VPS; рабочие ключи владельца и его существующий `~/.ssh/config` не используются и не меняются. Отдельный SSH-конфиг `~/.ssh/run_agg.conf` с `IdentitiesOnly yes`, `IdentityAgent none`, `BatchMode yes`, `StrictHostKeyChecking yes`, `ForwardAgent no`, `RequestTTY no`, отдельный `known_hosts`. Открытый ключ добавляет на VPS сам владелец с префиксом `restrict` и удаляет после Phase 1.
2. **Только через обёртку `run_block.sh`** (хранится вне репозитория) и только блоки из белого списка `01-COMMANDS.md`; удалённая команда всегда `bash -s`. Блоки утверждает владелец командой `approve` после чтения; изменение блока отзывает утверждение (проверка по sha256).
3. **Автоматические проверки.** До запуска: `safety_lint`, GET.RUN gate и guard, непустая нагрузка, допустимое имя блока. После каждого прогона: `redaction_check` и `owner_leak_check`. При любой ошибке остановка; файл, не прошедший проверку, попадает в карантин. Сырой вывод, `VPS_IP`, `VPS_HOST`, контакт владельца и другие секреты не печатаются; значения лежат в `local.conf` (права 600) вне репозитория.
4. **Что остаётся под отдельным разрешением владельца:** любые изменения на VPS, установка пакетов, изменения firewall, systemd, Docker и другие административные действия (раздел 10.3). GET.RUN при `getrun_tos: ask-first`: с VPS только `dns` и `robots.txt`, страницы забегов не запрашиваются без отдельного разрешения.
5. Пароли, приватные ключи и токены в чат, документы и репозиторий не передаются. `robots.txt`, ToS и документацию API инструменты читают со своей стороны. Секреты из вывода в документы не записываются.

## 8. Telegram

### 8.1 Архитектура
`Telegram → Bot → store → PostgreSQL`. **Long polling.** Webhook, домен и reverse proxy в MVP не нужны. Redis для состояния не используется: состояние фильтров хранится в `users.filters` (jsonb) с версией `filters_v`.

### 8.2 Сценарий
`/start → «Найти забег» → фильтры → список → карточка → ссылка на регистрацию.`

- **Фильтры:** дата, город, дистанция, тип. Регион в SQL и модели есть, отдельного фильтра в интерфейсе нет.
- **По умолчанию:** будущие даты, вся Россия. Длинного мастера нет.
- **Дата:** пресеты («30 дней», «этот месяц», «следующий месяц») и выбор месяца.
- **Дистанция:** корзины (≤5 км, ~10 км, полумарафон, марафон, ультра); границы уточняются в Phase 4.
- **Город:** кнопки топ-10 по данным БД и текстовый ввод с приведением к `city_key`.
- **Карточка:** название, даты и время, город и адрес, тип, список дистанций, короткое описание, кнопка регистрации, источники со ссылками.
- **Статусы `cancelled` и `postponed` не скрываются.** В списке и в карточке они показываются явно с пометкой в начале названия: **`[ОТМЕНЁН]`** и **`[ПЕРЕНЕСЁН]`**. Из выдачи убирают только события с `is_listed = false` или `merged_into_id`.

### 8.3 Callback и пагинация
- Компактный `callback_data` (до 64 байт), роутинг по префиксу: `f:` фильтры, `p:` страница, `e:` карточка. Пример: `f:c:moscow`, `p:3:v7`, `e:1234`, где `v` — версия фильтров; при несовпадении бот просит обновить выдачу.
- Один обработчик на экран, а не на кнопку.
- **Пагинация `LIMIT/OFFSET`** по стабильному `ORDER BY start_date, id`, номер страницы в callback. Обоснование: выдачи — тысячи строк, кнопка «Назад» тривиальна. Переход на keyset при выдачах в десятки тысяч.
- Листание через `editMessageText`. На каждый callback — `answerCallbackQuery`. Обработчики идемпотентны (состояние фильтров задаётся абсолютными значениями).

### 8.4 Админ-функции
Доступ только для `ADMIN_TG_IDS`:
- `/dupes` — просмотр потенциальных дублей с подтверждением и отклонением;
- `/runs` — последние прогоны по источникам.

Ежедневная сводка по кандидатам вместо уведомления на каждую запись. Это не веб-админка.

### 8.5 Данные пользователей
Хранятся Telegram ID, настройки поиска и ответы добровольной анкеты (пол, возрастная группа, страна и город проживания, виды спорта). Анкета необязательна: отказ не ограничивает функции бота, любой ответ можно изменить в `/profile`. Username, имена и другие данные из Telegram не сохраняются.

## 9. Дедупликация

Отдельный этап после нормализации. Задача — избежать и **ложного объединения** разных соревнований, и **дублирования** одного.

### 9.1 Уровни
1. **`(source_id, external_id)`** — идемпотентность записи источника. Это не дедуп между источниками.
2. **Кандидаты:** та же страна и пересечение диапазонов дат.
3. **Оценка:** сходство нормализованных названий (триграммный Jaccard в Go, без `pg_trgm`), совпадение `city_key`, домен организатора, другие признаки. Координаты — в будущем.
4. **Решение:** высокая уверенность → автоматическая связь; средняя → отдельное событие плюс запись в `dedup_candidates`; низкая → отдельное событие.

### 9.2 Пороги
Значения **0,7 / 0,4 — только стартовая гипотеза**, не окончательные. Схема оценки и пороги **конфигурируемы** и **калибруются на реальных данных первых источников** (Phase 5) на размеченном наборе пар (порядок 30–50).

### 9.3 Правила
- **Одинаковый хост и путь регистрации — только дополнительный сигнал**, не самостоятельное основание для автоматического слияния.
- Дистанция не входит в идентичность и не обязательна.
- Записи одного источника автоматически не склеиваются, если парсер не дал `group_key`.
- Приоритет — избегать ложных слияний: лишняя копия в выдаче менее вредна, чем потеря разных событий.
- Ручные решения фиксируются и не отменяются автоматикой.
- Сложный случай: источник, публикующий каждую дистанцию отдельным событием. Решается подсказкой группировки от парсера; иначе принимаются дубли и разбираются через `/dupes`.
- Годовые повторения одного названия различаются датой (дата входит в ключ кандидата).

### 9.4 Масштабирование дедупа
Тот же принцип; ML и эмбеддинги допускаются только если ручная очередь станет узким местом. В MVP не входят.

### 10.2 Состав
Docker Compose: `postgres` (образ PostgreSQL 17, том, порт наружу не публикуется, healthcheck), `migrate` (одноразовый), `bot`, `worker` (`restart: unless-stopped`, ротация логов `max-size 10m`, `max-file 3`). Не используются: Kubernetes, Kafka, Redis, Elasticsearch, отдельный сервер PostgreSQL.

### 10.3 Результаты аудита VPS (и что с ними делать)
| Находка | Действие | Когда |
|---|---|---|
| `docker compose` отсутствует (стоит `docker.io` из Ubuntu без плагина Compose) | установить `docker-compose-v2` из того же репозитория Ubuntu | подготовка к production, только с разрешения |
| **`tinyproxy` слушает на всех интерфейсах, порт 8888** | расследование (см. раздел 12.3) | Phase 1, до production |
| Часы не синхронизированы (`System clock synchronized: no` при активном NTP) | диагностика `timedatectl timesync-status`, исправление | до production |
| Swap отсутствует | добавить swap 1–2 ГБ | подготовка к production |
| Ожидается перезапуск, доступны обновления, вход под `root` | системное обновление и перезагрузка **не выполнять автоматически**; сначала проверка сервисов (прежде всего `tinyproxy`), затем отдельное разрешение владельца. Затем пользователь без `root`, отключение входа `root` по паролю | по отдельному разрешению |
| Порты Docker обходят `ufw` | порты БД не публикуются | при развёртывании |

Системные изменения на VPS (установка пакетов, обновление, перезагрузка, swap, изменение сервисов) выполняются только с отдельного разрешения владельца.

### 10.4 Хост
`ufw` пропускает только SSH (входящие порты приложению не нужны при long polling), вход по ключам, NTP. Автоматические обновления (`unattended-upgrades`) не являются частью MVP. Опционально, только после отдельного разрешения владельца VPS и только в Phase 6. Системные обновления автоматически не выполняются.

## 11. Мониторинг, алерты, бэкапы

### 11.1 Мониторинг (MVP)
Структурные логи `slog`, таблица `ingest_runs`, алерты админу в Telegram, heartbeat и healthcheck. Prometheus и Grafana не добавляются. **Порядок по фазам:** Phase 3 — структурные логи, `ingest_runs` и состояние ошибок и здоровья источника (без Telegram-алертов); Phase 4 — Telegram-алерты админу о `failed`, `suspect` и всплеске ошибок парсера (бот уже существует); Phase 6 — heartbeat, healthcheck, инфраструктурные алерты (БД, сбой бэкапа) и внешний heartbeat.

- **Heartbeat.** `bot` и `worker` раз в минуту пишут строку в `heartbeats` и следят за «соседом»: устарел больше 10 минут → алерт.
- **Docker healthcheck** через подкоманду `healthcheck` и `pg_isready`.
- **Внешний heartbeat** (dead man's switch) входит в production-фазу и не блокирует локальную разработку. Он нужен на случай падения всего хоста. Конкретный сервис выбирается позже.

### 11.2 Условия алертов

Отправка в Telegram появляется с Phase 4 (в Phase 3 — только логи и `ingest_runs`); инфраструктурные алерты — Phase 6.

| Условие | Поведение |
|---|---|
| Прогон источника `failed` | алерт |
| Прогон `suspect` | алерт с деталями |
| Всплеск ошибок парсера | алерт |
| PostgreSQL недоступна | алерт (ретраи с backoff) |
| Устарел heartbeat `worker` или `bot` | алерт |
| Telegram API недоступен | только лог; ретраи |
| Сбой бэкапа | алерт |

Алерт отправляется один раз при смене состояния, повтор-напоминание через 24 часа.

### 11.3 Бэкапы
- **Ночной `pg_dump`** → шифрование → **внешнее хранилище** (не единственная копия на этом VPS).
- Шифрование ассиметричное: на VPS лежит только публичный ключ. **Ключ расшифровки на этом VPS не хранится.** Инструмент (`age` или `gpg`) и место хранения ключа выбираются до Phase 6.
- **Retention: 7 ежедневных + 4 еженедельных.**
- **Проверка восстановления** периодически (стартово раз в месяц) в отдельном контейнере, шаги записаны в runbook. Не проверенный бэкап не считается бэкапом.
- Сбой бэкапа даёт алерт. PITR и WAL-архив не нужны: потеря до суток допустима, каталог восстанавливается сбором, невосстановимы только пользовательские настройки и ручные решения дедупа.

## 12. Безопасность

### 12.1 Секреты
Никаких секретов в репозитории и документации: токен бота, пароль БД, `ADMIN_TG_IDS`, ключи. Только переменные окружения; `.env` вне репозитория, права 600, в `.gitignore`. IP-адреса сервера и хостнейм в документы не записываются.

### 12.2 Данные и права
Хранятся Telegram ID, настройки поиска и ответы добровольной анкеты; ответы хранятся бессрочно и попадают в резервные копии базы. Данные участников соревнований не собираются. Изображения не копируются, описания ограничены, источник всегда указан. Сервер расположен в ЕС, поэтому персональные данные минимизируются (это не юридическое заключение).

### 12.3 `tinyproxy` на VPS
**Не входит в архитектуру проекта.** Бот и worker не используют его для запросов к источникам. До production отдельно выяснить: зачем он установлен, кто его использует, директивы `Listen` и `Allow` (и наличие аутентификации; содержимое секретов не запрашивается и не записывается), состояние `ufw`, нужен ли он вообще.

- Если он нужен для других задач владельца, **не удалять и не менять без отдельного подтверждения**.
- Если не нужен и является открытым прокси, предложить безопасный вариант закрытия (ограничить `Listen` и `Allow`, закрыть порт в `ufw`, либо отключить сервис). Выполняется только с подтверждения.

## 13. Масштабирование

Одна нода, без преждевременной распределённой архитектуры. Оценка порядка величин, не замеры.

| | A: 10 источников, 10 тыс. событий, 100 польз. | B: 30 / 100 тыс. / 10 тыс. | C: 100 / 1 млн / 100 тыс. |
|---|---|---|---|
| CPU | простаивает | пики при парсинге и пересчётах | 4 shared vCPU справляются, заметны бэкфиллы |
| RAM | ~1 ГБ | горячие данные (будущие события) в кэше | БД не помещается целиком, горячий набор мал |
| PostgreSQL | тривиально | сотни МБ – 2 ГБ, поиск за миллисекунды | 10–20 ГБ с индексами и `payload` |
| HTTP | минуты на цикл | страницы деталей доминируют, нужны условные GET и хеши | 100 хостов, нужна честность планировщика |
| Парсеры | редкие поломки | еженедельные поломки | **операционная нагрузка — главный ресурс** |
| Дедуп | мгновенно | blocking по дате; бэкфилл разово | тот же принцип, полный пересчёт дорог |
| Telegram API | не ограничивает | рассылок нет в MVP | рассылка на 100 тыс. — порядка часа, нужна очередь с лимитом |
| Сеть | пренебрежимо | пренебрежимо | пренебрежимо |
| Диск | сотни МБ | ~1–3 ГБ | **30 ГБ впритык**: больший диск или архив `payload` |

**Вывод:** текущая архитектура и VPS выдерживают сценарий B с запасом. Сценарий C требует прежде всего диска и чистки `payload`. Распределённость не нужна. 1 млн событий — это в основном история за годы.

Первое, что менять при росте: (1) диск или архив `payload`; (2) очередь исходящих сообщений при появлении рассылок; (3) `min/max` дистанций в `events`; (4) keyset-пагинация.

## 14. Roadmap

Нумерация совместима с GSD. **Phase 1 соответствует логическому Phase 0** (discovery), который обязателен перед Phase 2.

| Phase | Название | Делаем | Не делаем | Готово, когда |
|---|---|---|---|---|
| **1** | **Source Discovery / VPS Audit** | Проверка 2–3 источников по разделу 7.2 с VPS (команды только на чтение выполняет владелец, раздел 7.4); аудит VPS (`tinyproxy`, часы, `ufw`, Docker); решение по выбору источников и замене; отчёт | Код, миграции, любые изменения на VPS | Отчёт по источникам и VPS готов; источники подтверждены или заменены; решения зафиксированы |
| **2** | **Foundation** | Модуль Go (1.27.1), БД и миграции (`goose`), домен `event`, `normalize` (словарь городов, дистанции, даты, зоны), dev-окружение, тестовая инфраструктура с реальной PostgreSQL | Бот, парсеры, дедуп | Миграции применяются; юнит-тесты `normalize`; интеграционный тест upsert |
| **3** | **First Source** | Fetch, Parse, Validate, upsert, `ingest_runs`, проверки прогона, состояние ошибок и здоровья в логах и `ingest_runs` (без Telegram-алертов); golden-тесты без сети; пробный запуск на VPS при готовности предпосылок | Дедуп, второй источник | Прогон идемпотентен; тесты зелёные без сети; реальные данные в БД |
| **4** | **Telegram Search** | Long polling, фильтры, список, карточка, пагинация, атрибуция, админ-доступ, Telegram-алерты админу (`failed`, `suspect`, всплеск ошибок парсера), пометки `[ОТМЕНЁН]` и `[ПЕРЕНЕСЁН]` | Избранное, гео, регион в UI | Забег находится по городу, дате, дистанции и типу на реальных данных |
| **5** | **Multiple Sources & Deduplication** | Источники 2–3, `match`, `dedup_candidates`, `/dupes`, сводка админу, калибровка порогов на размеченных парах | ML, веб-админка | Известные дубли склеены; разные забеги не слиты автоматически; очередь читаема |
| **6** | **Production** | Compose на VPS, установка плагина Compose, swap, NTP, обновление и перезагрузка (по разрешению), бэкапы и проверка восстановления, внешний heartbeat, runbook, ротация логов, закрытие находок по VPS | Prometheus, Redis, увеличение VPS | Переживает перезапуск; алерт приходит; восстановление проверено; хост подготовлен |

Пробный запуск на VPS в Phase 3 желателен, но требует установки плагина Compose (системное изменение с отдельным разрешением). Если разрешения ещё нет, запуск на VPS переносится в Phase 6, а доступность источников из Варшавы уже проверена в Phase 1.

После MVP (по отдельному решению): избранное, уведомления, `event_changes`, гео и радиус, новые источники и страны, цена.

## 15. Критерии готовности MVP

1. Работает не менее 2 подтверждённых источников; прогоны идут по расписанию без ручного вмешательства.
2. Пользователь находит забег по дате, городу, дистанции и типу; карточка содержит ссылку на регистрацию и источники.
3. На размеченном наборе пар автоматическое слияние **не даёт ложных слияний**; средние случаи попадают в `/dupes`.
4. Сбой источника, подозрительный прогон, недоступная БД и остановка worker приводят к **алерту**, а не к тихой порче данных. `suspect` и `failed` прогоны ничего не применяют.
5. Исчезновение записи из источника **не меняет `events.status`**, влияет только на `is_listed`, и только по здоровым прогонам.
6. Парсеры покрыты golden-тестами и не ходят в сеть в тестах.
7. Перезапуск контейнеров и хоста не приводит к потере данных; прогоны идемпотентны.
8. Бэкап выгружается во внешнее хранилище, шифрован, ключ расшифровки не на VPS, **восстановление проверено хотя бы один раз**.
9. Секреты не попали в репозиторий и документацию.
10. Все известные ограничения из раздела 16 записаны.

## 16. Известные ограничения

- События без метража (суточные забеги, «6 часов») не имеют строки в `event_distances` и не находятся по фильтру дистанции.
- Регион ненадёжен (источники редко его отдают), поэтому не выведен в интерфейс.
- Нет цены, координат, статуса регистрации и истории изменений; старая дата при переносе перезаписывается.
- Возможны дубли в «средней» зоне до ручного разбора; ложные слияния считаются более серьёзной ошибкой, поэтому автоматика консервативна.
- Один VPS без отказоустойчивости; при падении хоста поможет только внешний heartbeat, восстановление ручное.
- Российские источники могут быть недоступны или отдавать другую страницу с зарубежного IP; выясняется в Phase 1.
- Зависимость от структуры чужих сайтов: поломки парсеров неизбежны, поэтому важны тесты и алерты.
- Только русскоязычный интерфейс; транслитерация ru↔en в сопоставлении не поддерживается.
- Долгосрочный риск диска при накоплении `payload`.

## 19. Журнал решений

| # | Решение | Причина |
|---|---|---|
| 1 | Слой `source_events` между источниками и `events` | дедуп обратим, можно пересчитывать без повторной загрузки |
| 2 | `Fetch` и `Parse` разделены, `Parse` чистая | парсеры тестируются на файлах без сети |
| 3 | `lat/lon` не добавлять | без геокодинга и радиуса пусты; добавление колонки мгновенное |
| 4 | Без `pg_trgm`, схожесть в Go | кандидатов единицы; детерминированные юнит-тесты; нет зависимости от локали БД |
| 5 | `LIMIT/OFFSET` вместо курсора | выдачи малы; «Назад» тривиально |
| 6 | Цена и `registration_status` отложены | ненадёжные данные, вводят в заблуждение |
| 7 | Слоя `usecase` нет | тонкий проброс без логики |
| 8 | Один бинарник с подкомандами | один образ, единый способ запуска миграций |
| 9 | Пороги дедупа 0,7 / 0,4 — гипотеза, конфигурируемы, калибруются на данных | нет реальных данных для окончательных значений |
| 10 | Совпадение хоста и пути регистрации — только доп. сигнал | разные события могут делить страницу организатора |
| 11 | `events.status` и `source_events.state` разделены; `gone ≠ cancelled` | исчезновение из выдачи не доказывает отмену |
| 12 | Исчезновение не меняет `events.status`, влияет на `is_listed` | не врать пользователю, не терять данные |
| 13 | `source_events` не удаляются при слиянии | история для отладки и пересчёта |
| 14 | `suspect` / `failed` прогоны ничего не применяют | защита от порчи данных сломанным парсером |
| 15 | Phase 1 (discovery) обязательна перед разработкой | доступность источников с VPS — главный неизвестный риск |
| 16 | Источники заменяемы, цель — 2–3 качественных | не привязываться к именам |
| 17 | PostgreSQL 17, Go 1.27.1 | зрелая мажорная версия; версия, установленная у владельца |
| 18 | `pgx/v5` + `pgxpool`, `goose`, `go-telegram/bot` | проверено по документации; минимум зависимостей |
| 19 | Планировщик, rate limiter, конфиг — стандартная библиотека | не добавлять зависимости без необходимости |
| 20 | Бэкапы шифрованные, ключ не на VPS, 7 daily + 4 weekly, проверка восстановления | защита данных и реальная восстановимость |
| 21 | Внешний heartbeat — в production-фазе | не блокирует локальную разработку |
| 22 | `tinyproxy` вне архитектуры; менять только с подтверждения | может быть нужен владельцу для других задач |
| 23 | Обновление и перезагрузка VPS только по отдельному разрешению | сначала проверка сервисов |
| 24 | Политика Git: `commit_docs = true`; GSD и `gsd-executor` коммитят самостоятельно (не только `.planning/`); обычный `git push` в remote проекта разрешён; `push --force`, `--force-with-lease`, `reset --hard`, удаление веток и remote запрещены без подтверждения; теги отключены; в сообщениях коммитов нет упоминаний ИИ; remote создаёт владелец; CI вне MVP | обновлено по решению владельца (заменяет прежнее «коммиты и push только вручную») |
| 25 | VPS достаточен, заранее не увеличивать | измеренные ресурсы с большим запасом |
| 26 | Telegram-алерты админу переносятся в Phase 4; в Phase 3 только логи, `ingest_runs`, состояние ошибок | бота ещё нет; фаза не зависит от более позднего решения (токен и `ADMIN_TG_IDS` — Phase 4) |
| 27 | `cancelled` и `postponed` не скрываются, показываются с пометкой `[ОТМЕНЁН]` / `[ПЕРЕНЕСЁН]` | пользователь должен видеть, что событие отменено или перенесено |
